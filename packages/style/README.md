# @omnifield/probe-web-style

Стилевой слой локации `probe-web`: **токен-контракт**, **`cn`/`createStyle`** и **дефолтная
пара тем**. Основание, на котором стоит кит, — и то, от чего не зависит никто выше.

Зависимостей на `ui`, `runtime` и `build` здесь нет и быть не может: направление
зависимостей одностороннее. Контракт зон целиком — `kb:PROBEWEB-4`; эта страница его не
заменяет, а пересказывает со стороны пакета. Цветовая модель и её основания — `kb:PROBEWEB-12`.

## Что наружу

| точка | что даёт |
|---|---|
| `@omnifield/probe-web-style` | `cn`, `createStyle`, токен-контракт, генератор шкал, **модель темы и её отрисовка в CSS**, гейт контраста, механика тем, реэкспорт `cva` |
| `@omnifield/probe-web-style/base.css` | сброс, производные размерные шкалы, **роли**, устаревшие псевдонимы, `color-scheme` |
| `@omnifield/probe-web-style/themes.css` | **значения ступеней** дефолтной пары: `:root` — светлая, `.dark` — тёмная |

CSS через корневой вход НЕ идёт: манифест объявляет `sideEffects: false`, и импорт-побочка
из корня была бы выброшена tree-shaking'ом. Стили подключает приложение — двумя строками:

```ts
import "@omnifield/probe-web-style/themes.css"; // значения ступеней
import "@omnifield/probe-web-style/base.css";  // сброс, шкалы, роли
```

**Оба файла обязательны.** Роли живут в `base.css`, значения — в `themes.css`; без первого
нечему ссылаться, без второго нечего показывать. Порядок не важен: `var()` разрешается на
этапе вычисления значения, а не по месту в файле.

## Два уровня: ШКАЛА и РОЛЬ

Ровно то, ради чего переписан цвет (`kb:PROBEWEB-12`, пункты 1–2).

```
--brand-9            ступень: сырьё, у неё номер и закреплённое назначение   → themes.css
--brand-solid        роль: назначение в интерфейсе, ССЫЛКА на ступень        → base.css
--primary            устаревшее имя, ссылка на роль                          → base.css
```

Проверка смысла одним вопросом: **смена бренда обязана менять шкалу, не трогая роли.**
Поэтому роли не входят в тему — они одинаковы для всех палитр и обоих режимов, и копия в
каждой теме означала бы, что разделение объявлено, но не сделано.

**Цепляйся за РОЛЬ.** Ступень — это из чего роль сделана; она может быть перенастроена.

### Двенадцать ступеней и что каждая значит

| ступень | назначение | гарантия контраста |
|---|---|---|
| 1 | фон приложения | — (фон) |
| 2 | фон приложения, приглушённый | — (фон) |
| 3 | фон элемента | — (фон) |
| 4 | фон элемента при наведении | — (фон) |
| 5 | фон элемента при нажатии | — (фон) |
| 6 | тонкая граница, разделитель | — (оформление) |
| 7 | граница элемента | — (оформление) |
| 8 | сильная граница, кольцо фокуса | **≥3:1** к ступеням 1–2 (1.4.11) |
| 9 | сплошной акцент | — (верность бренду) |
| 10 | сплошной акцент при наведении | — (верность бренду) |
| 11 | текст низкого контраста | **≥4.5:1** к ступеням 1–3 (1.4.3) |
| 12 | текст высокого контраста | **≥4.5:1** к ступеням 1–5 (1.4.3) |
| `contrast` | подпись поверх сплошной ступени | **≥4.5:1** к ступеням 9–10 (1.4.3) |

Шкал три — `neutral`, `brand`, `danger`; плюс отдельный ряд `--chart-1…5` (категориальные
цвета данных, каждый ≥3:1 к фону приложения — на графике цвет носит информацию).

У каждой шкалы есть **параллельный альфа-ряд** `--<шкала>-a1…a12` и одно отдельное значение
`--scrim` — см. «Слои поверх страницы».

**Где гарантии НЕТ и почему** — перечень объявлен явно и живёт кодом (`NO_PROMISE`), потому
что молчание читается как «гарантия есть»:

- **1–5** — фоны: контраст даёт то, что НА них, а не они сами;
- **6–7** — тонкая граница и разделитель: оформление, а не носитель информации;
- **9–10** — сплошной акцент: сохраняем верность бренду. 1.4.11 требует контраста от того,
  что ИДЕНТИФИЦИРУЕТ контрол; у кнопки с видимой подписью это подпись, и её контраст
  обещает ступень `contrast`. Кнопка без подписи (одна иконка) — забота того, кто её рисует.

### Роли

Нейтральные: `--surface`, `--surface-subtle`, `--element`, `--element-hover`,
`--element-active`, `--separator`, `--border`, `--border-strong`, `--element-solid`,
`--element-solid-hover`, `--on-element-solid`, `--text-muted`, `--text`.

Бренд: `--brand-element`, `--brand-element-hover`, `--brand-element-active`,
`--brand-border`, `--focus-ring`, `--brand-solid`, `--brand-solid-hover`, `--on-brand-solid`,
`--brand-text`, `--brand-text-strong`.

Опасность: `--danger-element`, `--danger-element-hover`, `--danger-border`, `--danger-solid`,
`--danger-solid-hover`, `--on-danger-solid`, `--danger-text`.

Просвечивающие: `--overlay`, `--tint-hover`, `--tint-active`, `--brand-tint`, `--danger-tint`.

Имя роли никогда не кончается номером ступени — иначе потребитель цепляется за сырьё.

**Чего в ролях нет и не будет без разговора:** отдельного состояния «сплошной при нажатии».
Модель отдаёт сплошному акценту две ступени (9 и 10), а не три; третье состояние — это
изменение МОДЕЛИ, а не добавление имени. Нажатие показывается мягким вариантом
(`--brand-element-active`) или не цветом вовсе.

## Смена бренда — одно значение

```ts
import { createTheme, registerTheme } from "@omnifield/probe-web-style";

registerTheme(createTheme({ name: "ocean", brand: "#0f6fde" }));
```

Семя понимается как `oklch(L C H)` или `#rrggbb`. Незаданная шкала берётся из дефолтной
пары: сменить один только бренд стоит одного значения, а не переписывания всех трёх.

**Шкала считается ПРИ СБОРКЕ, в CSS уезжают готовые значения.** Сверка 2026-08-16:
`oklch()` и `color-mix()` поддержаны повсеместно, относительный синтаксис цвета — около 90%.
Девяноста процентов достаточно для украшения и недостаточно для того, на чём держится весь
вид: у оставшихся цвет не деградирует, а исчезает. Рантайм-генерация разрешена ровно в одном
месте — в ручке бренда на стенде `skin`, где отсутствие поддержки означает «ручка не
работает у части», а не «вид сломан у всех».

Тёмная половина — **своя шкала**, а не инверсия светлой: при инверсии фон элемента
становится текстом, то есть назначение ступеней перестаёт выполняться.

### Откуда берутся значения ступеней

- **1–7** — лестница светлоты режима;
- **8 и 11** — РЕШАЮТСЯ из порога нормы: это самая светлая граница, которая ещё даёт 3:1, и
  самый приглушённый текст, который ещё даёт 4.5:1. Основание значения — WCAG, а не вкус;
- **9–10** — от семени бренда: светлота, цветность и тон приходят от него. В тёмном режиме
  сплошная ступень сохраняет ОТНОШЕНИЕ к фону своего режима, а не абсолютную светлоту:
  чёрная кнопка на белом и чёрная кнопка на чёрном — это не одна тема в двух режимах;
- **12** — предельная читаемая краска режима;
- **`contrast`** — та сторона (светлая или тёмная), которая даёт больший запас над 4.5:1.

Наведение уводит сплошную ступень ОТ её собственной подписи, а не «в светлом темнее»: иначе
светлая кнопка с тёмной подписью на наведении роняет контраст подписи ниже нормы, и контрол
соответствует норме ровно до того, как на него навели.

Шкала может быть НЕмонотонной: ступени 9–10 идут от бренда, и у светлого бренда они
окажутся светлее текстовых. Это свойство модели, а не дефект — тот же эффект у любой
системы, которая обещает верность бренду.

### Гейт контраста

Обещание проверяется машиной, а не глазами: `test/contrast.test.ts` считает контраст на
**180 шкалах на режим** (12 тонов × 5 светлот × 3 цветности) — обещание, проверенное на трёх
наших цветах, это не обещание, а совпадение.

Та же формула доступна снаружи: тот, кто ставит свой бренд, обязан уметь проверить обещание
на своих значениях **тем же** способом, иначе «проверено» у него и у нас означает разное.

```ts
import { AA_TEXT, contrastRatio } from "@omnifield/probe-web-style";

contrastRatio("#1f6feb", "#ffffff") >= AA_TEXT;
```

Считается по WCAG 2.2 (Recommendation, 12 December 2024), критерии 1.4.3 (текст, 4.5:1) и
1.4.11 (нетекстовые элементы, 3:1). Цвет вне охвата sRGB отображается в охват НАМИ, а не
браузером: браузерная обрезка меняет светлоту, и посчитанное разошлось бы с показанным.

## Слои поверх страницы

Два разных вопроса, и путать их дорого: **чем красить** просвечивающий слой и **в каком
порядке** слои лежат.

### Альфа-ступени: чем красить

Сплошная ступень закрывает то, что под ней. Слою поверх страницы это подходит не всегда:
затемнение под диалогом обязано просвечивать, а подсветка при наведении ложится на
**произвольный** фон — полосатую таблицу, картинку, чужой блок, — а не на известный.

Поэтому у каждой шкалы есть параллельный ряд: **ступень `aN` поверх ступени 1 даёт ступень
`N`**. Обещание проверяется машиной (`test/alpha.test.ts`), а не глазами на стенде.

```css
[data-slot="row"]:hover { background-color: var(--tint-hover); }
[data-slot="dialog-overlay"] { background-color: var(--overlay); }
```

Три свойства, о которых надо знать заранее:

- **Совпадение гарантировано только поверх ступени 1.** На произвольном фоне вуаль его
  подкрашивает, а не заменяет, — ради этого альфа-ряд и заводится.
- **Альфа-ступень следует за режимом:** в светлом затемняет, в тёмном осветляет. Для
  подсветки при наведении это ровно то, что нужно.
- **Верхние ступени насыщенных шкал вырождаются в непрозрачные.** Цвет с почти нулевым
  каналом поверх почти белого фона недостижим ни при какой прозрачности — это свойство
  композиции, а не дефект. В такой точке ступень честно совпадает со сплошной.

**Затемнение под модальным слоем — это `--overlay`, а не альфа-ступень.** Оно чёрное в обоих
режимах: осветляющая вуаль в тёмной теме не убирает содержимое из фокуса, а подсвечивает его.
От шкалы берётся только сила перекрытия — прозрачность девятой альфа-ступени светлого режима.

**Гарантии контраста на альфа-ступенях нет и быть не может:** контраст полупрозрачного цвета
зависит от того, что под ним. Считает его тот, кто знает подложку.

### Шкала слоёв: в каком порядке

| токен | значение | что лежит |
|---|---|---|
| `--z-base` | 0 | обычный поток страницы |
| `--z-dropdown` | 10 | панель списка: выпадающий список, автодополнение |
| `--z-popover` | 20 | поповер, всплывающая подсказка |
| `--z-overlay` | 30 | затемнение под модальным слоем |
| `--z-dialog` | 40 | диалог, выезжающая панель |
| `--z-toast` | 50 | уведомление |

Пока слой один, `z-index: 1` работает. При четырёх слоях число из головы спорит с чужим
числом из головы, и спор выигрывает тот, кто написал больше. **Порядок слоёв — контракт:**
перестановка двух слоёв ломает чужой вид так же, как переназначение ступени, и едет мажором.

Шаг 10, а не 1: между нашими слоями обязано остаться место для чужого — кому нужен слой между
поповером и диалогом, вписывает 25 и не просит нас перенумеровать шкалу.

**Что шкала НЕ решает.** Мы объявляем порядок; контекст наложения создаёт тот, кто рисует
слой. `z-index` действует только среди соседей по контексту (CSS Position 3, §9), и никакой
токен не поднимет слой, вложенный в чужой `transform` или `filter`. Слои поверх страницы
монтируются порталом в корень — это забота зон `ui` и `skin`.

## Размерные шкалы

Приём тот же, что у скруглений: производная шкала от ОДНОГО семени. Семя задаёт тема,
ступени считает `base.css`.

| семя | ступени | плотность |
|---|---|---|
| `--radius` | `--radius-xs…3xl`, `--radius-full` | нет |
| `--space` | `--space-1…10` (сетка 4px) | **да** |
| `--font-size` | `--font-size-xs…4xl` | нет |
| `--control-height` | `--control-height-sm/md/lg` | **да** |
| `--border-width` | `--border-width-1/2/4` | нет |
| `--tracking` | `--tracking-tight/normal/wide` | нет |

Без шкалы намеренно: `--leading-*` (высота строки — безразмерное отношение),
`--weight-*` (нормированный ряд, CSS Fonts 4 §2.3), `--control-target-min` (пол нормы),
`--motion-*` и `--ease-*` (подобранный ряд, а не размеры).

### Плотность — ось, а не набор значений

`--density` умножает **интервалы и высоты контролов**. Кегль она не трогает: уменьшенный
плотным режимом текст ломает 1.4.4 Resize Text, а плотность нужна ради количества строк на
экране, а не ради мелкого шрифта. Скругления и толщины — тоже нет: это форма, а не размер.

```css
.table-dense { --density: 0.875; }
```

**Нижняя граница оси — 0.75**, и она посчитана, а не назначена: при плотности `d` нижняя
ступень контрола даёт `2.5rem × 0.8 × d`, и она обязана остаться не ниже минимального
размера цели 24×24 CSS-пикселя (WCAG 2.2, 2.5.8). Ниже границы оформление перестаёт
соответствовать норме, и узнаёт об этом не тот, кто крутил ручку.

## Прежний плоский набор — устарел

`--background`, `--foreground`, `--card*`, `--popover*`, `--primary*`, `--secondary*`,
`--muted*`, `--accent*`, `--destructive*`, `--input`, `--ring`, `--sidebar-*` — **живы и
выражены через роли**, но объявлены устаревшими. Удаление — мажорным поднятием версии.

Два имени на одно и то же — это две правды; новый код берёт роли. Что изменилось по смыслу:

- `--accent` был вторым именем приглушённого фона, которым за неимением ступени затыкали
  наведение; теперь это ровно ступень наведения (`--element-hover`);
- `--input` был серым, которым `skin` красил фон поля; теперь это явный `--element`;
- `--destructive-foreground` был чистым белым на красном — **4.37:1, ниже порога 1.4.3**.
  Теперь подпись выбирается по контрасту, и гейт краснеет, если порог не взят;
- `--tracking-normal` из СЕМЕНИ стал ступенью, семя зовётся `--tracking`. Прежнее имя было
  и семенем, и ступенью сразу, а токен, объявленный через самого себя, — цикл, и браузер
  такое свойство отменяет. Тема, задававшая `--tracking-normal`, задаёт `--tracking`.

`--border` и `--chart-1…5` устаревшими НЕ объявлены: первое стало ролью под тем же именем и
с тем же смыслом, второе — самостоятельный ряд.

## Политика выпусков: вид ломается токенами

**Изменение состава или назначения токенов — ЛОМАЮЩЕЕ изменение** (`kb:PROBEWEB-12`, п. 6).

- добавление токена или изменение состава — **минор** с явной записью в примечаниях;
- удаление токена или переназначение ступени/роли — **мажор**.

Причина: потребитель цепляется за токены так же, как `skin` цепляется за `data-slot`.
Переназначенная ступень ломает чужой вид ровно так же, как переименованный слот. Пока пакет
в `0.x`, ломающее едет минором — это правило semver, а не послабление нашей политики.

## Токены: тема — это ДАННЫЕ

Контракт оформлен типом, а не «что нашлось в CSS»:

- `SCALE_TOKENS` — 81 цветовой токен (3 шкалы × 25 + 5 рядов графика + `--scrim`),
  **обязательное ядро**; 25 на шкалу = 12 сплошных ступеней + 12 альфа + подпись на сплошной;
- `THEME_META_TOKENS` — шрифты, тени и СЕМЕНА размерных шкал; опциональны;
- `ROLE_TOKENS` / `LEGACY_TOKENS` / `LAYER_TOKENS` — роли, устаревшие имена и шкала слоёв;
  **в тему не входят** (порядок слоёв от палитры не зависит);
- `ThemeTokens` / `ThemeDefinition` — тема как объект; `themeToCss` — её сериализация;
- `PALETTE_TOKENS` / `PaletteToken` — прежние имена `SCALE_TOKENS` / `ScaleToken`, оставлены
  устаревшими.

`dist/css/themes.css` и `dist/css/base.css` **генерируются** при сборке: значения ступеней —
из семян, перечни ступеней и ролей — из массивов в TS. Второй копии правды в репозитории
нет, поэтому рассинхрон невозможен by construction, а не «проверяется тестом на синхронность».

### Модель темы → файл

Тема, которую можно ПОСТАВИТЬ одним указанием, записывается коротко — `ThemeModel`: имя,
семена, мета, правки тёмной пары и плотность. Всё остальное из них считается
(`kb:PROBEWEB-15`, решение 2).

```ts
import { themeModelToCss } from "@omnifield/probe-web-style";

const css = themeModelToCss({
  id: "ocean",
  seeds: { brand: "oklch(0.55 0.16 248)", neutral: "…", danger: "…" },
  meta: { radius: "1.3rem" },
  darkOverrides: { "neutral-1": "oklch(0.205 0.008 248)" },
  density: "1",
});
```

Наружу едет файл: блок `[data-theme="ocean"]` со значениями светлой пары и плотностью плюс
блок под классом `dark` со значениями тёмной. Подключение — этот файл и атрибут на `<html>`,
**без единой строки JS**; `registerTheme` остаётся для тех, кто приносит палитру данными в
рантайме.

- **правки — только тёмной паре**: светлая остаётся расчётной, иначе обещания контраста
  ничего не значат; теме, которой мало светлой лестницы, менять надо семя;
- **плотность едет в тот же блок**, что и ступени: она такое же значение вида, как
  скругление, и отдельный блок означал бы, что тема переносится в два приёма;
- **названия, происхождения и идентификатора записи в модели нет** — это понятия стенда и
  хранилища, а не вида.

### Переключение

```ts
const theme = createThemeController({ themes: [ocean], initialMode: "dark" });
theme.toggleMode();       // класс `dark` на documentElement
theme.setTheme("ocean");  // атрибут `data-theme`
theme.setTheme(undefined); // назад к дефолтной паре
```

Контроллер **per-instance** — приложение создаёт его на бутстрапе. Синглтон в пакете
означал бы одно состояние темы на весь процесс, и второе приложение (или тест) молча
получало бы чужое.

**Персиста тут нет.** Ключ хранилища, поведение при SSR и вспышка неверной темы до
гидратации — решения приложения; пакет, выбравший их за него, занимает чужой ключ без
спроса. Дефолт при этом работает вообще без JS: `themes.css` красит `:root` и `.dark` сам.

## `cn` — почему не одним `clsx`

`clsx` собирает условные формы, `tailwind-merge` разрешает КОНФЛИКТЫ утилит:

```ts
cn("p-2", "p-4");                    // → "p-4"
cn("p-2", "px-4");                   // → "p-2 px-4"  (разные группы, обе живут)
cn("base", cond && "hidden");        // ложное выпадает
```

Без разрешения конфликтов переопределение стиля через проп `class` не работает: в атрибут
попадают оба класса, и выигрывает тот, что раньше в CSS, — то есть порядок правил вместо
порядка аргументов.

## `createStyle` — варианты, которые пересчитываются

```tsx
import { createStyle, cva } from "@omnifield/probe-web-style";

const button = cva("inline-flex p-2", {
  variants: { size: { sm: "text-sm", lg: "text-lg p-4" } },
  defaultVariants: { size: "sm" },
});

function Button(props: { size?: "sm" | "lg"; class?: string }) {
  const cls = createStyle(button, props);
  return <button class={cls()}>…</button>;
}
```

Пропсы читаются ВНУТРИ мемо, поэтому смена варианта пересчитывает класс, а не застывает на
значении момента вызова. Проп `class` потребителя идёт последним аргументом `cn` — при
конфликте утилит выигрывает он, а не вариант. Это единственный способ переопределить стиль
компонента снаружи, и потому он часть контракта, а не деталь реализации.

Префикс `create*` — конвенция Solid для реактивного примитива.

## Почему подпути названы с расширением

Типы для CSS приходят потребителю wildcard-правилом `declare module '*.css' {}` (`vite/client`,
его объявляет `tsconfig` зоны `build` полем `types`). Шаблон сопоставляется с **текстом
спецификатора**, а не с тем, куда он резолвится, — поэтому подпуть без расширения под правило
не попадает, и `tsc` роняет прогон потребителя (`TS2882`). Так было до 0.2.0: подпуть звался
`/css`; он переименован в `/base.css`, алиаса не осталось.

Держат это два гейта в паре: `test/types.test.ts` ставит тарбол в чистую установку и
типизирует оба импорта настоящим `tsc`; `test/pack.test.ts` проверяет, что подпуть правда
резолвится в файл поставки. Второе нужно потому, что шаблон `*.css` покрывает ЛЮБОЕ имя с
таким расширением — зелёный `tsc` сам по себе не доказывает, что файл в тарболе есть.

## Инвариант `base.css`

Ни одного литерального ЦВЕТА — ни в ручной части, ни в сгенерированных блоках: только сброс,
производные шкалы и ссылки на токены. Держится тестом, а не обещанием в шапке файла — цвет в
базовом слое не переключается вместе с темой и всплывает светлым пятном в тёмном режиме.

Размерные шкалы при этом несут значение по умолчанию прямо в `var(--семя, …)`, поэтому
геометрия работает и вовсе без темы. Дефолт подставляется генератором из того же описания
шкалы — второго места, где он записан, нет.

## Чего здесь нет

Осознанные пропуски порта, а не забытое:

- **tailwind-мост** (`@theme inline`, `@apply`, `@custom-variant`) — потребовал бы
  `tailwindcss` у каждого потребителя, а контракт зон его не объявляет. `cn` при этом
  работает и без Tailwind: конфликтные группы — знание внутри `tailwind-merge`.
- **цветовая библиотека** (`@radix-ui/colors` и родня) — взята МОДЕЛЬ, а не пакет. Обвес
  ставится в чужие репозитории, и любая наша зависимость становится зависимостью каждого
  потребителя; знание «сколько ступеней и что каждая значит» этим не оплачивается.
- **CSS-анимации компонентов kobalte** (popover/select/accordion) — презентация конкретных
  примитивов, это зона `ui`.
- **статус-механика** (`has-status`) и **`merge`** — первое апп-уровневое, второе плоский
  спред под именем, которое в Solid 2.0 занимает `mergeProps`.

## Разработка

```bash
pnpm install
pnpm run build      # tsc → dist, затем генерация dist/css
pnpm run typecheck
pnpm run test       # build + vitest (dom + node)
```

Машинного pre-commit в репозитории нет: сборку, типы и тесты гоняем руками перед каждым
коммитом.

**Мутационные проверки** — каждая воспроизводится за минуту, и каждая прогонялась. Не
покраснело — гейта нет, есть его имитация.

| что ломаем | что обязано покраснеть |
|---|---|
| `TEXT_STRONG_L.light` в `src/scale.ts`: `0.24` → `0.75` | `contrast.test.ts` — со шкалой, ступенью, фоном, отношением и критерием нормы |
| в `src/color/alpha.ts` убрать вторую границу прозрачности (`if (b < 1) …`) | `alpha.test.ts` — композиция перестаёт давать цель |
| в `src/layer.ts` увести `z-dialog` на `15` | `layer.test.ts` — порядок слоёв и место затемнения |
| в `src/model.ts` увести `--density` во второй блок | `model.test.ts` — плотность отстаёт от остальных значений |
| в `src/model.ts` поменять порядок спреда тёмной пары | `model.test.ts` — правки модели затираются расчётом |

Мутация, которая НЕ годится в пробу: округление прозрачности вверх (`ceilAlpha`) на
округление вниз. Разница уходит в тысячные и тонет в допуске — это выбор ради того, чтобы не
опираться на срез диапазона, а не то, что ловится гейтом. Мутация, которую гейт не ловит по
существу, в списке не нужна.
