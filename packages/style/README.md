# @omnifield/probe-web-style

**Набор значений** локации `probe-web`: токен-контракт, шкалы, роли и дефолтная пара тем.

**Это ОДИН ИЗ ПОСТАВЩИКОВ значений, а не фундамент** (`PWEB-3`). Оформление вправе взять
значения у нас, взять у кого-то ещё или обойтись своими — и остаться законным: скин,
написанный без единого нашего токена, обязан проходить все проверки. Пока «фундамент»
значило «без нас ничего не работает», право скина не брать наши значения держалось словом.

**Инструментов стилизации здесь нет.** `cn`, `createStyle` и реэкспорт `cva` — отдельная
необязательная поставка `@omnifield/probe-web-style-tools`; зависимости на неё у нас нет, как
и у неё на нас. Разрез идёт в обе стороны: односторонний держался бы обещанием.

Зависимостей на `ui`, `runtime` и `build` здесь нет и быть не может: направление
зависимостей одностороннее. Контракт зон целиком — `kb:PROBEWEB-4`; эта страница его не
заменяет, а пересказывает со стороны пакета. Цветовая модель и её основания — `kb:PROBEWEB-12`.

## Что наружу

| точка | что даёт |
|---|---|
| `@omnifield/probe-web-style` | токен-контракт, генератор шкал, **модель темы и её отрисовка в CSS**, имя маркера приезда базы, гейт контраста, механика тем (возит палитру **любого** поставщика — `PaletteValues`) |
| `@omnifield/probe-web-style/values` | **то же самое без реактивной части** — и без Solid (`PWEB-44`) |
| `@omnifield/probe-web-style/generate` | **порождение CSS по требованию**: `baseCss()`, `themesCss()` — чистые функции, из которых берутся оба файла ниже |
| `@omnifield/probe-web-style/base.css` | сброс, производные размерные шкалы, **роли**, устаревшие псевдонимы, `color-scheme`. **Ничего не одевает** — ни цвета, ни начертания на документ (`PWEB-39`) |
| `@omnifield/probe-web-style/themes.css` | **дефолтная палитра** `default`: значения ступеней и плотность под `[data-theme="default"]`, тёмная половина — под классом `dark` |

CSS через корневой вход НЕ идёт: манифест объявляет `sideEffects: false`, и импорт-побочка
из корня была бы выброшена tree-shaking'ом. Стили подключает приложение — двумя строками:

```ts
import "@omnifield/probe-web-style/themes.css"; // дефолтная палитра `default`
import "@omnifield/probe-web-style/base.css";  // сброс, шкалы, роли
```
```html
<html data-theme="default">        <!-- без имени палитры страница нецветная -->
```

**Оба файла обязательны — но только для того, кто взял ЭТОТ набор значений.** Роли живут в
`base.css`, значения — в `themes.css`; без первого нечему ссылаться, без второго нечего
показывать. Порядок не важен: `var()` разрешается на этапе вычисления значения, а не по месту
в файле. Обязательность внутренняя: приложение, которое берёт значения на стороне, не
подключает ни одного из этих файлов и остаётся законным.

### Два входа, и различает их ровно одно — нужен ли Solid (`PWEB-44`)

```ts
import { buildScale } from "@omnifield/probe-web-style/values"; // значения и цвет, без Solid
import { createThemeController } from "@omnifield/probe-web-style"; // + реактивный контроллер
```

Solid трогает **ровно один файл** — `src/theme.ts`. Шкалы, цвет, роли, разбор про него не знают.
Но вход был один, и Solid приезжал всем, включая тех, кому нужны только значения. Попалась на
этом механика скина: она отдаёт модель отдельным подпутём **без отрисовки** — хранилищу и
проверке сохранённого дерева реактивность не нужна, — а модель начала тянуть Solid транзитивно.

**Граница проведена по одному признаку: в узком входе всё, что не требует Solid.** Не отобранная
руками подборка «самого нужного»: её пришлось бы объяснять каждому, кому не хватило слоёв или
осей, и расширять по одному имени за выпуск. Правило «узкий вход = корневой минус реактивность»
объясняется одной фразой и проверяется машиной.

Отсюда раскладка: перечень имён живёт в `src/values.ts`, а `src/index.ts` берёт его целиком
одной строкой `export *` и добавляет реактивное. Второй перечень разъехался бы, и однажды имя
оказалось бы в корне, но не в узком входе — узкий обеднел бы **молча**.

**Второй копии кода нет.** Узкий подпуть — другой вход в тот же код: формула контраста объявлена
гейтом зоны, и два входа обязаны давать один ответ. **Что попало в узкий вход, то обещано:** он
такая же публичная поверхность и замерзает выпуском наравне с корневой.

#### `solid-js` объявлен НЕОБЯЗАТЕЛЬНЫМ одноранговым

Без этого обещание «узкий вход не тянет Solid» верно только для графа модулей: pnpm с 8-й версии
доставляет одноранговые сам (`auto-install-peers` включён по умолчанию, проверено на pnpm 11), и
Solid приехал бы на диск и тому, кто взял только `/values`. Поле не послабление, а точное
описание факта: Solid нужен ровно одному входу из четырёх.

Цена названа: потребитель **корневого** входа, забывший поставить Solid, узнает об этом при
запуске, а не при установке. Взвешено замером — все сегодняшние потребители корня
(`apps/reference`, `products/skin`, `products/tables`) объявляют `solid-js` у себя напрямую.

#### Чем это проверено

Запуском в установке, где Solid физически нет, а не чтением манифеста — манифест расходится с
фактом молча. `test/pack.test.ts` распаковывает настоящий тарбол и импортирует из него отдельным
процессом node:

| проба | ожидание |
|---|---|
| `import "…/values"` | поднимается |
| `import "…"` (корень) | падает с `Cannot find package 'solid-js'` |
| `import "…/generate"` | поднимается |

Вторая строка — **положительный контроль**, и без неё зелёный прогон значил бы и «Solid узкому
входу не нужен», и «проверка до Solid вообще не дошла».

Сверх того `test/entries.test.ts` держит само правило: корень — сумма узкого входа и
реактивного и ничего сверх; `solid-js` импортируется ровно одним файлом; из собранного
`dist/values.js` до чужого модуля не дойти обходом графа.

### Палитра принимает ИМЯ, а не селектор

Дефолт — **обычная палитра**, а не особый случай: `themes.css` объявляет её тем же
генератором и цепляет тем же способом, что и любой пресет (`kb:PROBEWEB-18`). Отсюда три
следствия, каждое проверяемо пробой:

- **`:root` палитрой не красится никогда** — ни дефолтной, ни какой-либо ещё;
- **нет выбранного имени → нет оформления.** Не потому, что мы это где-то проверяем, а
  потому что красить нечему: атрибут не стоит — ни одно правило палитры не подошло;
- **страница без палитры не ломается.** Геометрия работает: её дефолты подставлены прямо в
  `var(--семя, …)` базового слоя, и это инвариант 4 (`kb:SKIN-7`).

Zero-config этим снимается сознательно, и это цена, а не потеря: приложению, которому нужен
прежний вид, нужна **одна видимая строка** — `data-theme="default"` (`DEFAULT_PALETTE`), тем
же способом, что и любой другой пресет. Видимая строка лучше невидимого умолчания.

**Режим — не палитра.** `color-scheme` и класс `dark` живут в `base.css` на `:root` и от
имени палитры не зависят: режим ортогонален пресету (`kb:SKIN-7`, инвариант 3). Привязав
его к имени, мы вернули бы `twitter-dark` отдельной темой.

## Два уровня: ШКАЛА и РОЛЬ

Ровно то, ради чего переписан цвет (`kb:PROBEWEB-12`, пункты 1–2).

```
--brand-9            ступень: сырьё, у неё номер и закреплённое назначение   → themes.css
--brand-solid        роль: назначение в интерфейсе, ССЫЛКА на ступень        → base.css
--primary            устаревшее имя, ссылка на роль                          → base.css
```

Проверка смысла одним вопросом: **смена бренда обязана менять шкалу, не трогая роли.**
Поэтому роли не входят в тему — они одинаковы для всех палитр и обоих режимов, и копия в
каждой теме означала бы, что разделение объявлено, но не сделано.

**Цепляйся за РОЛЬ.** Ступень — это из чего роль сделана; она может быть перенастроена.

### Двенадцать ступеней и что каждая значит

| ступень | назначение | гарантия контраста |
|---|---|---|
| 1 | фон приложения | — (фон) |
| 2 | фон приложения, приглушённый | — (фон) |
| 3 | фон элемента | — (фон) |
| 4 | фон элемента при наведении | — (фон) |
| 5 | фон элемента при нажатии | — (фон) |
| 6 | тонкая граница, разделитель | — (оформление) |
| 7 | граница элемента | — (оформление) |
| 8 | сильная граница, кольцо фокуса | **≥3:1** к ступеням 1–2 (1.4.11) |
| 9 | сплошной акцент | — (верность бренду) |
| 10 | сплошной акцент при наведении | — (верность бренду) |
| 11 | текст низкого контраста | **≥4.5:1** к ступеням 1–3 (1.4.3) |
| 12 | текст высокого контраста | **≥4.5:1** к ступеням 1–5 (1.4.3) |
| `contrast` | подпись поверх сплошной ступени | **≥4.5:1** к ступеням 9–10 (1.4.3) |

Шкал три — `neutral`, `brand`, `danger`; плюс отдельный ряд `--chart-1…5` (категориальные
цвета данных, каждый ≥3:1 к фону приложения — на графике цвет носит информацию).

У каждой шкалы есть **параллельный альфа-ряд** `--<шкала>-a1…a12` и одно отдельное значение
`--scrim` — см. «Слои поверх страницы».

**Где гарантии НЕТ и почему** — перечень объявлен явно и живёт кодом (`NO_PROMISE`), потому
что молчание читается как «гарантия есть»:

- **1–5** — фоны: контраст даёт то, что НА них, а не они сами;
- **6–7** — тонкая граница и разделитель: оформление, а не носитель информации;
- **9–10** — сплошной акцент: сохраняем верность бренду. 1.4.11 требует контраста от того,
  что ИДЕНТИФИЦИРУЕТ контрол; у кнопки с видимой подписью это подпись, и её контраст
  обещает ступень `contrast`. Кнопка без подписи (одна иконка) — забота того, кто её рисует.

### Роли

Нейтральные: `--surface`, `--surface-subtle`, `--element`, `--element-hover`,
`--element-active`, `--separator`, `--border`, `--border-strong`, `--element-solid`,
`--element-solid-hover`, `--on-element-solid`, `--text-muted`, `--text`.

Бренд: `--brand-element`, `--brand-element-hover`, `--brand-element-active`,
`--brand-border`, `--focus-ring`, `--brand-solid`, `--brand-solid-hover`, `--on-brand-solid`,
`--brand-text`, `--brand-text-strong`.

Опасность: `--danger-element`, `--danger-element-hover`, `--danger-border`, `--danger-solid`,
`--danger-solid-hover`, `--on-danger-solid`, `--danger-text`.

Просвечивающие: `--overlay`, `--tint-hover`, `--tint-active`, `--brand-tint`, `--danger-tint`.

Имя роли никогда не кончается номером ступени — иначе потребитель цепляется за сырьё.

**Чего в ролях нет и не будет без разговора:** отдельного состояния «сплошной при нажатии».
Модель отдаёт сплошному акценту две ступени (9 и 10), а не три; третье состояние — это
изменение МОДЕЛИ, а не добавление имени. Нажатие показывается мягким вариантом
(`--brand-element-active`) или не цветом вовсе.

## Смена бренда — одно значение

```ts
import { createTheme, registerTheme } from "@omnifield/probe-web-style";

registerTheme(createTheme({ name: "ocean", brand: "#0f6fde" }));
```

Семя понимается как `oklch(L C H)` или `#rrggbb`. Незаданная шкала берётся из дефолтной
пары: сменить один только бренд стоит одного значения, а не переписывания всех трёх.

**Шкала считается ПРИ СБОРКЕ, в CSS уезжают готовые значения.** Сверка 2026-08-16:
`oklch()` и `color-mix()` поддержаны повсеместно, относительный синтаксис цвета — около 90%.
Девяноста процентов достаточно для украшения и недостаточно для того, на чём держится весь
вид: у оставшихся цвет не деградирует, а исчезает. Рантайм-генерация разрешена ровно в одном
месте — в ручке бренда на стенде `skin`, где отсутствие поддержки означает «ручка не
работает у части», а не «вид сломан у всех».

Тёмная половина — **своя шкала**, а не инверсия светлой: при инверсии фон элемента
становится текстом, то есть назначение ступеней перестаёт выполняться.

### Откуда берутся значения ступеней

- **1–7** — лестница светлоты режима;
- **8 и 11** — РЕШАЮТСЯ из порога нормы: это самая светлая граница, которая ещё даёт 3:1, и
  самый приглушённый текст, который ещё даёт 4.5:1. Основание значения — WCAG, а не вкус;
- **9–10** — от семени бренда: светлота, цветность и тон приходят от него. В тёмном режиме
  сплошная ступень сохраняет ОТНОШЕНИЕ к фону своего режима, а не абсолютную светлоту:
  чёрная кнопка на белом и чёрная кнопка на чёрном — это не одна тема в двух режимах;
- **12** — предельная читаемая краска режима;
- **`contrast`** — та сторона (светлая или тёмная), которая даёт больший запас над 4.5:1.

Наведение уводит сплошную ступень ОТ её собственной подписи, а не «в светлом темнее»: иначе
светлая кнопка с тёмной подписью на наведении роняет контраст подписи ниже нормы, и контрол
соответствует норме ровно до того, как на него навели.

Шкала может быть НЕмонотонной: ступени 9–10 идут от бренда, и у светлого бренда они
окажутся светлее текстовых. Это свойство модели, а не дефект — тот же эффект у любой
системы, которая обещает верность бренду.

### Гейт контраста

Обещание проверяется машиной, а не глазами: `test/contrast.test.ts` считает контраст на
**180 шкалах на режим** (12 тонов × 5 светлот × 3 цветности) — обещание, проверенное на трёх
наших цветах, это не обещание, а совпадение.

Та же формула доступна снаружи: тот, кто ставит свой бренд, обязан уметь проверить обещание
на своих значениях **тем же** способом, иначе «проверено» у него и у нас означает разное.

```ts
import { AA_TEXT, contrastRatio } from "@omnifield/probe-web-style";

contrastRatio("#1f6feb", "#ffffff") >= AA_TEXT;
```

Считается по WCAG 2.2 (Recommendation, 12 December 2024), критерии 1.4.3 (текст, 4.5:1) и
1.4.11 (нетекстовые элементы, 3:1). Цвет вне охвата sRGB отображается в охват НАМИ, а не
браузером: браузерная обрезка меняет светлоту, и посчитанное разошлось бы с показанным.

### Разбор цвета: какие записи понимает гейт (`PWEB-42`)

Формула бесполезна, если цвет до неё не доехал. Разбор понимал `oklch(L C H)` и
шестнадцатеричную запись, и скин, написанный чем угодно ещё, целиком уходил в «посчитать
нечем» — честно, но бесполезно: нечитаемый скин проезжал незамеченным.

| запись | пример | берётся |
|---|---|---|
| шестнадцатеричная, все четыре длины | `#f00` · `#f00c` · `#ff0000` · `#ff0000cc` | да |
| доли красного-зелёного-синего | `rgb(255, 0, 0)` · `rgb(255 0 0 / 1)` · `rgba(…)` | да |
| тон-насыщенность-светлота | `hsl(210, 40%, 25%)` · `hsl(210 40 25)` · `hsla(…)` | да |
| тон-белизна-чернота | `hwb(210 20% 30%)` | да |
| наша же модель в декартовых осях | `oklab(0.55 -0.02 -0.16)` | да |
| именованные цвета CSS, все 148 | `white` · `rebeccapurple` · `MidnightBlue` | да |
| CIE Lab и LCH | `lab(50% 40 59)` · `lch(…)` | **нет**, названо |
| другие охваты | `color(display-p3 1 0 0)` | **нет**, названо |
| вычисляемые записи | `color-mix()` · `light-dark()` · `rgb(from …)` | **нет**, названо |

**Состав выбран по тому, чем цвет пишут руками и чем его отдают чужие палитры**, а не по
полноте: `hsl` везёт tailwind до четвёртой версии и всё, что выросло из shadcn; `rgba()` уже
лежал в наших собственных эталонных скинах и отвергался; восьмизначную шестнадцатеричную выдаёт
любой редактор графики. Отказ от Lab/LCH и охватов — не пробел, а цена: это вторые цветовые
пространства со своей белой точкой и своей матрицей, точность которых пришлось бы доказывать
отдельно, а руками их почти не пишут. Вычисляемые записи — вовсе не значения: они зависят от
контекста, и разбирать их здесь значило бы завести второй каскад.

**Прозрачность по-прежнему отвергается**, и правило то же: контраст полупрозрачного зависит от
того, что под ним, — обещание перестаёт быть проверяемым. Изменилось не правило, а ИМЯ отказа:

```ts
import { tryParseColor } from "@omnifield/probe-web-style";

tryParseColor("hsl(210 40% 25%)"); // { ok: true,  color: {…} }
tryParseColor("rgba(0, 0, 0, .5)"); // { ok: false, refusal: "translucent" }
tryParseColor("color-mix(…)");      // { ok: false, refusal: "unknown-notation" }
```

Причин у отказа две, потому что чинятся они разным: «допиши, что под этим» — не то же самое,
что «здесь опечатка». Прежде полупрозрачное значение просто не разбиралось и было неотличимо от
мусора. Бросающая форма `parseColor` осталась и построена на этой же функции: она нужна там, где
отказ означает поломку сборки (семя шкалы), а не запись в перечне.

**Таблица имён взята из нормы и сверена вторым источником.** 148 имён сняты из CSS Color 4 §6.1
и прогнаны через живой Chromium — все совпали до байта (сверено 2026-08-21). Таблица по памяти
выглядит правдоподобно и врёт на десятке значений, а ошибка здесь становится ошибкой ответа про
читаемость. `transparent` в таблицу не входит намеренно: он прозрачен, и в таблице проехал бы
за чёрный.

**Точность: сверено с браузером, расхождений по существу нет.** `test/parse.test.ts` держит
таблицу, снятую с Chromium: каждая запись разбирается и сравнивается с тем, что показывает он.
Допуск — половина уровня 0…255, то есть предел, с которым браузер ПЕЧАТАЕТ цвет: значение
нередко попадает между уровнями (`hsl(210 40% 25%)` — ровно 38.25, `hwb(90 60% 60%)` — ровно
127.5), и округляет их браузер при печати, а не при вычислении. Худшее отличие по всей таблице —
0.500115 уровня, и хвост `1.15e-4` это шум обхода sRGB→OKLCH→sRGB; на целых значениях браузера
тот же обход не теряет ни одного уровня.

Округлять до восьми бит у себя мы **не стали**: наш собственный путь `oklch()` восемью битами не
квантуется, и введи мы квантование только для sRGB-записей — один и тот же цвет, написанный
двумя способами, дал бы два разных ответа. Ровно от этого гейт и защищает.

## Слои поверх страницы

Два разных вопроса, и путать их дорого: **чем красить** просвечивающий слой и **в каком
порядке** слои лежат.

### Альфа-ступени: чем красить

Сплошная ступень закрывает то, что под ней. Слою поверх страницы это подходит не всегда:
затемнение под диалогом обязано просвечивать, а подсветка при наведении ложится на
**произвольный** фон — полосатую таблицу, картинку, чужой блок, — а не на известный.

Поэтому у каждой шкалы есть параллельный ряд: **ступень `aN` поверх ступени 1 даёт ступень
`N`**. Обещание проверяется машиной (`test/alpha.test.ts`), а не глазами на стенде.

```css
[data-slot="row"]:hover { background-color: var(--tint-hover); }
[data-slot="dialog-overlay"] { background-color: var(--overlay); }
```

Три свойства, о которых надо знать заранее:

- **Совпадение гарантировано только поверх ступени 1.** На произвольном фоне вуаль его
  подкрашивает, а не заменяет, — ради этого альфа-ряд и заводится.
- **Альфа-ступень следует за режимом:** в светлом затемняет, в тёмном осветляет. Для
  подсветки при наведении это ровно то, что нужно.
- **Верхние ступени насыщенных шкал вырождаются в непрозрачные.** Цвет с почти нулевым
  каналом поверх почти белого фона недостижим ни при какой прозрачности — это свойство
  композиции, а не дефект. В такой точке ступень честно совпадает со сплошной.

**Затемнение под модальным слоем — это `--overlay`, а не альфа-ступень.** Оно чёрное в обоих
режимах: осветляющая вуаль в тёмной теме не убирает содержимое из фокуса, а подсвечивает его.
От шкалы берётся только сила перекрытия — прозрачность девятой альфа-ступени светлого режима.

**Гарантии контраста на альфа-ступенях нет и быть не может:** контраст полупрозрачного цвета
зависит от того, что под ним. Считает его тот, кто знает подложку.

### Шкала слоёв: в каком порядке

| токен | значение | что лежит |
|---|---|---|
| `--z-base` | 0 | обычный поток страницы |
| `--z-dropdown` | 10 | панель списка: выпадающий список, автодополнение |
| `--z-popover` | 20 | поповер, всплывающая подсказка |
| `--z-overlay` | 30 | затемнение под модальным слоем |
| `--z-dialog` | 40 | диалог, выезжающая панель |
| `--z-toast` | 50 | уведомление |

Пока слой один, `z-index: 1` работает. При четырёх слоях число из головы спорит с чужим
числом из головы, и спор выигрывает тот, кто написал больше. **Порядок слоёв — контракт:**
перестановка двух слоёв ломает чужой вид так же, как переназначение ступени, и едет мажором.

Шаг 10, а не 1: между нашими слоями обязано остаться место для чужого — кому нужен слой между
поповером и диалогом, вписывает 25 и не просит нас перенумеровать шкалу.

**Что шкала НЕ решает.** Мы объявляем порядок; контекст наложения создаёт тот, кто рисует
слой. `z-index` действует только среди соседей по контексту (CSS Position 3, §9), и никакой
токен не поднимет слой, вложенный в чужой `transform` или `filter`. Слои поверх страницы
монтируются порталом в корень — это забота зон `ui` и `skin`.

## Размерные шкалы

Приём тот же, что у скруглений: производная шкала от ОДНОГО семени. Семя задаёт тема,
ступени считает `base.css`.

| семя | ступени | плотность |
|---|---|---|
| `--radius` | `--radius-xs…3xl`, `--radius-full` | нет |
| `--space` | `--space-1/2/3/4/6/8/12/16/24/32` (сетка 0.25rem) | **да**, с посадкой на сетку |
| `--font-size` | `--font-size-xs…4xl` | **да**, без посадки на сетку |
| `--column` | `--column-24/32/40/48/56` (ширины поверхностей) | **да**, с посадкой на сетку |
| `--control-height` | `--control-height-sm/md/lg` | **да**, с посадкой на сетку |
| `--border-width` | `--border-width-1/2/4` | нет |
| `--tracking` | `--tracking-tight/normal/wide` | нет |

Без шкалы намеренно: `--leading-*` (высота строки — безразмерное отношение),
`--weight-*` (нормированный ряд, CSS Fonts 4 §2.3), `--control-target-min` (пол нормы),
`--motion-*` и `--ease-*` (подобранный ряд, а не размеры).

### Имя ступени интервалов равно её множителю

`--space-6` — это шесть шагов сетки, `--space-32` — тридцать два. Не порядковый номер: с
номером ступень **нельзя вставить**, между `--space-4` и `--space-5` места нет, и залатать один
разрыв вставкой значит получить тот же затык на следующем. С множителем в имени вставлять
ничто не мешает — недостающая кратность уже названа своим числом. Заодно имя перестало врать:
порядковый `--space-5` был множителем 6, `--space-6` — восьмёркой.

**Переименование ломающее и сделано разом (2026-08-18, `kb:PROBEWEB-16` часть Б).** Устаревших
псевдонимов, в отличие от цветовых ролей, здесь нет и быть не может: `--space-5` существует в
обеих схемах с РАЗНЫМИ значениями (24 порядковое, 20 множитель), а псевдоним не может значить
оба сразу — переход потребовал бы третьего имени на время.

| было | стало | значение при плотности 1 |
|---|---|---|
| `--space-1…4` | без изменений | 4·8·12·16px |
| `--space-5` | `--space-6` | 24px |
| `--space-6` | `--space-8` | 32px |
| `--space-7` | `--space-12` | 48px |
| `--space-8` | `--space-16` | 64px |
| `--space-9` | `--space-24` | 96px |
| `--space-10` | `--space-32` | 128px |

**Осторожно с `--space-6` и `--space-8`: имя выживает, значение меняется.** Прежний `--space-6`
был 32px, новый — 24px. Такое место у потребителя не краснеет ни сборкой, ни пробой — уезжает
вид, и это единственный молчаливый класс правки во всём переезде. Исчезнувшие имена (`5`, `7`,
`9`, `10`) ведут себя честнее: неразрешённый `var()` делает свойство недействительным, и это
видно.

### Плотность — ось, а не набор значений

`--density` умножает **интервалы, высоты контролов, кегль и ширины колонок**. Форму она не
трогает — скругления, толщины границ, трекинг: это очертание, а не размер.

```css
.table-dense { --density: 0.875; }
```

**Кегль в оси с 2026-08-18, и прежнее основание снято явно.** Раньше здесь стояло обратное:
«кегль не трогаем, иначе 1.4.4 Resize Text». Причина не выдержала проверки — 1.4.4 требует
ВОЗМОЖНОСТИ увеличить текст вдвое, а не запрещает множитель меньше единицы, и вся шкала
выражена в `rem`, поэтому настройка пользователя уважается при любой плотности. Половинчатая
же ось разваливала вещь: геометрия ехала, а всё, что меряется кеглем, стояло на месте.
Размер текста защищает не запрет оси, а её нижняя граница. Решение — `kb:PROBEWEB-16`, часть А.

### Сетка 0.25rem держится при любом множителе

Произвольная плотность даёт дробь, а от дроби едут соседние элементы, посчитанные от разных
ступеней. Поэтому значение плотной шкалы возвращается на сетку — и объявляется **дважды**,
подстраховкой на случай браузера без `round()` (см. ниже):

```css
:root {
  /* первым — без округления: это и есть подстраховка */
  --space-4: calc(var(--space, 0.25rem) * 4 * var(--density, 1));
}

@supports (width: round(nearest, 1rem, 0.25rem)) {
  :root {
    --space-4: round(nearest, calc(var(--space, 0.25rem) * 4 * var(--density, 1)), 0.25rem);
  }
}
```

Шаг сетки — **литерал `0.25rem`, а не семя интервалов**: сетка это общий ритм двух шкал с
разными семенами (`--space` и `--control-height`), и сделай шагом семя — шкалы сядут на разные
сетки. В `rem`, а не в `px`: при корневом кегле ≠ 16px «сетка 4px» перестаёт быть правдой.

**Кегль на сетку НЕ садится, и это единственное исключение.** Он задан отношениями к базовому,
а шаг сетки эти отношения разрушает: уже при плотности 1 — то есть у всех, кто плотность не
трогал вовсе, — `sm` (0.875rem) совпал бы с `md`, а `lg` (1.125rem) с `xl`. Шкала потеряла бы
две ступени, сборка у потребителя при этом не краснеет, а вид уезжает. Исключение держится
пробой «сетка схлопнула бы шкалу кегля», а не обещанием.

У интервалов сходиться ступеням можно и нормально: на нижней плотности `--space-2` и
`--space-3` дают одно значение — это цена сетки для ритма. Чего не бывает — старшая ступень
мельче младшей; это отдельная проба.

### Ширины поверхностей — колонка, а не кратность интервалу

Ширина модального окна, потолок панели, потолок подсказки, минимум меню, ширина уведомления —
раньше база их не нормировала вовсе, и они жили абсолютными литералами у потребителя.

**Семя `--column` — средняя ширина ОДНОГО знака при базовом кегле, а имя ступени равно числу
знаков:** `--column-40` это колонка на сорок знаков. Тот же приём, что у интервалов, где семя —
один шаг сетки.

```css
[data-slot="dialog"] { inline-size: min(var(--column-56), 100vw - var(--space-8)); }
[data-slot="tooltip"] { max-inline-size: var(--column-32); }
```

| ступень | знаков | при плотности 1 |
|---|---|---|
| `--column-24` | 24 | 12rem |
| `--column-32` | 32 | 16rem |
| `--column-40` | 40 | 20rem |
| `--column-48` | 48 | 24rem |
| `--column-56` | 56 | 28rem |

**Почему не кратность интервалу.** Ширину окна можно получить и как `calc(var(--space-32) *
3.5)` — число выйдет то же, а связь будет придуманной. Ширина окна происходит не от ритма
отступов, а от того, сколько знаков в строке человек прочитывает, не теряя её начала.
Основание, взятое у соседней шкалы ради красоты вывода, — фикция, только записанная.

**Почему не `ch`, хотя единица знака в CSS есть.** `ch` разрешается по шрифту ТОГО элемента,
где токен применён: один и тот же `--column-40` дал бы разную ширину в основном тексте и в
моноширинном блоке. Для контракта ширины это дефект, а не гибкость. Семя в `rem` —
приближение (≈0.5rem у типичного гротеска при кегле 16px) и **переопределяемо темой**:
гарнитура с другой средней шириной знака ставит своё, и все ступени едут за ним.

**Плотность — да, сетка — да.** Кегль едет плотностью; не поехала бы за ним колонка — на
плотном виде в ту же ширину влезало бы больше знаков, чем названо в имени ступени, и число в
имени перестало бы быть правдой. На сетку садится, потому что ступени кратны её шагу и стоят
в шестнадцать шагов друг от друга: посадка сдвигает край максимум на четверть знака и
схлопнуть ничего не может — в отличие от кегля, где шаг сетки крупнее расстояния между
ступенями.

**Верх ряда — 56 знаков при потолке нормы в 80** (WCAG 2.2, 1.4.8 Visual Presentation, AAA:
«Width is no more than 80 characters or glyphs»; сверено 2026-08-18). Норма даёт потолок, а не
ряд: сам ряд из неё не выводится, но выходить за него не должен — это проверяет проба.

### Границы оси: пол из нормы, потолок — предел поддержки

**Нижняя граница — 0.75**, и она ВЫВЕДЕНА, а не назначена и не взята с рынка. Норма — WCAG 2.2,
2.5.8 Target Size (Minimum), AA: цель не меньше 24×24 CSS-пикселя, то есть 1.5rem. Связывает
она нижнюю ступень контрола: `2.5rem × 0.8 × d = 2rem × d ≥ 1.5rem` → `d ≥ 0.75`.

Вывод сделан **после округления**, потому что в поставку уезжает округлённое значение.
`round(nearest, …)` может увести значение вниз на половину шага — до `0.125rem`. Норму это не
пробивает: округление монотонно, а порог 1.5rem сам лежит на сетке (1.5 = 6 × 0.25), значит всё,
что не ниже порога, остаётся не ниже и после округления. Потеря съедает **запас**: при `d = 0.8`
ступень 1.6rem садится ровно на 1.5rem — на минимум, а не под него.

Почему не 0.6875, хотя формально норму удержало бы и оно: 1.375rem — ровно середина шага, а её
`round(nearest, …)` уводит вверх, до 1.5rem. Тогда норму держала бы сторона округления, а не
геометрия — объявленная высота 22px, поставленная 24px. Пол обязан держаться по обе стороны
округления.

Вторая связывающая норма — читаемость кегля — **числа не даёт, и придумывать его нельзя**:
минимального кегля у WCAG 2.2 нет вовсе (сверено 2026-08-18), а 1.4.4 при `rem`-шкале
выполняется при любой плотности. Строгая из двух — 2.5.8, пол остаётся 0.75.

**Верхняя граница — 1.5, и это предел ПОДДЕРЖКИ, а не требование доступности.** По норме крупнее
не хуже: ни 2.5.8, ни 1.4.4 множителем больше единицы не нарушаются. 1.5 — верх диапазона, на
котором прогоняются пробы, и верх того, что зона обещает; выше значения остаются действительным
CSS, но проверок и обещаний по ним нет.

Обе границы **объявлены, а не зажаты `clamp()`**. Зажать пол значило бы молча подменить число,
которое поставил потребитель; зажать потолок — отнять то, что нормой разрешено.

### Подстраховка `round()`: браузер без неё теряет геометрию, а не портит

**`round()` — Baseline newly available с мая 2024** (все три движка; сверено 2026-08-18 по MDN).
До «widely available» ещё не дошло, и деградация здесь жёсткая: недействительное значение делает
свойство невычислимым, и элемент едет на унаследованном или начальном. Геометрия не ухудшается —
она **исчезает**, а исчезнувшее оформление человек читает как «сломалось».

Поэтому **значение плотной шкалы объявлено дважды, и порядок объявлений — часть решения**
(`kb:PROBEWEB-16`, «Открытый вопрос»; `tasker:PROBEWEB-63`):

1. **первым — без округления.** Его берёт браузер, который `round()` не поддерживает, и
   получает дробное, но **живое** значение: произведение семени, множителя и плотности. Ряд при
   этом цел — отношения ступеней сохраняются точно, теряется только посадка на сетку;
2. **вторым, под `@supports`, — то же значение на сетке.** `@supports` специфичности не
   добавляет: побеждает объявление, стоящее **позже**. Переставь блоки местами — подстраховка
   начнёт перебивать сетку у всех, и сетки не станет ни у кого. Это держит проба.

**Что человек видит в браузере без `round()`.** При плотности 1 — ничего: семена и множители
подобраны так, что значение уже лежит на сетке, и оба объявления дают одно и то же число
(отдельная проба). Расхождение появляется только у того, кто **крутил плотность**: `--density:
0.9` даёт интервалы вроде `3.6px` вместо `4px` — ритм чуть «плывёт», соседние элементы,
посчитанные от разных ступеней, перестают попадать друг в друга. Вещь при этом целая и
пользуемая; **без подстраховки** та же ручка обнуляла бы отступы, ширины и высоты контролов до
унаследованных или начальных — то есть разваливала бы вид.

**Пол оси плотности подстраховка не меняет.** `DENSITY_FLOOR = 0.75` выведен ПОСЛЕ округления и
потому строже: без округления запас не съедается, и нижняя ступень контрола остаётся не ниже
минимума нормы при любом множителе из диапазона. Это тоже проба, а не рассуждение.

**Форма проверки — обычное свойство с типом длины, а не кастомное.** `@supports (--x: round(…))`
истинно в любом браузере с поддержкой переменных: кастомное свойство принимает почти любой поток
токенов, и такая проба не значит ничего. `var()` в условии тоже запрещён — объявление с `var()`
считается действительным на разборе. Отсюда `(width: round(nearest, 1rem, 0.25rem))`: та самая
функция, та самая стратегия, тот самый шаг сетки — и никакой соседней возможности.

Перечень подстрахованных шкал **не список, а поле `snap`**: два объявления получает ровно то, что
садится на сетку (`--space`, `--column`, `--control-height`). Кегль в блок `@supports` не попадает
вовсе — он на сетку не садится, подстраховывать нечего.

### Границы ВСЕХ осей — таблицей `AXES`, и «границы нет» тоже ответ

Тому, кто строит панель настройки вида, край значения нужен по каждой оси, а не только по
плотности. Раньше про остальные молчали — и молчание читается как «база не знает, где край»:
панель стенда получила шесть зашитых скруглений вместо ползунка ровно поэтому.

Теперь границы объявлены **значением, а не умолчанием** — `AXES` из `src/axes.ts`, и тот же
перечень уезжает комментарием в `base.css` (тему пишут в CSS, туда за границами и пойдут):

```ts
import { AXES, axisOf } from "@omnifield/probe-web-style";

const density = axisOf("density")!;
density.floor;   // { value: 0.75, kind: "норма", norm: "WCAG 2.2, 2.5.8 …", why: "…" }
axisOf("radius")!.floor;   // { value: null, kind: "границы нет", norm: null, why: "…" }
```

| ось | пол | потолок |
|---|---|---|
| `--density` | `0.75` — **норма** (2.5.8) | `1.5` — предел поддержки |
| `--control-height` | `1.875rem` — **норма** (2.5.8) | границы нет |
| `--radius` | границы нет | практический предел, числом не выражается |
| `--font-size` · `--space` · `--column` · `--border-width` · `--tracking` | границы нет | границы нет |

Читается это так:

- **`kind: "норма"`** — единственный случай, когда нарушение означает несоответствие. Только у
  таких границ заполнено поле `norm` со ссылкой на критерий; это структурное поле, а не текст,
  именно затем, чтобы предел поддержки, объяснённый через норму в свободной фразе, не начали
  соблюдать как требование.
- **`практический предел`** у скругления: радиус больше половины меньшей стороны даёт пилюлю.
  Свойство геометрии, **не требование доступности**, и числом база его назвать не может —
  половина зависит от элемента, а не от токена.
- **`границы нет`** — связывающей нормы не существует, любое значение законно. У кегля это
  проверенный факт: минимального кегля у WCAG 2.2 нет вовсе (сверено 2026-08-18), а 1.4.4
  требует возможности увеличить текст вдвое, а не запрещает мелкий.
- **`continuous: true`** у всех: «правильных» ступеней у базы нет ни у одной оси. Свои три
  ступени плотности потребитель предложить вправе — выдавать их за базовые не может.

**Пол высоты контрола подвижен, и это единственная пара осей, которая перемножается.**
`1.875rem` — порог при плотности 1; на нижней границе плотности порог равен `2.5rem`, то есть
ровно нынешнему семени. Крутить семя и плотность вниз одновременно нельзя: границы не
складываются. Значение выводится из данных шкалы, а не переписано числом.

Полнота таблицы держится пробой: **новая шкала без объявленных границ роняет прогон** — иначе
следующая заведённая шкала молча вернёт то самое молчание, ради выхода из которого таблица и
появилась.

## Прежний плоский набор — устарел

`--background`, `--foreground`, `--card*`, `--popover*`, `--primary*`, `--secondary*`,
`--muted*`, `--accent*`, `--destructive*`, `--input`, `--ring`, `--sidebar-*` — **живы и
выражены через роли**, но объявлены устаревшими. Удаление — мажорным поднятием версии.

Два имени на одно и то же — это две правды; новый код берёт роли. Что изменилось по смыслу:

- `--accent` был вторым именем приглушённого фона, которым за неимением ступени затыкали
  наведение; теперь это ровно ступень наведения (`--element-hover`);
- `--input` был серым, которым `skin` красил фон поля; теперь это явный `--element`;
- `--destructive-foreground` был чистым белым на красном — **4.37:1, ниже порога 1.4.3**.
  Теперь подпись выбирается по контрасту, и гейт краснеет, если порог не взят;
- `--tracking-normal` из СЕМЕНИ стал ступенью, семя зовётся `--tracking`. Прежнее имя было
  и семенем, и ступенью сразу, а токен, объявленный через самого себя, — цикл, и браузер
  такое свойство отменяет. Тема, задававшая `--tracking-normal`, задаёт `--tracking`.

`--border` и `--chart-1…5` устаревшими НЕ объявлены: первое стало ролью под тем же именем и
с тем же смыслом, второе — самостоятельный ряд.

## Политика выпусков: вид ломается токенами

**Изменение состава или назначения токенов — ЛОМАЮЩЕЕ изменение** (`kb:PROBEWEB-12`, п. 6).

- добавление токена или изменение состава — **минор** с явной записью в примечаниях;
- удаление токена или переназначение ступени/роли — **мажор**.

Причина: потребитель цепляется за токены так же, как `skin` цепляется за `data-slot`.
Переназначенная ступень ломает чужой вид ровно так же, как переименованный слот. Пока пакет
в `0.x`, ломающее едет минором — это правило semver, а не послабление нашей политики.

## Токены: тема — это ДАННЫЕ

Контракт оформлен типом, а не «что нашлось в CSS»:

- `SCALE_TOKENS` — 81 цветовой токен (3 шкалы × 25 + 5 рядов графика + `--scrim`),
  **обязательное ядро**; 25 на шкалу = 12 сплошных ступеней + 12 альфа + подпись на сплошной;
- `THEME_META_TOKENS` — шрифты, тени и СЕМЕНА размерных шкал; опциональны;
- `ROLE_TOKENS` / `LEGACY_TOKENS` / `LAYER_TOKENS` — роли, устаревшие имена и шкала слоёв;
  **в тему не входят** (порядок слоёв от палитры не зависит);
- `ThemeTokens` / `ThemeDefinition` — тема как объект; в CSS её отрисовывает `themeModelToCss`
  (по ИМЕНИ палитры). Свободного селектора на поверхности нет намеренно: пока он есть,
  правило «палитра принимает имя» держится обещанием, а не машиной (`kb:PROBEWEB-18`);
- `DEFAULT_PALETTE` — имя дефолтной палитры (`default`), то самое, что уезжает в
  `data-theme`; `DEFAULT_THEME_MODEL` — она же как модель, из неё собирается `themes.css`;
- `BASE_MARKER` — имя токена, которым проверяют ПРИЕЗД БАЗЫ (см. ниже);
- `PALETTE_TOKENS` / `PaletteToken` — прежние имена `SCALE_TOKENS` / `ScaleToken`, оставлены
  устаревшими.

`dist/css/themes.css` и `dist/css/base.css` **порождаются**: палитра — тем же
`themeModelToCss()`, каким рождается любой пресет (своей ветки у дефолта нет), перечни ступеней
и ролей — из массивов в TS. Второй копии правды в репозитории нет, поэтому рассинхрон
невозможен by construction, а не «проверяется тестом на синхронность». Когда именно они
порождаются — ниже.

### CSS порождается по требованию, а не прошлой сборкой

Файл, который собирается из данных, обязан отражать **текущие** исходники. Пока породить его
умела одна сборка, в разработке приложение показывало результат ПРОШЛОЙ сборки: правишь
токен — на экране вчерашнее, и `git status` при этом чист. Ошибка выглядит как ошибка вида,
поэтому её списывают на что угодно, кроме устаревшей сборки (`PWEB-20`).

Порождение — обычный модуль зоны (`src/css/generate.ts`) и публичный подпуть:

```ts
import { baseCss, themesCss } from "@omnifield/probe-web-style/generate";
```

Зовут его три места и одинаково: сборочный сценарий (пишет `dist/css/*.css` для поставки),
**дев-сервер — в момент запроса**, и пробы (сверяют порождённое с поставкой). Функции чистые:
ни файловой системы, ни путей, ни аргументов, — иначе порождение зависело бы от того, откуда
его позвали, а зовущему пришлось бы знать нашу раскладку.

Отсюда две вещи, которые легко принять за странность:

- **ручная часть базового слоя — модуль, а не файл `.css`** (`src/css/written.ts`). Файл рядом
  заставил бы каждого зовущего знать путь к нему и уметь его прочитать. Цена названа честно:
  редактор подсвечивает этот CSS как строку;
- **`prepare` здесь не годится.** Он строит пакет один раз, на установке, — то есть возвращает
  ту же болезнь через заднюю дверь. Он законен для оснастки (она обязана существовать раньше
  всех и меняется редко); набор значений — не оснастка.

Сверено с рынком 2026-08-19: порождение по запросу через плагин дев-сервера и виртуальный
модуль — устоявшийся приём (UnoCSS `virtual:uno.css`, `@tailwindcss/vite`). Оттуда взята
раскладка: генерация — чистая функция пакета, зацеп — плагин, который зовёт её на запрос.
**Сам зацеп живёт в зоне `build`**: дев-сервер её предмет, а не наш.

### Маркер приезда базы

`checkStyleOrder()` из `runtime` спрашивает: подключён ли базовый CSS? Спросить это можно
только про конкретный токен на корне, а знание «какой токен приезжает с базой» принадлежит
нам — поэтому имя механика **принимает снаружи** и не знает (`kb:PROBEWEB-13`).

```ts
import { BASE_MARKER } from "@omnifield/probe-web-style";
checkStyleOrder({ marker: BASE_MARKER, preset });   // имя приходит от `style`
```

Литерал вместо этого импорта — тихая связь: переименуем токен здесь, и проверка там начнёт
врать. Цена ошибки несимметрична — имя уезжает в скелет, а скелет кладётся потребителю
`placed-once` и **не обновляется никогда**.

Маркер сегодня — `--control-target-min`, и держат его не имя, а три свойства (проба
`test/marker.test.ts` про них и не знает, какой это токен):

1. **объявлен базовым слоем**, безусловно — не под `@supports`, иначе «базы нет» услышит тот,
   у кого движок постарше;
2. **никогда не объявлен палитрой.** Иначе проверка перестанет отличать «базы нет» от
   «палитра не выбрана» — а это ровно те два состояния, которые механика различает
   (`missing-base` против `no-skin`), и документ без палитры законен (`kb:PROBEWEB-18`);
3. **значение не зависит от палитры** — литерал, без единого `var()`.

Почему именно он: `--control-target-min` — пол нормы (WCAG 2.2, 2.5.8), а не наша ступень.
Палитра, объявившая его, — дефект по определению, поэтому «никогда в палитре» держится
контрактом токенов, а не тем, что сегодня в файле его нет.

**Область действия маркера — ТОЛЬКО наш набор** (`PWEB-3`). Он отвечает на вопрос «приехала
ли наша база», то есть на вопрос о ПРОИСХОЖДЕНИИ значений, и осмыслен для того, кто взял этот
набор. Оформление на чужих значениях маркера не объявляет и объявлять не обязано — «маркера
нет» про него не значит ничего. Вопрос по существу — другой, и проверяется он иначе, см. ниже.

### Проверка по существу, а не по происхождению

Вопрос «взял ли ты наш токен» и вопрос «работает ли вид» — разные, и второй не следует из
первого. Оформление, собранное из чужих значений, первую проверку не проходит, а вторую
проходит; пока проходит только первая, набор значений — фундамент, а не поставщик.

По существу проверяется одно: **значение следует за режимом и за выбранной палитрой.**

```ts
const theme = createThemeController({
  themes: [{ name: "foreign", light: { ink: "#111" }, dark: { ink: "#eee" } }],
  initialTheme: "foreign",
});
// --ink меняется на toggleMode() и на setTheme("другая"), и исчезает на setTheme(undefined)
```

`ThemeDefinition` принимает `PaletteValues` — **любой** состав кастом-свойств, а не наше ядро
(`ThemeTokens`). Отрисовка чужую палитру печатала и раньше; не пропускал её ТИП, и на этом
«мы один из поставщиков» кончалось. Строгость никуда не делась — она осталась там, где ей
место: наш собственный набор по-прежнему `ThemeTokens`, полное ядро обязательно.

Держит это `test/foreign-values.test.ts`: чужая палитра, ни одного нашего токена на документе,
`base.css` в прогоне не подключён — и вид следует за режимом и за выбором. Отдельной пробой
проверено, что имена в ней действительно чужие: совпади хоть одно с нашим, гейт остался бы
зелёным, перестав быть гейтом.

### Модель темы → файл

Тема, которую можно ПОСТАВИТЬ одним указанием, записывается коротко — `ThemeModel`: имя,
семена, мета, правки тёмной пары и плотность. Всё остальное из них считается
(`kb:PROBEWEB-15`, решение 2).

```ts
import { themeModelToCss } from "@omnifield/probe-web-style";

const css = themeModelToCss({
  id: "ocean",
  seeds: { brand: "oklch(0.55 0.16 248)", neutral: "…", danger: "…" },
  meta: { radius: "1.3rem" },
  darkOverrides: { "neutral-1": "oklch(0.205 0.008 248)" },
  density: "1",
});
```

Наружу едет файл: блок `[data-theme="ocean"]` со значениями светлой пары и плотностью плюс
блок под классом `dark` со значениями тёмной. Подключение — этот файл и атрибут на `<html>`,
**без единой строки JS**; `registerTheme` остаётся для тех, кто приносит палитру данными в
рантайме.

Селектор из имени выводит ОДНА функция на зону (`src/palette.ts`), и её зовут оба места —
генератор файла и рантайм-инжект. Собранных руками строк `[data-theme="…"]` в зоне не
остаётся ни одной: это держит проба, а не соглашение. Дефолтная палитра проезжает тем же
вызовом — `themeModelToCss(DEFAULT_THEME_MODEL)`.

- **правки — только тёмной паре**: светлая остаётся расчётной, иначе обещания контраста
  ничего не значат; теме, которой мало светлой лестницы, менять надо семя;
- **плотность едет в тот же блок**, что и ступени: она такое же значение вида, как
  скругление, и отдельный блок означал бы, что тема переносится в два приёма;
- **названия, происхождения и идентификатора записи в модели нет** — это понятия стенда и
  хранилища, а не вида.

### Переключение

```ts
const theme = createThemeController({ themes: [ocean], initialMode: "dark" });
theme.toggleMode();       // класс `dark` на documentElement
theme.setTheme("ocean");  // атрибут `data-theme`
theme.setTheme(undefined); // палитра СНЯТА: страница нецветная, геометрия работает
```

`undefined` — это «палитры нет», а не «дефолтная». Прежний вид возвращает названное имя:
`theme.setTheme(DEFAULT_PALETTE)`. Контроллер имя не подставляет сам — подставив, он вернул
бы покрашенный по умолчанию документ, только уже из JS.

Контроллер **per-instance** — приложение создаёт его на бутстрапе. Синглтон в пакете
означал бы одно состояние темы на весь процесс, и второе приложение (или тест) молча
получало бы чужое.

**Персиста тут нет.** Ключ хранилища, поведение при SSR и вспышка неверной темы до
гидратации — решения приложения; пакет, выбравший их за него, занимает чужой ключ без
спроса. Палитра при этом работает вообще без JS: файл плюс атрибут — и вид на месте.

## Инструменты стилизации — другая поставка

`cn`, `createStyle` и реэкспорт `cva` живут в `@omnifield/probe-web-style-tools` и здесь их
нет (`PWEB-3`). Импорт по привычке даёт `TS2305` — «модуль не экспортирует такого имени», и
это намеренно: подсказка ведёт в другую поставку, а не молча привозит инструменты вместе со
значениями. Держит это гейт (`test/types.test.ts`), а не память.

Разрез считается сделанным не тогда, когда `cn` исчез с поверхности, а когда его зависимости
(`clsx`, `tailwind-merge`, `class-variance-authority`) перестали приезжать вместе со
значениями: пока их привозила одна установка, «инструменты необязательны» было словом. Это
отдельный гейт — `test/pack.test.ts`.

## Почему подпути названы с расширением

Типы для CSS приходят потребителю wildcard-правилом `declare module '*.css' {}` (`vite/client`,
его объявляет `tsconfig` зоны `build` полем `types`). Шаблон сопоставляется с **текстом
спецификатора**, а не с тем, куда он резолвится, — поэтому подпуть без расширения под правило
не попадает, и `tsc` роняет прогон потребителя (`TS2882`). Так было до 0.2.0: подпуть звался
`/css`; он переименован в `/base.css`, алиаса не осталось.

Держат это два гейта в паре: `test/types.test.ts` ставит тарбол в чистую установку и
типизирует оба импорта настоящим `tsc`; `test/pack.test.ts` проверяет, что подпуть правда
резолвится в файл поставки. Второе нужно потому, что шаблон `*.css` покрывает ЛЮБОЕ имя с
таким расширением — зелёный `tsc` сам по себе не доказывает, что файл в тарболе есть.

## Инвариант `base.css`: базовый слой НЕ ОДЕВАЕТ

Инвариант с 2026-08-21 сильнее прежнего. Раньше он звучал «ни одного литерального цвета»;
теперь — **ни одного объявления вида на документ**, литерального или нет. Реестр в
`test/base-css.test.ts` ведётся С ДВУХ СТОРОН: разрешено ровно три свойства —
`box-sizing`, `margin`, `color-scheme`, — и любое четвёртое краснеет само.

### Почему прежней формулировки не хватило (`PWEB-39`)

Из `body` ушли шесть объявлений: фон, цвет текста, начертание, кегль, высота строки, трекинг.
Ни одно из них не было литеральным цветом — они ссылались на роли, — и прежний инвариант их
пропускал.

**Пять из шести НАСЛЕДУЮТСЯ, и в этом всё дело.** База не просто красила документ — она через
наследование одевала кит. Кнопка, которую не одевал никто, получала от нас цвет текста, шрифт,
кегль, высоту строки и трекинг, ничего не спросив. «Нет скина — приложение голое»
(`kb:PROBEWEB-11`) держалось на бумаге.

Замеряется это не рассуждением: голая страница на новом `base.css` показывает начертание
`Times New Roman` и кегль `16px` — умолчания браузера. На прежнем она показывала
`ui-sans-serif, system-ui, …` и нашу ступень, то есть нашу одежду.

Шестое, фон, не наследуется — оно делало другое: объявляло страницу нашей. **Прямое следствие
снятия: страницу теперь не красит никто ни в одной конфигурации, включая тему.** Тема
объявляет только ступени; красил их на `body` этот самый ушедший `background-color`. Кто красит
страницу — отдельный вопрос с отдельным владельцем, и он больше ничем не замаскирован.

### Что осталось адресовано документу и почему это не одежда

- **сброс** (`box-sizing: border-box`, `body { margin: 0 }`) — снятие решений БРАУЗЕРА, а не
  внесение своих: ничего не наследуется, ни одно наше значение не приезжает;
- **`color-scheme`** — разобран ниже отдельно;
- **токены** (движение, шкалы, роли, псевдонимы) — это ЗНАЧЕНИЯ, а не применения. Объявленный
  токен не надет ни на что, пока его не позвали.

### Почему `color-scheme` остался

Строка спорная, и обе стороны верны по факту: снимешь — голый кит перестанет выглядеть
по-разному в двух режимах; оставишь — базовый слой продолжает что-то говорить браузеру о виде.
Остался, и вот на чём.

1. **Это не решение о виде, а перевод уже принятого.** Режим выбирает приложение и несёт
   классом `dark` на корне (зона `runtime`); `color-scheme` говорит браузеру то же самое.
   Промолчи мы — браузер решит сам и решит независимо: у одного ответа станет два источника.
   Расхождение двух источников — ровно тот дефект, из-за которого ушли шесть строк.
2. **Сказать это больше некому.** Скин? Тогда у приложения без скина режима нет вовсе, а у
   двух скинов их два, при том что режим ортогонален скину (`kb:SKIN-7`, инвариант 3).
   Потребитель? Тогда связь «класс ↔ режим браузера» держится соглашением в каждом скелете.
   База — единственный, кто присутствует во всех конфигурациях.
3. **«Голый кит выглядит по-разному в двух режимах» — верно по факту, неверно по выводу.**
   Голый кит это не наш вид, а отсутствие нашего вида; что осталось — вид браузера, а у него
   их два, потому что у человека два режима. Сделать одинаковым можно только пришпилив один:
   `color-scheme: light` для всех — не нейтральность, а необъявленный выбор светлого.
4. **Последствие названо, а не спрятано:** от `color-scheme` зависит канва браузера и его
   начальный цвет текста, поэтому голая страница в тёмном режиме выглядит тёмной. Красит её
   БРАУЗЕР своим умолчанием — мы лишь сказали, каким из двух; появится источник, он перекроет
   умолчание обычным объявлением. Снятая строка отняла бы и это: системные элементы (полосы
   прокрутки, галочки, автозаполнение) остались бы светлыми на тёмной странице.

### Геометрия работает без всего

Размерные шкалы несут значение по умолчанию прямо в `var(--семя, …)`, поэтому геометрия
считается и вовсе без палитры. Дефолт подставляется генератором из того же описания шкалы —
второго места, где он записан, нет.

## Чего здесь нет

Осознанные пропуски порта, а не забытое:

- **tailwind-мост** (`@theme inline`, `@apply`, `@custom-variant`) — потребовал бы
  `tailwindcss` у каждого потребителя, а контракт зон его не объявляет.
- **инструменты стилизации** (`cn`, `createStyle`, `cva`) — уехали отдельной необязательной
  поставкой `@omnifield/probe-web-style-tools` (`PWEB-3`), см. раздел выше.
- **цветовая библиотека** (`@radix-ui/colors` и родня) — взята МОДЕЛЬ, а не пакет. Обвес
  ставится в чужие репозитории, и любая наша зависимость становится зависимостью каждого
  потребителя; знание «сколько ступеней и что каждая значит» этим не оплачивается.
- **CSS-анимации компонентов kobalte** (popover/select/accordion) — презентация конкретных
  примитивов, это зона `ui`.
- **статус-механика** (`has-status`) и **`merge`** — первое апп-уровневое, второе плоский
  спред под именем, которое в Solid 2.0 занимает `mergeProps`.
