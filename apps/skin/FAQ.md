🔍 Короткие ответы на конкретные вопросы, которые уже возникали по этому приложению. Не общая
документация (она в [`README.md`](./README.md)) и не план (он в [`ROADMAP.yaml`](./ROADMAP.yaml))

## Структура каталогов

### Почему у каждой папки — файл `index`, даже когда внутри всего один файл?

**Коротко: `index` — не формальность, а публичная граница модуля; без него ничто не мешает
соседнему коду залезть во внутренний файл напрямую, в обход любого правила.**

До правки часть виджетов лежала как `widgets/component-tree/component-tree.tsx` —
дублирующее имя папки и файла, и снаружи ничего не подсказывало, что `component-tree.tsx` —
единственно правильная точка входа, а не один из нескольких файлов, в которые можно смотреть.
Переименовано в `component-tree/index.tsx` везде, где встретился этот паттерн (`header`, `tree`,
`preview`, `input`, `renderer`, `slot`, `app`). Агрегирующие папки без единственного файла
(`model`, `ui`, верх слайса `entities/component`, `entities/showcase`, `widgets/component`)
получили свой `index.ts` — тонкий barrel (`export * from "./..."`), реэкспортирующий только то,
что реально используется снаружи, а не всё подряд.

---

### Почему `index` держит только реэкспорт, а не саму логику?

**Коротко: `index` — паблик API каталога; грузить его реализацией значит смешивать интерфейс с
внутренностями в одном файле.**

`entities/component/utils/fake-generator/index.ts` изначально нёс сразу всё: таблицу слов,
`randomWord`/`randomInt`/`targetLength`/`fakeText` и саму `generateFakeData`. Разнесено на
`index.ts` (один `export { generateFakeData } from "./generate"`), `generate.ts` (сама функция),
`text.ts` (приватные хелперы генерации текста) и `hints.ts` (таблица подсказок — тоже не
публичная, нужна только `generate.ts`).

## Импорты

### Почему в `tsconfig.json` задублирован алиас `#/*`, если он уже есть в `package.json`?

**Коротко: TypeScript 7.0.2 применяет мягкое резолвление bundler-режима (без расширения, с
авто-`index` папки) только к относительным путям и `tsconfig.paths` — к `package.json#imports`
не применяет, даже когда `moduleResolution` стоит `"bundler"`.**

Проверено эмпирически на живом прогоне `tsc`, три попытки подряд с одним и тем же импортом
(`#/shared/ui/theme-switch`): голый путь к папке — `Cannot find module`; путь с явным `/index`
без расширения — та же ошибка; путь с явным `/index.tsx` — резолвится. То есть дело не в
папке-без-файла, а конкретно в том, что `#`-специфайер идёт через `package.json#imports`-
резолвинг, который остаётся строгим (по спецификации Node ESM) независимо от `moduleResolution`. Добавление зеркального `compilerOptions.paths: {"#/*": ["./src/*"]}` в
`tsconfig.json` решает: тот же алиас, но резолвится через путь, где TS даёт полную bundler-мягкость.
Правка — локально в `apps/skin/tsconfig.json`, общий `@web-core/build/tsconfig` не тронут: находка
про конкретно `package.json#imports`, не про профиль в целом.

## Фейк-генератор

### Почему `generateFakeData` принимает zod-схему, а не имя компонента?

**Коротко: генератору не нужно ничего знать о паспорте, ките или чём-либо ещё о компоненте —
только форму, по которой строить данные.**

Первая версия принимала имя компонента и сама тянула его io-схему (`ioOf`). По результату
разговора это лишняя связанность: единственное, что реально нужно генератору — сама схема.
Второй параметр (`component: string`) остался, но сменил смысл — это уже не «источник знаний о
компоненте», а просто ключ подсказок (`hints.ts`); без записи в таблице для этого имени генератор
ведёт себя ровно так же, как если бы второго параметра не было вовсе.

---

### Почему подсказки длины применяются через `.supply()` по ссылке на схему поля, а не `.override()` по типу?

**Коротко: `.override()` перехватывает ВСЕ вхождения типа во всей схеме разом — задело бы
соседние строковые поля без всякой подсказки; `.supply()` привязан к конкретному экземпляру
схемы по ссылке, значит только явно названное поле.**

`zocker(schema).override("string", generator)` подменил бы генерацию у КАЖДОГО `z.string()` в
схеме — включая поля, для которых в таблице подсказок ничего не сказано, и им пришлось бы либо
тоже писать собственный фолбэк внутри одного общего генератора, либо мириться с тем, что они
внезапно ведут себя иначе. `.supply(fieldSchema, generator)` регистрируется на КОНКРЕТНЫЙ объект
схемы (сравнение по ссылке), полученный через `schema.shape[field]` — затрагивает ровно то поле,
для которого в таблице есть запись, остальные генерируются как обычно.
