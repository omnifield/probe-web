# `@omnifield/probe-web` — заготовка фронта в `web/`

Обвес `baser`. Кладёт в чужую локацию **пять файлов скелета** под `web/` и больше ничего.
Вся начинка — за четырьмя пакетами, которые скелет зовёт зависимостями: рантайм, оснастка
сборки, примитивы и стилевой слой.

> Этот файл **едет в тарбол вопреки `files`**: npm всегда кладёт README, манифест и
> LICENSE. Значит правка README — это правка поставки, а не заметка для своих.

## Поставить

```sh
baser add @omnifield/probe-web
pnpm -C web install
pnpm -C web dev
```

Третья строка поднимает дев-сервер, `pnpm -C web build` собирает статику.

**`-C web` не опечатка.** Скелет ложится в `web/`, а не в корень: в одну локацию рядом с
нами встаёт обвес бэка (`core/`), и оба в корень означали бы перемешанные скелеты. Практическое
следствие для локации: `installCommand` девбокса обязан заходить в `web/` — в корне ставить
нечего.

## Что ложится

| файл | что в нём |
|---|---|
| `web/package.json` | имя приложения, четыре наши зависимости, `dev` и `build` |
| `web/index.html` | страница с `<div id="root"></div>`, точкой входа и блоком оформления кита |
| `web/vite.config.ts` | три строки: конфиг приезжает из `-build` |
| `web/tsconfig.json` | две строки: база типов наследуется из `-build` |
| `web/src/main.tsx` | базовый CSS стиля, примитив из `-ui`, `mount()`, проверка порядка |

**Все пять — класс `placed-once`:** положены один раз, дальше файлы твои, и обвес в них
больше не заглянет. Правь свободно — при обновлении обвеса они не перезапишутся.

## Чего обвес НЕ трогает

`.gitignore` · `.devcontainer/` · корневой `README.md` · **корневой `package.json`** ·
`.omnifield/` · `.claude/`.

Корневой манифест назван отдельно, потому что соблазн залезть в него у фронта самый сильный —
там workspaces и скрипты. У файла один хозяин, и спор за него всплыл бы у потребителя.

## Настройки

Действуют **в момент укладки**, а не в момент работы: значение попадает в файл один раз и
дальше живёт как часть твоего кода.

| настройка | что делает |
|---|---|
| `productName` | поле `name` в `web/package.json` |
| `runtimeVersion` | диапазон npm для `@omnifield/probe-web-runtime` |
| `buildVersion` | диапазон npm для `@omnifield/probe-web-build` |
| `uiVersion` | диапазон npm для `@omnifield/probe-web-ui` |
| `styleVersion` | диапазон npm для `@omnifield/probe-web-style` |

Незаполненная настройка едет за нашими выпусками, заполненная замирает на твоём значении.
Версии в шаблоне не хардкодятся: дефолты проставляются перед публикацией, поэтому обвес не
ждёт выпуска ни одной из зон.

`@omnifield/probe-web-style` назван в манифесте **явно, а не транзитивно через `-ui`**:
приложение импортирует его CSS напрямую, а строгий менеджер пакетов транзитивный импорт не
разрешит. Это не избыточность.

Порта дев-сервера здесь нет намеренно. Он бы застыл в файле при укладке и выглядел живой
регулировкой, ничего не регулируя, — то, что крутится потом, живёт за пакетами.

## Как одеть безголовый кит

`@omnifield/probe-web-ui` **не везёт ни одного класса по умолчанию**: он отвечает за поведение,
доступность и стабильные зацепки, внешний вид — твой. Поэтому скелет показывает приём, а не
оставляет тебя перед неоформленной кнопкой без единой подсказки, с какой стороны к ней подойти.

Приём — блок `<style>` в `web/index.html`, одно правило:

```css
[data-slot="button"] {
  padding: 0.5rem 0.875rem;
  border: 1px solid currentColor;
  border-radius: var(--radius-md);      /* производная шкала — из base.css */
}
```

Цепляйся за две вещи и только за них:

- **`data-slot`** — зацепка, которую примитив ставит ДО спреда пропсов, поэтому её можно
  перебить своим пропом. Одно правило одевает все кнопки приложения разом.
- **размерные шкалы** — `var(--radius-md)` и соседи. Они производные от семени, у семени есть
  подстраховка, и работают они без всякого скина. Имена — того **набора значений**, который
  подключён в `main.tsx`: наш стоит там умолчанием, но обязательным не является. Взял значения
  на стороне — поставь в правило имена своего поставщика, оно твоё целиком.

**Цвета в примере нет намеренно.** Цвет приходит скином, скин — единица (переменные и правила
вида вместе), и половины его поставка не везёт: цвета у того, чего не сшили, быть не может.
Цветовые роли до надетого скина пусты — правило, опирающееся на них, выглядит рабочим и молча
теряет объявления. Свой цвет литералом — тем более: он не следует ни за режимом, ни за скином.

Второй путь — `createStyle` из инструментов стилизации, когда класс зависит от состояния. В
скелете он не показан намеренно: вызов заморозил бы у тебя ещё одну точку поверхности ради
примера, а сами инструменты — отдельная необязательная поставка, и брать их ты не обязан.

**Оформление в разметке — место временное, и это названо в самом файле.** Своё оформление
клади отдельным `.css` рядом с `main.tsx`, импортируй его там, а блок из `index.html` убирай.

**Цена решения названа.** Пример замерзает у тебя навсегда — обвес в `placed-once`-файл больше
не заглянет. Поэтому он ровно один и держится пробой `test/styling.test.ts`: второй селектор
или литеральный цвет роняют прогон. Обратная сторона честного «ничего не показывать» была бы
хуже: скелет — первое, что видит чужая команда, и «как одеть безголовый кит» это первый же её
вопрос.

## Приложение без скина — голое, и это рабочее состояние

Скелет **не одевает приложение**: он не ставит на корень ни имени скина, ни режима, и не везёт
надеваемого набора цветов. Вид приходит **скином** — единицей из переменных и правил вида, — а
скин у тебя свой: его собирают в редакторе и берут из хранилища.

Половины скина не бывает. Пока фреймворк вёз набор цветов «по умолчанию», «нет скина —
приложение голое» оставалось неправдой: одежда снята, а цвет у неё есть. Довод, которым это
решено, короток: **футболку красят после того, как сшили.**

Что из этого следует практически:

- **Режим (светлая/тёмная пара) принадлежит скину, а не документу.** Нет скина — нет и режима:
  переключатель на голом приложении не меняет ни пикселя, потому что менять нечего. Выбор
  человека при этом не теряется — механика скина помнит его и поставит, когда скин наденут.
- **Цветовые роли пусты, пока скин не надет.** Опираться на них в своём CSS до этого нельзя.
  Размерные шкалы работают всегда: они производные от семени, и у семени есть подстраховка.
- **Вспышки светлой темы перед тёмной здесь нет и взяться ей неоткуда.** Скелет ничего не
  восстанавливает до первого кадра, потому что вида нет вовсе. Базовый слой объявляет браузеру,
  что страница умеет обе пары, — это объявление способности, а не выбор вида: голая страница
  следует за настройкой человека, ровно как рисовал бы браузер и без нас.

Появился скин — его имя и режим ставит механика скина из `@omnifield/probe-web-runtime`, и
зовёшь её ты, у себя: имя скина твоё, и в `placed-once`-файле поставки его быть не может.

### Порядок импортов — не декоративный

```
базовый слой → скин
```

Скин, подключённый перед базой, проигрывает ей в каскаде: получится вид, посчитанный от
умолчаний. Выглядит это как «скин почти работает» — хуже явной поломки, потому что чинить такое
никто не идёт. Слот под скин в шаблоне закрыт комментарием: **оформление необязательно**, и
скелет без единого файла скина обязан запускаться.

Тот же случай ловит вторая строка механики, в конце файла:

```ts
checkStyleOrder({ marker: BASE_MARKER });
```

Она спрашивает документ, объявлен ли на корне маркерный токен подключённого набора значений, и
кричит в консоль, если оформление стоит, а базы нет. Ничего не роняет и ничего не красит; не
нужна в проде — сними строку. Имя маркера приезжает экспортом, а не строкой: оно принадлежит
стилевому слою, а этот файл кладётся один раз и не обновляется никогда.

### Набор значений — поставщик, а не фундамент

Базовый слой даёт **поставщик значений**, и наш набор — один из них. В скелете он стоит
умолчанием только потому, что приезжает зависимостью, а не потому, что без него что-то ломается:
набором значений вправе быть чужой, и приложение на нём — исправное приложение.

Поэтому наш набор занимает в `main.tsx` **две строки подряд, которые снимаются вместе**:

```ts
import "@omnifield/probe-web-style/base.css";
import { BASE_MARKER } from "@omnifield/probe-web-style";
```

Взял значения на стороне — сними обе, подключи на их место файл своего поставщика и реши судьбу
проверки порядка. Решений ровно два:

- **у твоего поставщика есть маркерный токен базы** — назови его имя вместо `BASE_MARKER`, и
  проверка продолжит ловить тот же дефект на его наборе. Имён она не знает: что передали, про
  то и спросит;
- **маркера у него нет** — сними строку `checkStyleOrder(…)`. Спрашивать нечего, а оставленная
  проверка кричала бы «базы нет» на исправном приложении.

**Проверка при этом не выброшена, и выбрасывать её не за что.** Она ловит настоящий дефект:
оформление, вставшее без базы, даёт вид, посчитанный от умолчаний. Условной стала не она, а её
вызов — прежде скелет подставлял туда наш маркер безусловно, и потребитель на чужом наборе
получал предупреждение о поломке на исправном приложении.

Половину блока снять не выйдет молча: `BASE_MARKER` приедет ниоткуда, `tsc` назовёт оставшуюся
строку (TS2304), а собранное приложение упадёт на ней при запуске (`vite build` типов не смотрит
и такое соберёт). Громкий отказ вместо тихого ложного крика — это и есть разница, ради которой
блок сделан цельным.

## Что скелет замораживает

Файлы `placed-once` зовут пакеты вечно и той версией вызова, какой их положили. Поэтому
поверхность, которую трогает скелет, — **шесть точек плюс `#root`** в разметке:

```ts
import { mount, checkStyleOrder } from "@omnifield/probe-web-runtime";  // рантайм
import { Button } from "@omnifield/probe-web-ui";                       // примитивы
import { BASE_MARKER } from "@omnifield/probe-web-style";               // имя стиля
import "@omnifield/probe-web-style/base.css";                           // стиль: базовый слой
import { defineConfig } from "@omnifield/probe-web-build/vite";         // сборка
// "extends": "@omnifield/probe-web-build/tsconfig"                     // типы
```

CSS одной строкой, а не двумя: второго подпутя — с надеваемым набором цветов — у поставки
больше нет. Базовый слой не одевает и не держит ни одного цвета; цвет приходит скином, и скин
у тебя свой.

**Две точки стилевого слоя — это точки НАШЕГО набора значений, а не условие работы скелета.**
Он умолчание, а не фундамент: взял значения на стороне — обе уезжают вместе с ним, и поверхность
скелета сокращается до четырёх. Как именно — раздел «Набор значений — поставщик, а не
фундамент».

**Корневой вход `@omnifield/probe-web-style` — отдельная точка, и добавлена она сознательно.**
Оттуда приезжает ровно одно имя: имя токена-маркера базы. Оно принадлежит стилевому слою, и
строкой в `placed-once`-файле его держать нельзя — переименование у соседа не доедет ни до
одного уже созданного продукта.

Подпуть назван **с расширением**. Типы CSS у потребителя приходят шаблоном `declare module
'*.css'` из `vite/client`, а шаблон сопоставляется с ТЕКСТОМ спецификатора: `…-style/css` под
него не попадает, и `tsc` падает с `TS2882`. Дефект нашла зона `reference` до публикации —
иначе он замёрз бы в скелете каждого созданного продукта.

Версия Vite, набор плагинов, цель компиляции и способ разрешения путей за этими точками
двигаются выпуском пакета, не задевая уже созданные продукты. Так же уедет и переход на
Solid 2.0 со сменой `jsxImportSource`: у потребителя в `tsconfig.json` лежит только `extends`.

Число касаний сторожит проба `test/surface.test.ts`: попытка позвать из скелета что-то сверх
шести точек — красная.

## Проверить обвес

```sh
pnpm test               # объявление, груз, поверхность, оформление кита, голое приложение,
                        # поставщик значений
pnpm run typecheck      # типы проб
pnpm run check          # baser check . — обвес подходит посадочному месту
pnpm run payload        # baser pack . --into <временный каталог>
```

`baser check` отвечает данными и называет, чего не хватает, — проверяем им, а не глазами.

Каталог выдачи `pack` обязан лежать **вне** пакета и быть пустым: иначе нагрузка стала бы
частью того, из чего её собирают, а упаковка молча затёрла бы прежнюю. Поэтому `payload`
целится во временный каталог и чистит **свой собственный** перед сборкой.

## Форма объявления — 3

Блок `baser` в `package.json` объявлен формой **3**: это единственное значение, которое
проходит все ворота установленного `@omnifield/baser-cli@0.1.0`. Поднимать «заодно» нельзя —
отказ приедет не к нам, а к потребителю.

Обвес **ничего не исполняет**: он объявляет, а результат есть чистая функция от шаблона и
значений. На этом держится ответ `baser plan` «сошлось».

## На чём это стоит

Четыре правила, которым обвес подчинён и которые объясняют его форму:

- **у файла один хозяин** — потому обвес не трогает ни корневой манифест, ни `.gitignore`, ни
  чужие каталоги локации;
- **обвес описывает себя сам** — состав, настройки и посадочное место объявлены в его же
  манифесте, отдельного реестра снаружи нет;
- **он объявляет, а не исполняет** — результат укладки есть чистая функция от шаблона и
  значений;
- **поверхность, которую трогает скелет, узкая и названа** — всё, что за ней, зоны двигают
  выпуском, не задевая уже созданные продукты.

Ссылок на задачи и узлы здесь нет намеренно: задача закрывается, узел переезжает, ссылка гниёт
— а читатель остаётся без ответа. Что важно знать, написано словами и на месте.
