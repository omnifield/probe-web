# ❓ FAQ

Короткие ответы на конкретные вопросы, которые уже возникали по этому пакету. Не общая
документация (она в [`README.md`](./README.md)) и не план (он в [`ROADMAP.yaml`](./ROADMAP.yaml))
— только решения, каждое с причиной.

---

## Устройство пакета

### Почему genus — `tooling`, а не `engine`?

**Коротко: три функции не делят ни данных, ни состояния — общая только тема, не механизм.**

`registerTool`, `createServer`, `paginate` можно использовать по отдельности и в любом сочетании —
регистрация тула не нуждается в транспорте пакета (её можно вызвать на сервере, поднятом чем
угодно другим), пагинация не в курсе ни того, ни другого. Это ровно определение `tooling` из
корневого README: «россыпь независимых утилит, которые пользователь настраивает штатными
средствами, а не единый собранный механизм». Пилот того же genus — `packages/build`, доку оттуда и
взяли за основу по прямому указанию user.

---

### Почему в корне `src/` только `index.ts`, а `registerTool`/`createServer`/`paginate` — в отдельных каталогах, а не сразу файлами рядом с ним?

**Коротко: правило репозитория — в корне `src/` из файлов только барель, всё остальное по
каталогам (`packages/store`: `engine/` → `.`, `machine/`/`addons/` → свои подпути).**

Первая версия держала три файла (`index.ts`/`transport.ts`/`pagination.ts`) плоско рядом — так в
репозитории не делают нигде: `index.ts` обязан быть тонким барелем без своей логики
(`export * from "./register-tool/index.js"`), а сама логика — в каталоге, даже когда это ОБЩАЯ
(корневая) часть. Общее — то, чем пользуется буквально каждый MCP-сервер зоны (`registerTool`/
`ok`/`err`) — едет через барель `.`, поэтому `register-tool/` переиспользуется корневым адресом.
Тяжёлое и опциональное — своим подпутём: `transport/` тянет `node:http`/`node:crypto` и нужен не
всегда (тул можно регистрировать на сервере, поднятом снаружи), `pagination/` — отдельная
маленькая тема, вообще не про регистрацию тула. `@web-core/build` тут не образец структуры (у
него нет корневого барреля вовсе, `bin.mjs` — не JS-модуль, а CLI-бинарник) — образец именно
`packages/store`.

### Почему `z` в тестах приходит из `@web-core/io`, а не напрямую из `zod`?

**Коротко: `packages/io/src/engine/index.ts` — единственная точка входа к `z` в репозитории,
пакет объявляет это прямым текстом («`z` через этот пакет, не напрямую из `zod`»).**

Раздельные версии `zod` в разных пакетах молча разъезжались бы — `@web-core/io` пин одной версии
на весь репозиторий, `apps/skin/.mcp/src/kit.ts` уже так делает. `src/index.ts` самого
`@web-core/mcp` `zod` не импортирует вообще (только тип `AnySchema` из
`@modelcontextprotocol/sdk/server/zod-compat.js`, стирается на компиляции) — прямая зависимость
на `zod`/`@web-core/io` нужна только тестам, поэтому `@web-core/io` в `devDependencies`, не в
`dependencies`.

### Почему `createServer({transport:"http"})` держит СЕССИЮ (`sessionIdGenerator: () => randomUUID()`), а не честный stateless (`sessionIdGenerator: undefined`), как у Windshift?

**Коротко: в этой версии TS SDK честный stateless требует новый `McpServer`+`transport` НА КАЖДЫЙ
запрос — не подходит модели «тулы регистрируются один раз при старте».**

Проверено живьём: с `sessionIdGenerator: undefined` второй HTTP-запрос на ТОТ ЖЕ `transport`
(после успешного `initialize`) падает `500` без содержательного сообщения — собственный
эталонный пример SDK (`examples/server/simpleStatelessStreamableHttp.js`) создаёт `McpServer` и
`StreamableHTTPServerTransport` заново в каждом обработчике запроса, что для нашей модели (тулы
регистрируются один раз в `createServer`+`registerTool`, не на каждый запрос) означало бы
перерегистрировать все тулы зоны на каждый HTTP-вызов. `sessionIdGenerator: () => randomUUID()`
(stateful режим — сессия трекается заголовком `mcp-session-id`, SDK делает это сам) проверен тем
же способом и работает: один `McpServer`, тулы регистрируются один раз, много запросов подряд.
Windshift этой проблемы не имеет, потому что это другая (Go) реализация SDK от другого вендора —
поведение между SDK на разных языках не гарантированно совпадает даже для одного протокола.

### Почему `access` — три уровня (`read`/`write`/`destructive`), а не четыре, как `AccessLevel` у Windshift (`internal/aitools`)?

**Коротко: у Windshift `admin` — часть его собственной модели скоупов токена, не часть протокола MCP.**

Нативные annotations спеки MCP — `readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`
— различают ровно «читает», «пишет», «разрушает», больше уровней протокол не знает. `admin` у
Windshift нужен его собственному Agent Studio (профили доступа, UI выбора возможностей) — это
надстройка конкретного продукта над протоколом, а не то, что обязано быть в общем тулинге для
любой будущей MCP-зоны. Если какой-то зоне понадобится более тонкая модель прав поверх
`access` — это решение той зоны, не этого пакета.

### Почему конверт ответа (`ok`/`err`) — обязательная точка входа, а не просто «верни объект» в хендлере?

**Коротко: `isError` по спеке иначе никто не проставит — увидели живьём в `apps/skin/.mcp`.**

Аудит `apps/skin/.mcp` (`src/tools.ts`) показал: там ВСЕ ответы, включая настоящие отказы вроде
`unknown component`, уезжают как `isError: false` текстом внутри `{ok:false, error}` — клиент,
который умеет ретраить/иначе показывать `isError:true`, никогда этого не увидит. `ok`/`err` как
обязательная пара — то место, где это решается один раз для всех будущих тулов, а не в каждой
зоне заново (и не забывается, как забылось в skin-mcp).
