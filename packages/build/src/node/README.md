# 🖥️ node

📦 `@omnifield/probe-web-build/tsconfig-node` · `probe-web-node`

TS-раннер и tsconfig-профиль для серверов без Vite (MCP-серверы, локальные службы). Правило
репозитория: дев-пространство — TypeScript, компилированный JS — крайний случай, и его место в
`dist`. Для фронтенда это закрывает Vite. У серверных зон посредника не было — `node` умеет
исполнять только JS, и единственным выходом было писать сервер сразу на JS руками. Так и
получилось: серверы в репозитории написаны на JS не потому, что кто-то выбрал JS, а потому, что
для TS-сервера не было готового пути.

<h2 id="раннер">🚀 Раннер — probe-web-node</h2>

Бинарник пакета, тонкая обёртка над `tsx` (`src/node/bin.mjs`, одна строка). Потребитель не
знает, что внутри — как и с Vite, раннер и его версия решаются здесь, а не в замороженном
скрипте у каждого сервера.

```jsonc
// package.json серверного потребителя
{
  "scripts": {
    "start": "probe-web-node src/server.ts",
    "dev": "probe-web-node watch src/server.ts",
    "typecheck": "tsc -p tsconfig.json --noEmit"
  }
}
```

Бинарник потребитель получает через `pnpm`-симлинк `bin` прямой зависимости — как только он сам
зависит от `@omnifield/probe-web-build`, `tsx` тащить в свои зависимости не нужно: `tsx` —
обычная зависимость самого `build`, а `bin`-скрипт резолвит модули относительно СВОЕГО файла, не
относительно потребителя.

<h2 id="tsconfig-node">📐 /tsconfig-node</h2>

То же, что `/tsconfig` (фронтенд-профиль), но без DOM/JSX: `lib: ["ESNext"]`,
`types: ["node"]`. Общие строгие проверки обоих профилей — в `src/shared/tsconfig.json`.

```jsonc
// tsconfig.json серверного потребителя
{
  "extends": "@omnifield/probe-web-build/tsconfig-node",
  "include": ["src"]
}
```

<h2 id="module-resolution">🔀 Почему moduleResolution: bundler, не nodeNext</h2>

`nodeNext` заставил бы писать относительный импорт соседнего TS-файла с чужим расширением
(`import "./foo.js"` при исходнике `foo.ts`) — JS-расширение в TS-импорте, ровно то, что
правило «дев-пространство — TS-only» запрещает.

`tsx` резолвит модули как esbuild/Vite — без опоры на расширение выходного файла. `bundler`
проверяет типы по тем же правилам, по которым раннер реально исполняет — как и у
фронтенд-профиля с Vite.
