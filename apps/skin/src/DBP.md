# Декомпозиция, границы, принципы (DBP)

Заметка по прямому требованию user после разбора конкретной ошибки в `entities/adapter`:
компонент настройки ручки (`EndpointForm`) был молча перенесён из зоны ручки в зону
мастеринга адаптера — без запроса, без понимания, чья это ответственность. Ниже —
источники и разбор, почему это ошибка декомпозиции, не мелочь.

## 1. Разделение ответственности (Separation of Concerns)

- **Cohesion** (связность) — насколько части одного модуля относятся к ОДНОЙ задаче.
  Высокая связность — модуль занят одним делом от начала до конца.
- **Coupling** (зацепление) — насколько модуль зависит от чужих деталей. Низкое
  зацепление — модуль можно поменять, не трогая соседей.
- Separation of Concerns — делить систему так, чтобы у каждого модуля была ОДНА
  причина меняться. Смешение двух разных задач в одном модуле снижает cohesion И
  повышает coupling одновременно — это не два независимых недостатка, а один.

Источники: [Separation of Concerns — Alexey Naumov](https://nalexn.github.io/separation-of-concerns/),
[Understanding Cohesion, Coupling and Connascence](https://codesmells.substack.com/p/understanding-cohesion-coupling-and).

## 2. Feature-Sliced Design (FSD) — канон этого приложения

`apps/skin/src` уже размечен по FSD: `app / pages / widgets / entities / shared`. Канон:

- **Layers** — модуль слоя может импортировать ТОЛЬКО из слоёв строго ниже. `entities`
  не знает про `widgets`/`pages`; `widgets` не знает про `pages`.
- **Slices** — вертикальный разрез внутри слоя, по business-домену (`entities/component`,
  `entities/adapter`, `entities/chat`...). **Слайсы одного слоя не видят друг друга напрямую**
  — общий код только через Public API соседнего слайса, не через его внутренности.
- **Segments** — `ui/model/api/lib` внутри слайса, группировка по ТЕХНИЧЕСКОЙ роли, не
  по тому, "куда было удобно положить".
- **Одна сущность = одна ответственность.** Каждый слайс — один бизнес-объект
  (пользователь, пост, ручка, схема, адаптер). Смешение НЕСКОЛЬКИХ доменов в одном
  слайсе/компоненте ломает главный смысл FSD: "стабильность при рефакторинге через
  изоляцию", потому что перепутанные домены тянут cross-cutting зависимости обратно
  в код, от которых FSD и должен избавлять.
- **Public API (`index.ts`)** — единственная законная дверь наружу слайса/сегмента.
  Прямой импорт из чужих внутренностей: (а) ломает защиту "остальное приложение не
  должно знать о структуре слайса" — рефакторинг внутри одного слайса не должен
  требовать правок по всему дереву; (б) плодит циклические зависимости; (в) тащит
  наружу вес, который не предполагался публичным.

Источники: [FSD Overview](https://feature-sliced.design/docs/get-started/overview),
[FSD Public API](https://feature-sliced.design/docs/reference/public-api).

## 3. SolidJS — декомпозиция компонентов

- Компонент — одна причина для изменения. Пример из практики: компонент, который
  ОДНОВРЕМЕННО тянет данные и рисует их, нарушает SRP — делится на "кто достаёт" и
  "кто показывает".
- Solid поощряет **renderless-компоненты** (логика без разметки, как хук) и
  **compound-компоненты** (несколько частей делят состояние через контекст) — оба
  паттерна про то, что у каждой части — своя явная роль, а не "куда влезло".
- Предупреждение из тех же источников: не превращать это в догму — лишнее дробление
  ради дробления тоже вредно. Вопрос не "разбить как можно мельче", а "у каждого
  куска — одна явная причина существовать".

Источники: [Best Practices for Working with SolidJS](https://blog.openreplay.com/solidjs-best-practices/),
[SOLID principles: Single responsibility in JS frameworks](https://blog.logrocket.com/solid-principles-single-responsibility-in-javascript-frameworks/).

## 4. Разбор конкретной ошибки

Три РАЗНЫХ домена, у каждого — свой слайс/сегмент в `entities/adapter`:

| Домен | Что это | Где живёт |
|---|---|---|
| Ручка (`Endpoint`) | адрес, метод, хедеры, тело — как ПОЗВОНИТЬ вовне | `ui/openapi/` — там, где ручка заводится и живёт (список ручек) |
| Схема (`Schema`) | скелет ответа ручки — результат вызова | принадлежит ручке (`endpointId`), но это ДАННЫЕ, не форма |
| Адаптер (`Adapter`) | связка схема↔компонент, поле-в-поле | `ui/mastering/` — там, где адаптер СОЗДАЁТСЯ |

Ошибка: `EndpointForm` (настройка ручки — метод/адрес/хедеры/тело/кнопки вызова) была
перенесена внутрь `ui/mastering/index.tsx` — зоны, отвечающей за СВЕДЕНИЕ схем в
адаптер. Это смешало "где ручка настраивается" и "где адаптер собирается" в одном
компоненте. По FSD-канону это ровно тот случай "смешения концернов в одном слайсе",
который методология запрещает: `mastering` начал знать о деталях ручки (`onChangeMethod`,
`onChangeUrl`...), которые ему для его прямой задачи не нужны — ему нужна ТОЛЬКО уже
готовая схема.

Правило на будущее (сказано user прямым текстом): форма настройки ручки — там, где
ручка. Форма/показ схемы для адаптера — там, где адаптер создаётся. Мастерингу нужны
СХЕМЫ (готовые данные), не форма ввода ручки.

## 5. Чек-лист перед тем, как класть код в новое место

1. Чей это домен — ручка, схема или адаптер? Если ответ неочевиден — это сигнал
   остановиться и спросить, не отгадывать.
2. Двигаю компонент между зонами — я РЕШАЮ архитектуру или ВЫПОЛНЯЮ то, что сказал
   user? Если первое — стоп, спросить прямым текстом, не тащить самому.
3. Новый компонент тянет проп/колбэк из чужого домена (`onChangeMethod` внутри
   компонента про схемы) — это симптом, что он не в своей зоне.
4. Один компонент решает две задачи разом ("показать" + "настроить чужую сущность") —
   разделить на два, каждый в своей зоне.
