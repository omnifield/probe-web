# ⚡ vite

📦 `@web-core/build/vite`

Фабрика конфига Vite для web-core — и для приложения, и для библиотеки. `vite.config.ts`
потребителя едет классом `placed-once`: положен один раз и больше никогда не обновится.
Оставить его содержательным значило бы заморозить версию Vite, набор плагинов и настройки
сборки — то есть ровно то, что обязано двигаться. Поэтому конфиг целиком прячется сюда, а у
потребителя остаются три строки.

<h2 id="приложение">📱 Конфиг приложения</h2>

```ts
// vite.config.ts потребителя
import { defineConfig } from "@web-core/build/vite";
export default defineConfig();
```

`defineConfig(options?)` — готовый конфиг с `vite-plugin-solid` внутри; потребитель не знает
ни про плагин, ни про версию Vite. `options` — то немногое, что вывести неоткуда: `base`
(приложение живёт не в корне origin), `proxy` (чужой процесс, о котором пресет знать не может),
`plugins` (довесок сверх пресетных). Обычный потребитель не передаёт ничего.

<h2 id="дев-цикл">🔄 Дев-цикл: исходники соседей</h2>

Пакеты монорепозитория связаны `workspace:*` (симлинк), но их `exports` ведут в `dist`. Значит
без отдельной меры дев-сервер отдаёт приложению **собранное**: правишь исходник соседа — в
браузере вчерашний код, и вывод о своей правке делаешь по чужому старому (`PWEB-1`).

В дев-режиме (`apply: "serve"`, сборки не касается) конфиг добавляет:

- **алиас «подпуть соседа → файл его исходника»**. Сосед определяется машинно: символическая
  ссылка из `node_modules` ведёт НАРУЖУ из `node_modules`. Пакет из реестра (в том числе наш
  же кит, поставленный потребителю) остаётся внутри, алиасов не возникает вовсе;
- **`optimizeDeps.exclude`** на этих же соседей — иначе пребандл сложил бы их копию в кэш, и
  правка исходника перестала бы доезжать до браузера до сброса кэша;
- **`server.fs.allow`** на папки найденных соседей плюс корень приложения — их исходники лежат
  вне корня приложения, и без разрешения дев-сервер отказывается их отдавать;
- **`server.host: true`** — см. FAQ.md.

Подменяются только **модульные цели из `dist`**. У стилей и данных исходника-пары нет вовсе:
собранный `css` пакета бывает не копией файла, а результатом порождения. Свежесть таких целей
закрывает не алиас, а порождение по запросу — см. ниже.

<h3 id="порождённый-css">🎨 CSS соседа порождается на запрос</h3>

Часть соседей свой CSS не хранит, а порождает: ручная часть плюс блоки, собранные из перечней в
коде. Алиас здесь бесполезен — подставлять нечего. Без отдельной меры приложение получает
`dist/css/*.css` прошлой сборки: на свежем клоне его нет вовсе, а после сборки он тихо
устаревает от первой же правки перечня.

Поэтому такие подпути **порождаются на запрос**:

- способность соседа читается с его поверхности, а не из списка имён — подпуть `./generate` с
  найденным исходником, имя функции выводится из имени CSS-подпути (`./base.css` → `baseCss`);
- функции в модуле не нашлось — подпуть остаётся файлом с диска;
- id перехваченного модуля — та же цель `exports`, что и в сборке: один адрес в обоих режимах;
- порождатель грузится через сам дев-сервер (`ssrLoadModule`), не импортом из `dist` — иначе
  вернулась бы ровно та вчерашняя сборка, ради ухода от которой всё и делается;
- правка внутри папки соседа обесценивает всё, что он порождает (`hotUpdate`) — порождённый CSS
  в графе клиента на исходники соседа не ссылается, связь достраивается зацепом.

Форма рыночная (UnoCSS, `@tailwindcss/vite`) — своё здесь одно: как опознаётся способность
соседа (см. FAQ.md).

<h2 id="библиотека">📚 Конфиг библиотеки</h2>

Вторая работа того же подпутя — сборка библиотеки (`ui`, `skin`, `assembly`, …) вместо
приложения, вместо того, что раньше каждая такая зона несла своим `scripts/build.mjs` поверх
esbuild — почти дословным повтором, который никто не заметил бы разошедшимся.

```jsonc
// package.json потребителя
"build": "vite build && tsc -p tsconfig.build.json"
```

```ts
// vite.config.ts потребителя-библиотеки
import { defineLibraryConfig } from "@web-core/build/vite";
export default defineLibraryConfig({
  entries: [{ name: "index", source: "src/index.ts", solid: true }],
});
```

Один проход `vite build` (library mode — штатный режим Vite) собирает все входы веткой
`default` (JSX уже разобран `vite-plugin-solid`), и в конце сборки (`closeBundle`) довешивает
ветку `solid` — непреобразованный JSX (`dist/<name>.jsx`) — для входов с `solid: true`: условие
`solid` в `exports`, по которому потребитель на Solid применит свою трансформацию сам. Почему
это отдельный проход esbuild, а не ещё один `vite build` — см. FAQ.md.

Внешние зависимости — любой спецификатор не относительным путём: чужого в бандл не попадает ни
байта, копию `solid-js`/`@ark-ui/solid` приносит потребитель. Декларации (`.d.ts`) в этот
конфиг не входят — отдельным `tsc`, тем же компилятором, что проверяет код при typecheck.

<h2 id="prepare">🔧 prepare — оснастка собирается на установке</h2>

Конфиг приложения сам импортирует `@web-core/build/vite`, и его Vite грузит ДО того,
как плагин из этого конфига может что-то подменить. Алиасом это не лечится в принципе:
инструмент, которым собирают, не может собираться собой же во время собственной загрузки.

Поэтому у пакета есть жизненный цикл `prepare` (`PWEB-16`):

```jsonc
"scripts": { "prepare": "pnpm run build" }
```

Менеджер зовёт его для пакетов воркспейса **на установке** — собранная оснастка появляется сама,
до первой команды разработчика. `prepare` есть только у зоны `build`: остальные пакеты
репозитория видны через исходники алиасом, и собирать их на установке значило бы вернуть ровно
ту сборку, от которой уходим.
