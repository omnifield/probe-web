# @omnifield/probe-web-style

**Набор значений** локации `probe-web`: токен-контракт, шкалы и построение половин из семени.
Готового набора значений здесь НЕТ, и семантических имён тоже нет — это язык, а не палитра
(`PWEB-50`, `PWEB-61`).

**Это ОДИН ИЗ ПОСТАВЩИКОВ значений, а не фундамент** (`PWEB-3`). Оформление вправе взять
значения у нас, взять у кого-то ещё или обойтись своими — и остаться законным: скин,
написанный без единого нашего токена, обязан проходить все проверки. Пока «фундамент»
значило «без нас ничего не работает», право скина не брать наши значения держалось словом.

**Инструментов стилизации здесь нет.** `cn`, `createStyle` и реэкспорт `cva` — отдельная
необязательная поставка `@omnifield/probe-web-style-tools`; зависимости на неё у нас нет, как
и у неё на нас. Разрез идёт в обе стороны: односторонний держался бы обещанием.

Зависимостей на `ui`, `runtime` и `build` здесь нет и быть не может: направление
зависимостей одностороннее. Контракт зон целиком — `PROBEWEB-4`; эта страница его не
заменяет, а пересказывает со стороны пакета. Цветовая модель и её основания — `PROBEWEB-12`.

## Что наружу

| точка | что даёт |
|---|---|
| `@omnifield/probe-web-style` | токен-контракт, генератор шкал, **модель темы и её отрисовка в CSS**, имя маркера приезда базы, гейт контраста, разбор цвета |
| `@omnifield/probe-web-style/generate` | **порождение CSS по требованию**: `baseCss()`, `themesCss()` — чистые функции, из которых берутся оба файла ниже |
| `@omnifield/probe-web-style/base.css` | **только сброс**: `box-sizing`, `margin`, `appearance` на кнопках, ни одного кастом-свойства (`PWEB-66`, `PWEB-122`) |

CSS через корневой вход НЕ идёт: манифест объявляет `sideEffects: false`, и импорт-побочка
из корня была бы выброшена tree-shaking'ом. Стили подключает приложение — двумя строками:

```ts
import "@omnifield/probe-web-style/base.css";  // сброс и значения, и больше ничего
```

**CSS-артефакт ОДИН, и в нём остался ТОЛЬКО СБРОС** (`PWEB-66`, `PWEB-122`): `box-sizing`,
`margin` и нейтрализация нативного вида кнопки (`appearance: none`), ни одного кастом-свойства,
ни одного запасного значения. Ни палитры (`PWEB-50`), ни семантических имён (`PWEB-61`), ни
значений.

Знание при этом никуда не делось — ушла ПЕЧАТЬ. Форма шкалы, шаг сетки, проверка поддержки
`round()`, имя оси плотности, границы осей и порядок слоёв живут ДАННЫМИ на поверхности: из них
печатает скин и по ним строят ползунки. Подробнее — «Инвариант `base.css`» ниже.

Геометрия при этом работает: дефолты размерных шкал подставлены прямо в `var(--семя, …)`.

### Вход один (`PWEB-56`)

```ts
import { buildScale } from "@omnifield/probe-web-style";
```

Входов было два: корень и подпуть `/values` — он заводился как вход **без реактивной части**
(`PWEB-44`). Solid трогал ровно один файл, реактивный контроллер темы, но вход был один, и Solid
приезжал всем, включая тех, кому нужны только значения; попалась на этом механика скина.

**Реактивной части больше нет** — реестр тем и сигнал текущей темы сняты вместе с предметом: тем
не существует, единицей стал скин, режим стал его половиной, надеваемая палитра снята. Корень
совпал с подпутём имя в имя, и **подпуть снят**: две двери к одному и тому же — ровно тот второй
источник правды, против которого написано остальное здесь.

Снималась дверь отдельной правкой и в правильном порядке: сначала единственный потребитель
(`packages/skin`) вернулся на корень, потом ушёл ключ из `exports`. Наружу подпуть не уезжал ни
разу — версия всё это время `0.1.0`, — поэтому ломающее оно только внутри дерева.

**Файл `src/values.ts` при этом остался**, и это не инерция: у него было две работы — подпуть и
перечень поверхности. Ушла первая. Перечень имён живёт в одном месте, `src/index.ts` берёт его
одной строкой `export *`; здесь записано ЧТО зона обещает, там — КАК это отдаётся наружу, и
второе ещё будет меняться, а первое не должно.

**Solid зоне не нужен вовсе.** Снят из манифеста целиком — ни одноранговой, ни разработческой
зависимости. Проверено запуском в установке, где его физически нет:

| проба | было (`PWEB-44`) | стало |
|---|---|---|
| `import "…"` (корень) | **падает**: `Cannot find package 'solid-js'` | поднимается |
| `import "…/generate"` | поднимается | поднимается |
| `import "…/values"` | поднимается | **падает** — двери нет |

Последняя строка работает **положительным контролем**: без падающего импорта зелёный прогон
означал бы и «Solid не нужен», и «импорт вообще не выполнялся». Контролем взят именно снятый
подпуть, а не выдуманное имя, — так одна проба отвечает и «дверь закрыта», и «мы до двери дошли».
Со стороны компилятора то же держит `types.test.ts`: `TS2307` («модуля нет»), а не `TS2305`
(«имени нет») — разница между «двери нет» и «дверь есть, но пустая».

Обещание, ради которого подпуть заводился, дверь пережило и держится теперь на корне
(`test/entries.test.ts`): `solid-js` не импортирует ни один исходник, не объявлен ни одним видом
зависимости, и обход собранного графа поставки не выходит за её пределы.

### Своей палитры у зоны нет (`PWEB-50`)

Была: `themes.css` с парой половин, и скелет её надевал. Ушла целиком — вместе с семенами
(`DEFAULT_SEEDS`), посчитанными половинами (`DEFAULT_LIGHT`, `DEFAULT_DARK`), моделью
(`DEFAULT_THEME_MODEL`) и именем (`DEFAULT_PALETTE`).

**Довод, и он не про удобство.** Палитра без рецептов — это **половина скина**, отгруженная
фреймворком. Половин у скина не бывает: он единица, переменные и рецепты одной записью. Пока
палитра была, «нет скина — приложение голое» оставалось неправдой — тот же дефект, что прошлая
волна вычистила из типографики (`PWEB-39`), только в другом месте.

**Уходит набор, а не язык.** Шкалы, роли, ступени, построение половины из семени — это имена
для значений и способ их получить; они на месте, и прежние пробы на них зелёные без правок.
Не осталось только готовых значений: семя называет тот, кто делает скин.

**Сборщика тем тоже больше нет** (`PWEB-66`). Вопрос был не «удалить ли», а остался ли у него
ПРЕДМЕТ: тема как единица отменена, единицей стал скин. Замер подтвердил — живых зовущих во
всём дереве ноль, и скин строит свои половины сам, вызывая `buildScale` напрямую, а не через
сборщик. Ушли `createTheme`, `buildThemeTokens`, `themeModelToCss`, контракт токенов темы
(`SCALE_TOKENS`, `THEME_META_TOKENS`, `CHART_TOKENS`, `PALETTE_TOKENS`) и всё, чем палитра
цеплялась к документу по имени.

Вместе с ними — `SHARED_META`: шрифты, тени и умолчания семян. Рекомендованный ряд фреймворк не
возит ни в каком виде, его дом — эталонный скин.

### Режим принадлежит скину, а база объявляет способность

**Решение архитектора 2026-08-22**, страница «Скин», раздел «Режим — половина скина, а не
свойство документа».

Прежде базовый слой называл конкретный режим: `light` на корне, `dark` при классе. Довод был —
режим выбирает приложение, а мы лишь переводим его выбор браузеру. Предпосылка исчезла: режим
принадлежит **скину**, обе половины его половины, и «нет скина — нет и режима».

Назвать режим базе теперь нечем — скина она не знает. Молчать тоже нельзя: молчание браузер
читает как выбор светлого, то есть молчание — тоже выбор, просто необъявленный. Остаётся
третье:

```css
:root { color-scheme: light dark; }
```

«Страница умеет обе, следуй за человеком». Это не вид от фреймворка, а его отсутствие: браузер
рисует своё, ровно как рисовал бы без нас.

**Проверено живым документом, а не чтением** (`test/mode.test.ts`): на приложении без скина
переключение класса режима не двигает НИ ОДНОГО из объявленных базой значений. Рядом стоит
положительный контроль — с надетой палитрой режим значения меняет, значит замер умеет замечать
изменения, а не молчит.

Живой браузер добавляет то, чего jsdom не умеет (разрешение `var()` и канва): на голой странице
класс не меняет ничего, а цвет текста идёт за настройкой СИСТЕМЫ — чёрный при светлой, белый при
тёмной. С надетой палитрой тот же класс двигает шесть ролей.

**Чего здесь нет и почему это не наш пробел:** надетый скин обязан назвать браузеру свою
половину сам, иначе системные элементы (полосы прокрутки, галочки, автозаполнение) пойдут за
системой, а компоненты за скином. Объявить это может только тот, кто знает, какая половина
надета, — механика скина. Заявка туда поднята.

**Отдельно от режима — нативный вид кнопки, и это уже наша заявка** (`PWEB-122`). Живой Chromium
показал `appearance: auto` на каждой кнопке гармошки независимо от `data-variant`: браузер поверх
`background: transparent`, который ставит скин, рисует свой сплошной фон и свою рамку — вид кита
решает не скин, а UA. Это не вопрос ЦВЕТА (значит, не режима и не палитры), а вопрос того, кто
вообще ДЕРЖИТ кисть, — то же основание, по которому в сбросе стоит `box-sizing`. Нейтрализация
легла в сброс третьим правилом: `appearance: none` на `button` и трёх кнопочных `input[type]`.

## База НЕ ОДЕВАЕТ, и семантических имён в ней нет (`PWEB-61`)

Из базового слоя ушли три блока — **35 семантических ролей** (`--surface`, `--text`,
`--focus-ring`, `--brand-solid`, `--danger-solid` и остальные), **28 устаревших имён** прежнего
набора (`--primary`, `--card`, `--muted`, `--destructive`, `--input`, `--ring`, восемь
`--sidebar-*`) и **объявление `color-scheme`**. Исходники сняты вместе с выводом: мёртвый
порождатель хуже мёртвого вывода, его заведут обратно.

**Довод не в том, что они ссылались в пустоту** — хотя ссылались: ступеней `--neutral-1`,
`--brand-9`, `--danger-9` в поставке нет с тех пор, как снята палитра, и роли были проводкой
к тому, чего не существует.

Довод в границе: **значение, которое скин пересевает, — механизм; имя, которое называет вид, —
решение.** Шкала интервалов механизм. «Фон приложения — первая нейтральная ступень, текст —
двенадцатая, кольцо фокуса — восьмая брендовая» — чужая система вкуса, отгруженная фреймворком.
Скин, которому такие имена нужны, объявит их сам: у него для этого есть всё.

### `color-scheme` ушёл тоже, и это отмена прежнего объяснения

Строка стояла как `light dark` и объяснялась «способностью»: страница умеет обе половины,
следуй за человеком; браузер, мол, рисует своё и без нас (`PWEB-50`).

**Вторая половина объяснения оказалась неверной, и показал это живой браузер.** Без нашей
строки браузер отвечает `normal` и рисует светлое при ЛЮБОЙ настройке человека. Следование за
системой бралось не «само», а ровно из нашего объявления — то есть строка была решением о виде,
просто отданным браузеру.

Цена, которую замер сделал видимой: голая страница, где нет ничего, кроме базы, показывала два
разных вида — тёмные холст, поле, список и флажок при тёмной системе, светлые при светлой. Две
страницы там, где обещано отсутствие вида.

Замер живым браузером (`tools/live-check/`, 2026-08-22), кадры сравнивались по хешу:

| | светлая система | тёмная система | кадры |
|---|---|---|---|
| **сейчас** | `normal`, поле белое | `normal`, поле белое | **совпали** |
| мутация: вернуть `color-scheme: light dark` | поле белое | поле `rgb(59,59,59)`, текст белый | **разошлись** |

Мутация обязательна: без неё «кадры совпали» значило бы и «страница перестала меняться», и
«замер не различает вида вовсе».

**Надетый скин при этом называет половину сам** — и делает это правильно: без класса режима
страница отвечает `light`, под классом `dark`, и за системной настройкой не идёт ни в одном из
случаев. Проверено тем же браузером на настоящем порождённом скине.

### Что остаётся в базе и почему это не вид

- **сброс** — `box-sizing`, `margin`, `appearance: none` на кнопках (`PWEB-122`). Ради него
  база и едет: снятие решений браузера, а не внесение своих;
- **размерные шкалы** от семян, ось плотности, подстраховка `round()`;
- **границы осей** — знание о норме, а не вид;
- **шкала слоёв** — порядок перекрытия, а не look;
- **длительности и кривые**.

Сомнение по конкретному имени решается не здесь, а разговором: имя, называющее вид, снимается
решением, а не по ходу правки.

### Двенадцать ступеней и что каждая значит

| ступень | назначение | гарантия контраста |
|---|---|---|
| 1 | фон приложения | — (фон) |
| 2 | фон приложения, приглушённый | — (фон) |
| 3 | фон элемента | — (фон) |
| 4 | фон элемента при наведении | — (фон) |
| 5 | фон элемента при нажатии | — (фон) |
| 6 | тонкая граница, разделитель | — (оформление) |
| 7 | граница элемента | — (оформление) |
| 8 | сильная граница, кольцо фокуса | **≥3:1** к ступеням 1–2 (1.4.11) |
| 9 | сплошной акцент | — (верность бренду) |
| 10 | сплошной акцент при наведении | — (верность бренду) |
| 11 | текст низкого контраста | **≥4.5:1** к ступеням 1–3 (1.4.3) |
| 12 | текст высокого контраста | **≥4.5:1** к ступеням 1–5 (1.4.3) |
| `contrast` | подпись поверх сплошной ступени | **≥4.5:1** к ступеням 9–10 (1.4.3) |

Шкал три — `neutral`, `brand`, `danger`; плюс отдельный ряд `--chart-1…5` (категориальные
цвета данных, каждый ≥3:1 к фону приложения — на графике цвет носит информацию).

У каждой шкалы есть **параллельный альфа-ряд** `--<шкала>-a1…a12` и одно отдельное значение
`--scrim` — см. «Слои поверх страницы».

**Где гарантии НЕТ и почему** — перечень объявлен явно и живёт кодом (`NO_PROMISE`), потому
что молчание читается как «гарантия есть»:

- **1–5** — фоны: контраст даёт то, что НА них, а не они сами;
- **6–7** — тонкая граница и разделитель: оформление, а не носитель информации;
- **9–10** — сплошной акцент: сохраняем верность бренду. 1.4.11 требует контраста от того,
  что ИДЕНТИФИЦИРУЕТ контрол; у кнопки с видимой подписью это подпись, и её контраст
  обещает ступень `contrast`. Кнопка без подписи (одна иконка) — забота того, кто её рисует.

## Смена бренда — одно значение, и делает её скин

```ts
import { buildScale } from "@omnifield/probe-web-style";

const half = buildScale("#0f6fde", "dark");   // одно семя → вся половина шкалы
```

Прежде здесь стоял `createTheme`: он собирал ТЕМУ из трёх семян. Темы как единицы больше нет
(`PWEB-66`), и пересевает себя скин — своими семенами, вызывая построение напрямую. Зона отдаёт
то, что он зовёт: построение половины из одного значения с обещаниями контраста.

## Слои поверх страницы

Два разных вопроса, и путать их дорого: **чем красить** просвечивающий слой и **в каком
порядке** слои лежат.

### Альфа-ступени: чем красить

Сплошная ступень закрывает то, что под ней. Слою поверх страницы это подходит не всегда:
затемнение под диалогом обязано просвечивать, а подсветка при наведении ложится на
**произвольный** фон — полосатую таблицу, картинку, чужой блок, — а не на известный.

Поэтому у каждой шкалы есть параллельный ряд: **ступень `aN` поверх ступени 1 даёт ступень
`N`**. Обещание проверяется машиной (`test/alpha.test.ts`), а не глазами на стенде.

```css
[data-slot="row"]:hover { background-color: var(--tint-hover); }
[data-slot="dialog-overlay"] { background-color: var(--overlay); }
```

Три свойства, о которых надо знать заранее:

- **Совпадение гарантировано только поверх ступени 1.** На произвольном фоне вуаль его
  подкрашивает, а не заменяет, — ради этого альфа-ряд и заводится.
- **Альфа-ступень следует за режимом:** в светлом затемняет, в тёмном осветляет. Для
  подсветки при наведении это ровно то, что нужно.
- **Верхние ступени насыщенных шкал вырождаются в непрозрачные.** Цвет с почти нулевым
  каналом поверх почти белого фона недостижим ни при какой прозрачности — это свойство
  композиции, а не дефект. В такой точке ступень честно совпадает со сплошной.

**Затемнение под модальным слоем — это `--overlay`, а не альфа-ступень.** Оно чёрное в обоих
режимах: осветляющая вуаль в тёмной теме не убирает содержимое из фокуса, а подсвечивает его.
От шкалы берётся только сила перекрытия — прозрачность девятой альфа-ступени светлого режима.

**Гарантии контраста на альфа-ступенях нет и быть не может:** контраст полупрозрачного цвета
зависит от того, что под ним. Считает его тот, кто знает подложку.

### Шкала слоёв: в каком порядке

| токен | значение | что лежит |
|---|---|---|
| `--z-base` | 0 | обычный поток страницы |
| `--z-dropdown` | 10 | панель списка: выпадающий список, автодополнение |
| `--z-popover` | 20 | поповер, всплывающая подсказка |
| `--z-overlay` | 30 | затемнение под модальным слоем |
| `--z-dialog` | 40 | диалог, выезжающая панель |
| `--z-toast` | 50 | уведомление |

Пока слой один, `z-index: 1` работает. При четырёх слоях число из головы спорит с чужим
числом из головы, и спор выигрывает тот, кто написал больше. **Порядок слоёв — контракт:**
перестановка двух слоёв ломает чужой вид так же, как переназначение ступени, и едет мажором.

Шаг 10, а не 1: между нашими слоями обязано остаться место для чужого — кому нужен слой между
поповером и диалогом, вписывает 25 и не просит нас перенумеровать шкалу.

**Что шкала НЕ решает.** Мы объявляем порядок; контекст наложения создаёт тот, кто рисует
слой. `z-index` действует только среди соседей по контексту (CSS Position 3, §9), и никакой
токен не поднимет слой, вложенный в чужой `transform` или `filter`. Слои поверх страницы
монтируются порталом в корень — это забота зон `ui` и `skin`.

## Размерные шкалы

Приём тот же, что у скруглений: производная шкала от ОДНОГО семени. Семя задаёт тема,
ступени считает `base.css`.

| семя | ступени | плотность |
|---|---|---|
| `--radius` | `--radius-xs…3xl`, `--radius-full` | нет |
| `--space` | `--space-1/2/3/4/6/8/12/16/24/32` (сетка 0.25rem) | **да**, с посадкой на сетку |
| `--font-size` | `--font-size-xs…4xl` | **да**, без посадки на сетку |
| `--column` | `--column-24/32/40/48/56` (ширины поверхностей) | **да**, с посадкой на сетку |
| `--control-height` | `--control-height-sm/md/lg` | **да**, с посадкой на сетку |
| `--border-width` | `--border-width-1/2/4` | нет |
| `--tracking` | `--tracking-tight/normal/wide` | нет |

Без шкалы намеренно: `--leading-*` (высота строки — безразмерное отношение),
`--weight-*` (нормированный ряд, CSS Fonts 4 §2.3), `--control-target-min` (пол нормы),
`--motion-*` и `--ease-*` (подобранный ряд, а не размеры).

### Имя ступени интервалов равно её множителю

`--space-6` — это шесть шагов сетки, `--space-32` — тридцать два. Не порядковый номер: с
номером ступень **нельзя вставить**, между `--space-4` и `--space-5` места нет, и залатать один
разрыв вставкой значит получить тот же затык на следующем. С множителем в имени вставлять
ничто не мешает — недостающая кратность уже названа своим числом. Заодно имя перестало врать:
порядковый `--space-5` был множителем 6, `--space-6` — восьмёркой.

**Переименование ломающее и сделано разом (2026-08-18, `PROBEWEB-16` часть Б).** Устаревших
псевдонимов, в отличие от цветовых ролей, здесь нет и быть не может: `--space-5` существует в
обеих схемах с РАЗНЫМИ значениями (24 порядковое, 20 множитель), а псевдоним не может значить
оба сразу — переход потребовал бы третьего имени на время.

| было | стало | значение при плотности 1 |
|---|---|---|
| `--space-1…4` | без изменений | 4·8·12·16px |
| `--space-5` | `--space-6` | 24px |
| `--space-6` | `--space-8` | 32px |
| `--space-7` | `--space-12` | 48px |
| `--space-8` | `--space-16` | 64px |
| `--space-9` | `--space-24` | 96px |
| `--space-10` | `--space-32` | 128px |

**Осторожно с `--space-6` и `--space-8`: имя выживает, значение меняется.** Прежний `--space-6`
был 32px, новый — 24px. Такое место у потребителя не краснеет ни сборкой, ни пробой — уезжает
вид, и это единственный молчаливый класс правки во всём переезде. Исчезнувшие имена (`5`, `7`,
`9`, `10`) ведут себя честнее: неразрешённый `var()` делает свойство недействительным, и это
видно.

### Плотность — ось, а не набор значений

`--density` умножает **интервалы, высоты контролов, кегль и ширины колонок**. Форму она не
трогает — скругления, толщины границ, трекинг: это очертание, а не размер.

```css
.table-dense { --density: 0.875; }
```

**Кегль в оси с 2026-08-18, и прежнее основание снято явно.** Раньше здесь стояло обратное:
«кегль не трогаем, иначе 1.4.4 Resize Text». Причина не выдержала проверки — 1.4.4 требует
ВОЗМОЖНОСТИ увеличить текст вдвое, а не запрещает множитель меньше единицы, и вся шкала
выражена в `rem`, поэтому настройка пользователя уважается при любой плотности. Половинчатая
же ось разваливала вещь: геометрия ехала, а всё, что меряется кеглем, стояло на месте.
Размер текста защищает не запрет оси, а её нижняя граница. Решение — `PROBEWEB-16`, часть А.

### Сетка 0.25rem держится при любом множителе

Произвольная плотность даёт дробь, а от дроби едут соседние элементы, посчитанные от разных
ступеней. Поэтому значение плотной шкалы возвращается на сетку — и объявляется **дважды**,
подстраховкой на случай браузера без `round()` (см. ниже):

```css
:root {
  /* первым — без округления: это и есть подстраховка */
  --space-4: calc(var(--space, 0.25rem) * 4 * var(--density, 1));
}

@supports (width: round(nearest, 1rem, 0.25rem)) {
  :root {
    --space-4: round(nearest, calc(var(--space, 0.25rem) * 4 * var(--density, 1)), 0.25rem);
  }
}
```

Шаг сетки — **литерал `0.25rem`, а не семя интервалов**: сетка это общий ритм двух шкал с
разными семенами (`--space` и `--control-height`), и сделай шагом семя — шкалы сядут на разные
сетки. В `rem`, а не в `px`: при корневом кегле ≠ 16px «сетка 4px» перестаёт быть правдой.

**Кегль на сетку НЕ садится, и это единственное исключение.** Он задан отношениями к базовому,
а шаг сетки эти отношения разрушает: уже при плотности 1 — то есть у всех, кто плотность не
трогал вовсе, — `sm` (0.875rem) совпал бы с `md`, а `lg` (1.125rem) с `xl`. Шкала потеряла бы
две ступени, сборка у потребителя при этом не краснеет, а вид уезжает. Исключение держится
пробой «сетка схлопнула бы шкалу кегля», а не обещанием.

У интервалов сходиться ступеням можно и нормально: на нижней плотности `--space-2` и
`--space-3` дают одно значение — это цена сетки для ритма. Чего не бывает — старшая ступень
мельче младшей; это отдельная проба.

### Ширины поверхностей — колонка, а не кратность интервалу

Ширина модального окна, потолок панели, потолок подсказки, минимум меню, ширина уведомления —
раньше база их не нормировала вовсе, и они жили абсолютными литералами у потребителя.

**Семя `--column` — средняя ширина ОДНОГО знака при базовом кегле, а имя ступени равно числу
знаков:** `--column-40` это колонка на сорок знаков. Тот же приём, что у интервалов, где семя —
один шаг сетки.

```css
[data-slot="dialog"] { inline-size: min(var(--column-56), 100vw - var(--space-8)); }
[data-slot="tooltip"] { max-inline-size: var(--column-32); }
```

| ступень | знаков | при плотности 1 |
|---|---|---|
| `--column-24` | 24 | 12rem |
| `--column-32` | 32 | 16rem |
| `--column-40` | 40 | 20rem |
| `--column-48` | 48 | 24rem |
| `--column-56` | 56 | 28rem |

**Почему не кратность интервалу.** Ширину окна можно получить и как `calc(var(--space-32) *
3.5)` — число выйдет то же, а связь будет придуманной. Ширина окна происходит не от ритма
отступов, а от того, сколько знаков в строке человек прочитывает, не теряя её начала.
Основание, взятое у соседней шкалы ради красоты вывода, — фикция, только записанная.

**Почему не `ch`, хотя единица знака в CSS есть.** `ch` разрешается по шрифту ТОГО элемента,
где токен применён: один и тот же `--column-40` дал бы разную ширину в основном тексте и в
моноширинном блоке. Для контракта ширины это дефект, а не гибкость. Семя в `rem` —
приближение (≈0.5rem у типичного гротеска при кегле 16px) и **переопределяемо темой**:
гарнитура с другой средней шириной знака ставит своё, и все ступени едут за ним.

**Плотность — да, сетка — да.** Кегль едет плотностью; не поехала бы за ним колонка — на
плотном виде в ту же ширину влезало бы больше знаков, чем названо в имени ступени, и число в
имени перестало бы быть правдой. На сетку садится, потому что ступени кратны её шагу и стоят
в шестнадцать шагов друг от друга: посадка сдвигает край максимум на четверть знака и
схлопнуть ничего не может — в отличие от кегля, где шаг сетки крупнее расстояния между
ступенями.

**Верх ряда — 56 знаков при потолке нормы в 80** (WCAG 2.2, 1.4.8 Visual Presentation, AAA:
«Width is no more than 80 characters or glyphs»; сверено 2026-08-18). Норма даёт потолок, а не
ряд: сам ряд из неё не выводится, но выходить за него не должен — это проверяет проба.

### Границы оси: пол из нормы, потолок — предел поддержки

**Нижняя граница — 0.75**, и она ВЫВЕДЕНА, а не назначена и не взята с рынка. Норма — WCAG 2.2,
2.5.8 Target Size (Minimum), AA: цель не меньше 24×24 CSS-пикселя, то есть 1.5rem. Связывает
она нижнюю ступень контрола: `2.5rem × 0.8 × d = 2rem × d ≥ 1.5rem` → `d ≥ 0.75`.

Вывод сделан **после округления**, потому что в поставку уезжает округлённое значение.
`round(nearest, …)` может увести значение вниз на половину шага — до `0.125rem`. Норму это не
пробивает: округление монотонно, а порог 1.5rem сам лежит на сетке (1.5 = 6 × 0.25), значит всё,
что не ниже порога, остаётся не ниже и после округления. Потеря съедает **запас**: при `d = 0.8`
ступень 1.6rem садится ровно на 1.5rem — на минимум, а не под него.

Почему не 0.6875, хотя формально норму удержало бы и оно: 1.375rem — ровно середина шага, а её
`round(nearest, …)` уводит вверх, до 1.5rem. Тогда норму держала бы сторона округления, а не
геометрия — объявленная высота 22px, поставленная 24px. Пол обязан держаться по обе стороны
округления.

Вторая связывающая норма — читаемость кегля — **числа не даёт, и придумывать его нельзя**:
минимального кегля у WCAG 2.2 нет вовсе (сверено 2026-08-18), а 1.4.4 при `rem`-шкале
выполняется при любой плотности. Строгая из двух — 2.5.8, пол остаётся 0.75.

**Верхняя граница — 1.5, и это предел ПОДДЕРЖКИ, а не требование доступности.** По норме крупнее
не хуже: ни 2.5.8, ни 1.4.4 множителем больше единицы не нарушаются. 1.5 — верх диапазона, на
котором прогоняются пробы, и верх того, что зона обещает; выше значения остаются действительным
CSS, но проверок и обещаний по ним нет.

Обе границы **объявлены, а не зажаты `clamp()`**. Зажать пол значило бы молча подменить число,
которое поставил потребитель; зажать потолок — отнять то, что нормой разрешено.

### Подстраховка `round()`: браузер без неё теряет геометрию, а не портит

**`round()` — Baseline newly available с мая 2024** (все три движка; сверено 2026-08-18 по MDN).
До «widely available» ещё не дошло, и деградация здесь жёсткая: недействительное значение делает
свойство невычислимым, и элемент едет на унаследованном или начальном. Геометрия не ухудшается —
она **исчезает**, а исчезнувшее оформление человек читает как «сломалось».

Поэтому **значение плотной шкалы объявлено дважды, и порядок объявлений — часть решения**
(`PROBEWEB-16`, «Открытый вопрос»; `PROBEWEB-63`):

1. **первым — без округления.** Его берёт браузер, который `round()` не поддерживает, и
   получает дробное, но **живое** значение: произведение семени, множителя и плотности. Ряд при
   этом цел — отношения ступеней сохраняются точно, теряется только посадка на сетку;
2. **вторым, под `@supports`, — то же значение на сетке.** `@supports` специфичности не
   добавляет: побеждает объявление, стоящее **позже**. Переставь блоки местами — подстраховка
   начнёт перебивать сетку у всех, и сетки не станет ни у кого. Это держит проба.

**Что человек видит в браузере без `round()`.** При плотности 1 — ничего: семена и множители
подобраны так, что значение уже лежит на сетке, и оба объявления дают одно и то же число
(отдельная проба). Расхождение появляется только у того, кто **крутил плотность**: `--density:
0.9` даёт интервалы вроде `3.6px` вместо `4px` — ритм чуть «плывёт», соседние элементы,
посчитанные от разных ступеней, перестают попадать друг в друга. Вещь при этом целая и
пользуемая; **без подстраховки** та же ручка обнуляла бы отступы, ширины и высоты контролов до
унаследованных или начальных — то есть разваливала бы вид.

**Пол оси плотности подстраховка не меняет.** `DENSITY_FLOOR = 0.75` выведен ПОСЛЕ округления и
потому строже: без округления запас не съедается, и нижняя ступень контрола остаётся не ниже
минимума нормы при любом множителе из диапазона. Это тоже проба, а не рассуждение.

**Форма проверки — обычное свойство с типом длины, а не кастомное.** `@supports (--x: round(…))`
истинно в любом браузере с поддержкой переменных: кастомное свойство принимает почти любой поток
токенов, и такая проба не значит ничего. `var()` в условии тоже запрещён — объявление с `var()`
считается действительным на разборе. Отсюда `(width: round(nearest, 1rem, 0.25rem))`: та самая
функция, та самая стратегия, тот самый шаг сетки — и никакой соседней возможности.

Перечень подстрахованных шкал **не список, а поле `snap`**: два объявления получает ровно то, что
садится на сетку (`--space`, `--column`, `--control-height`). Кегль в блок `@supports` не попадает
вовсе — он на сетку не садится, подстраховывать нечего.

### Границы ВСЕХ осей — таблицей `AXES`, и «границы нет» тоже ответ

Тому, кто строит панель настройки вида, край значения нужен по каждой оси, а не только по
плотности. Раньше про остальные молчали — и молчание читается как «база не знает, где край»:
панель стенда получила шесть зашитых скруглений вместо ползунка ровно поэтому.

Теперь границы объявлены **значением, а не умолчанием** — `AXES` из `src/axes.ts`, и тот же
перечень уезжает комментарием в `base.css` (тему пишут в CSS, туда за границами и пойдут):

```ts
import { AXES, axisOf } from "@omnifield/probe-web-style";

const density = axisOf("density")!;
density.floor;   // { value: 0.75, kind: "норма", norm: "WCAG 2.2, 2.5.8 …", why: "…" }
axisOf("radius")!.floor;   // { value: null, kind: "границы нет", norm: null, why: "…" }
```

| ось | пол | потолок |
|---|---|---|
| `--density` | `0.75` — **норма** (2.5.8) | `1.5` — предел поддержки |
| `--control-height` | `1.875rem` — **норма** (2.5.8) | границы нет |
| `--radius` | границы нет | практический предел, числом не выражается |
| `--font-size` · `--space` · `--column` · `--border-width` · `--tracking` | границы нет | границы нет |

Читается это так:

- **`kind: "норма"`** — единственный случай, когда нарушение означает несоответствие. Только у
  таких границ заполнено поле `norm` со ссылкой на критерий; это структурное поле, а не текст,
  именно затем, чтобы предел поддержки, объяснённый через норму в свободной фразе, не начали
  соблюдать как требование.
- **`практический предел`** у скругления: радиус больше половины меньшей стороны даёт пилюлю.
  Свойство геометрии, **не требование доступности**, и числом база его назвать не может —
  половина зависит от элемента, а не от токена.
- **`границы нет`** — связывающей нормы не существует, любое значение законно. У кегля это
  проверенный факт: минимального кегля у WCAG 2.2 нет вовсе (сверено 2026-08-18), а 1.4.4
  требует возможности увеличить текст вдвое, а не запрещает мелкий.
- **`continuous: true`** у всех: «правильных» ступеней у базы нет ни у одной оси. Свои три
  ступени плотности потребитель предложить вправе — выдавать их за базовые не может.

**Пол высоты контрола подвижен, и это единственная пара осей, которая перемножается.**
`1.875rem` — порог при плотности 1; на нижней границе плотности порог равен `2.5rem`, то есть
ровно нынешнему семени. Крутить семя и плотность вниз одновременно нельзя: границы не
складываются. Значение выводится из данных шкалы, а не переписано числом.

Полнота таблицы держится пробой: **новая шкала без объявленных границ роняет прогон** — иначе
следующая заведённая шкала молча вернёт то самое молчание, ради выхода из которого таблица и
появилась.

## Прежнего плоского набора нет (`PWEB-61`)

`--background`, `--foreground`, `--card*`, `--popover*`, `--primary*`, `--secondary*`,
`--muted*`, `--accent*`, `--destructive*`, `--input`, `--ring`, `--sidebar-*` — были живы,
выражены через роли и объявлены устаревшими. Ушли вместе с ролями: имя, называющее вид, —
решение скина.

Отдельно про `--sidebar-*`: в комментарии рядом с ними было честно написано «токены
КОМПОНЕНТА, которого в ките нет». Восемь имён под компонент, которого не существует, —
хороший признак того, что уезжало не значение, а чужой дизайн-набор.

## Политика выпусков: вид ломается токенами

**Изменение состава или назначения токенов — ЛОМАЮЩЕЕ изменение** (`PROBEWEB-12`, п. 6).

- добавление токена или изменение состава — **минор** с явной записью в примечаниях;
- удаление токена или переназначение ступени/роли — **мажор**.

Причина: потребитель цепляется за токены так же, как `skin` цепляется за `data-slot`.
Переназначенная ступень ломает чужой вид ровно так же, как переименованный слот. Пока пакет
в `0.x`, ломающее едет минором — это правило semver, а не послабление нашей политики.

## Что осталось на поверхности

Контракта ТЕМЫ здесь больше нет — тема как единица отменена (`PWEB-66`). Осталось то, у чего
есть живой зовущий, и у каждого он назван:

| что | кто зовёт |
|---|---|
| `buildScale`, `buildAlphaScale`, `buildChartScale`, `buildScrim` | `packages/skin/src/seeds.ts` |
| `CONTRAST_PROMISES`, `ScaleMode` | там же и в его пробах |
| `DERIVED_SCALES`, `GRID_STEP`, `ROUND_SUPPORT_TEST`, `DENSITY_TOKEN` | `packages/skin/src/sizes.ts` |
| `contrastRatio`, `AA_TEXT`, `AA_NON_TEXT`, `tryParseColor` | `packages/skin/src/contrast.ts` |
| `BASE_MARKER` | скелет `starter`, эталон, пробы `runtime` |
| `AXES` | зовущего пока нет; оставлены решением — знание нужно тому, кто строит ползунок |

`DERIVED_TOKENS`, `LAYERS`, `FIXED_TOKENS` — перечни имён для контракта и доки; зовущих у них
нет, и это стоит померить отдельным заходом, а не решать заодно.

### Перечень поверхности сторожится (`PWEB-66`)

Пробел нашла мутация архитектора: `export const SHADOWS = {…}`, дописанный в `src/values.ts`,
прошёл зелёным на всех пробах. Решение «фреймворк не везёт готовых значений» не держалось
ничем — перечня экспортов не пинил никто.

**Сторожим поверхность целиком, а не «наборы».** Сторож «готовых значений не отдаём»
потребовал бы определить, что такое готовое значение, то есть перечислить ЗАПРЕЩЁННЫЕ формы —
тени были взяты наугад, вернуться может ряд длительностей, таблица отступов, «рекомендованные»
шрифты. Перечень запрещённого устарел бы на первом же новом наборе; перечень **разрешённого**
не устаревает.

Три пробы, и каждая закрывает то, что не видят другие:

| проба | что ловит |
|---|---|
| собранный вход = перечень значений | новое ЗНАЧЕНИЕ на поверхности, и тихую пропажу имени тоже |
| перечень значений и типов = объявленное в `values.ts` | реэкспорт мимо перечня |
| `values.ts` состоит только из реэкспортов | своё объявление любой формы — типом, интерфейсом, константой |

Третья появилась после замера: набор, объявленный **типом**, проходил две первые — в рантайме
типов нет, а разбор смотрел только блоки `export { … } from`. Форма файла закрывает это разом,
не перечисляя запрещённого.

Замер сторожа: мутация архитектора краснеет, набор типом краснеет, набор интерфейсом краснеет,
реэкспорт мимо перечня краснеет; сторож снят — все проходят снова.

Цена названа: добавить экспорт стало нельзя молча. Этого и добивались — поверхность замерзает
выпуском, и расширение её обязано быть решением, а не побочкой правки.

## Инструменты стилизации — другая поставка

`cn`, `createStyle` и реэкспорт `cva` живут в `@omnifield/probe-web-style-tools` и здесь их
нет (`PWEB-3`). Импорт по привычке даёт `TS2305` — «модуль не экспортирует такого имени», и
это намеренно: подсказка ведёт в другую поставку, а не молча привозит инструменты вместе со
значениями. Держит это гейт (`test/types.test.ts`), а не память.

Разрез считается сделанным не тогда, когда `cn` исчез с поверхности, а когда его зависимости
(`clsx`, `tailwind-merge`, `class-variance-authority`) перестали приезжать вместе со
значениями: пока их привозила одна установка, «инструменты необязательны» было словом. Это
отдельный гейт — `test/pack.test.ts`.

## Почему подпути названы с расширением

Типы для CSS приходят потребителю wildcard-правилом `declare module '*.css' {}` (`vite/client`,
его объявляет `tsconfig` зоны `build` полем `types`). Шаблон сопоставляется с **текстом
спецификатора**, а не с тем, куда он резолвится, — поэтому подпуть без расширения под правило
не попадает, и `tsc` роняет прогон потребителя (`TS2882`). Так было до 0.2.0: подпуть звался
`/css`; он переименован в `/base.css`, алиаса не осталось.

Держат это два гейта в паре: `test/types.test.ts` ставит тарбол в чистую установку и
типизирует оба импорта настоящим `tsc`; `test/pack.test.ts` проверяет, что подпуть правда
резолвится в файл поставки. Второе нужно потому, что шаблон `*.css` покрывает ЛЮБОЕ имя с
таким расширением — зелёный `tsc` сам по себе не доказывает, что файл в тарболе есть.

## Инвариант `base.css`: в листе остался ОДИН СБРОС

Инвариант рос трижды, и каждый раз следующий шаг снимал то, что после предыдущего переставало
иметь основание:

| | что стало запрещено |
|---|---|
| было | ни одного литерального цвета |
| `PWEB-39` | ни одного объявления вида **на документ** |
| `PWEB-61` | ни одного объявления вида **вообще**, включая имена и режим |
| `PWEB-66` | **ничего, кроме сброса**: ни одного кастом-свойства и ни одного значения |
| `PWEB-122` | (не запрет, а первое добавление) — сброс снимает ещё одно решение браузера: нативный вид кнопки |

Реестр в `test/base-css.test.ts` ведётся С ДВУХ СТОРОН: разрешено ровно три свойства —
`appearance`, `box-sizing` и `margin`, — и любое четвёртое краснеет само. Рядом два негатива:
**ни одного кастом-свойства** и **ни одного запасного значения** (`var(--x, …)`).

### `appearance: none` пришёл, и это первая правка листа В ДРУГУЮ сторону (`PWEB-122`)

Три прежних захода (таблица выше) СНИМАЛИ: убирали то, что лист печатал сверх сброса. Здесь
наоборот — в лист ДОПИСАНО правило, которого не было. Довод при этом тот же самый, просто
применённый к решению, которого раньше в перечне не было: `appearance: auto` — это выбор
БРАУЗЕРА, кто рисует кнопку, и сброс существует ровно для снятия таких выборов.

**Найдено живым Chromium** (`tools/live-check/`, PWEB-120 → PWEB-122, 2026-08-26): у каждой
кнопки `item-trigger` гармошки — `appearance: auto` независимо от `data-variant`. Родной вид
браузера (свой фон, своя рамка) рисуется ПОВЕРХ `background: transparent`, который ставит скин,
— поэтому «прозрачно» не прозрачно, и четыре визуальные вариации кита выглядят одинаково, хотя
CSS у них честно разный.

Мутация обязательна и здесь (кадры по `getComputedStyle`, не по хешу):

| | `appearance` кнопки |
|---|---|
| с листом (`button { appearance: none; }`) | `none` |
| мутация: строка снята из поставленного `base.css` | `auto` |

Расхождение — доказательство, что замер различает состояния, а не молчит зелёным всегда. `jsdom`
здесь не отвечает в принципе: UA-умолчание `auto` — не часть каскада, который он умеет вычислять,
а внутреннее правило браузера, поэтому вопрос — строго к живому Chromium.

**Только кнопки.** Свериться с `input`/`select`/`textarea` тем же приёмом — часть ТЗ (`PWEB-122`),
и ответ на сегодня отрицательный: во всём дереве кита нет ни одного места, где скин красит
нативный `<input>`/`<select>`/`<textarea>` НАПРЯМУЮ (`packages/ui`) — checkbox, switch, radio и
слайдер держат родной `<input>` визуально скрытым и рисуют свой вид соседним узлом, а видимые
текстовые поля (`field.tsx`, `number-field.tsx`, `combobox.tsx`) сегодня без рецепта скина вовсе.
Родного вида, который скин перебивал бы, нет — значит и симптома, который лечит `appearance`,
негде показать. Расширять сброс под гипотетический будущий рецепт значило бы вернуть тот же
довод, по которому лист не везёт невостребованных значений (раздел «Почему ушёл и остаток» ниже):
приехало бы всем и молча, а просящего пока нет ни одного. Когда рецепт для видимого нативного
поля появится и покажет тот же дефект — задача заведётся отдельно, с тем же замером.

### Почему ушёл и остаток, хотя он «просто значения»

Значение, объявленное листом, — это значение, которое приехало ВСЕМ и молча: потребитель,
ничего не просивший, получал тридцать кастом-свойств на корне и не мог от них отказаться.
А просивших не осталось: ссылок на них по всему дереву ноль, скин печатает свои сам.

**Запасных значений теперь нет нигде.** `var(--семя, умолчание)` был законным приёмом, пока
лист вёз шкалы: он давал геометрию без палитры. Возить нечего — и приём стал вредным:
запасное значение подменяет отсутствующее похожим и прячет состояние «значения нет», которое
обязано называться.

### Знание осталось, ушла печать — и это проверено мутацией

`DERIVED_SCALES`, `GRID_STEP`, `ROUND_SUPPORT_TEST`, `DENSITY_TOKEN`, `AXES`, `LAYERS` остались
данными на поверхности. Снести их вслед за печатью значило бы сломать соседа **не сборкой, а
видом** — то есть тише всего.

Доказывается это не словами: опустошите `DERIVED_SCALES` — краснеет **семь проб механики
скина**. Данные и печать разделены, а не удалены вместе.

Обязательства, которые касались ПОРЯДКА печати (подстраховка `round()` объявляется первой,
посадка на сетку — второй), переехали туда, где печатают. Здесь осталось то, без чего печатать
нельзя: две разные формы значения на каждую посаженную ступень и условие, по которому между
ними выбирают.

### Маркер приезда базы — ПАРА, а не имя

`BASE_MARKER` был `--control-target-min`. Кастом-свойств не осталось — предъявлять приезд стало
нечем, кроме самого сброса.

```ts
`${BASE_MARKER}:`                                                  // "box-sizing:"
getComputedStyle(el)[BASE_MARKER.property] === BASE_MARKER.value   // база приехала
```

**Почему пара, а не имя.** Свойство без ожидаемого значения — ровно та проверка, которая **врёт
зелёным**: `box-sizing` есть у каждого элемента всегда, и «свойство нашлось» не отличает наш
лист от его отсутствия. Отличает `border-box` против браузерного `content-box` — поэтому
носителем взят он, а не `margin` (у того умолчание тоже отличается, но стоит оно на одном
`body`, а `box-sizing` в сбросе — на всём).

**Взять одно без другого нельзя, и это условие формы.** Экспорт один и он заморожен: две
константы рядом дали бы потребителю выбрать имя и забыть значение, а забытое значение здесь не
неполнота, а тихо соврамший гейт.

**Печатается маркер именем свойства** — так он выглядит в тексте листа, и так его ищет эталон
подстановкой в строку. Это не уловка ради совместимости, а точное описание: в тексте маркер и
есть имя, а проверять живой документ надо парой.

**Второй копии значения в зоне нет:** и лист, и маркер печатаются из одной записи сброса.
Держится обходом исходников — гейт считает ВХОЖДЕНИЯ, а не файлы, потому что замером показано,
что вторая копия заводится ровно там же, где первая.

**Шов с `runtime` остаётся, и он назван.** `checkStyleOrder()` принимает имя кастом-свойства;
на нашем маркере она падает. Починка — принимать эту пару, ради того пара и отдана. Правка в
`runtime` и следом строка в шаблоне `starter`; ни то, ни другое не наше.

### Чем закрыт гейт живым браузером

`jsdom` не рисует ни холста, ни системных элементов — вопрос «выглядит ли страница одинаково»
он молча отвечает зелёным. Замер настоящим Chromium (`tools/live-check/`, кадры по sha256):

| | `color-scheme` | отступ `body` | ширина коробки | кадры при двух настройках системы |
|---|---|---|---|---|
| с листом | `normal` | `0px` | `100` (`border-box`) | **совпали** |
| без листа | `normal` | `8px` | `130` (`content-box`) | **совпали** |

Лист меняет ровно сброс и ничего больше: цвета, фон поля и ответ о режиме одинаковы с ним и
без него.

### Чего гейт НЕ ловит, и это названо

Комментарий, вписанный руками прямо в `WRITTEN_BASE`, ни одна проба не поймает: сверка идёт
против этого же текста, а второй его копии в зоне нет и заводить её нельзя — это ровно те две
правды, против которых написано остальное. Реалистичная форма возврата — печать через
генератор — **ловится**: `generate.test.ts` сверяет порождённое с шапкой и ручной частью
ПОБАЙТОВО, без вырезания комментариев. Замером показано, что версия со стрипом эту форму
пропускала.

### Почему прежней формулировки не хватило (`PWEB-39`)

Из `body` ушли шесть объявлений: фон, цвет текста, начертание, кегль, высота строки, трекинг.
Ни одно из них не было литеральным цветом — они ссылались на роли, — и прежний инвариант их
пропускал.

**Пять из шести НАСЛЕДУЮТСЯ, и в этом всё дело.** База не просто красила документ — она через
наследование одевала кит. Кнопка, которую не одевал никто, получала от нас цвет текста, шрифт,
кегль, высоту строки и трекинг, ничего не спросив. «Нет скина — приложение голое»
(`PROBEWEB-11`) держалось на бумаге.

Замеряется это не рассуждением: голая страница на новом `base.css` показывает начертание
`Times New Roman` и кегль `16px` — умолчания браузера. На прежнем она показывала
`ui-sans-serif, system-ui, …` и нашу ступень, то есть нашу одежду.

Шестое, фон, не наследуется — оно делало другое: объявляло страницу нашей. **Прямое следствие
снятия: страницу теперь не красит никто ни в одной конфигурации, включая тему.** Тема
объявляет только ступени; красил их на `body` этот самый ушедший `background-color`. Кто красит
страницу — отдельный вопрос с отдельным владельцем, и он больше ничем не замаскирован.

### Что осталось адресовано документу

Только **сброс**: `box-sizing: border-box` и `body { margin: 0 }`. Это снятие решений БРАУЗЕРА,
а не внесение своих: ничего не наследуется, ни одно наше значение не приезжает.

Токенов в листе нет ни одного. Токен — это ЗНАЧЕНИЕ, и живёт оно теперь данными, а печатает
его тот, кому оно понадобилось.

### Геометрия больше не приезжает листом

Прежде размерные шкалы несли умолчание прямо в `var(--семя, …)`, и геометрия считалась без
палитры. Листом она больше не приезжает вовсе (`PWEB-66`): печатает её тот, кто её просил.
Дефолт по-прежнему выводится из описания шкалы — второго места, где он записан, нет, — но
подставляет его печатающий, а не мы.

## Чего здесь нет

Осознанные пропуски порта, а не забытое:

- **tailwind-мост** (`@theme inline`, `@apply`, `@custom-variant`) — потребовал бы
  `tailwindcss` у каждого потребителя, а контракт зон его не объявляет.
- **инструменты стилизации** (`cn`, `createStyle`, `cva`) — уехали отдельной необязательной
  поставкой `@omnifield/probe-web-style-tools` (`PWEB-3`), см. раздел выше.
- **цветовая библиотека** (`@radix-ui/colors` и родня) — взята МОДЕЛЬ, а не пакет. Обвес
  ставится в чужие репозитории, и любая наша зависимость становится зависимостью каждого
  потребителя; знание «сколько ступеней и что каждая значит» этим не оплачивается.
- **CSS-анимации компонентов kobalte** (popover/select/accordion) — презентация конкретных
  примитивов, это зона `ui`.
- **статус-механика** (`has-status`) и **`merge`** — первое апп-уровневое, второе плоский
  спред под именем, которое в Solid 2.0 занимает `mergeProps`.

## Разработка

```bash
pnpm install
pnpm run build      # tsc → dist, затем генерация dist/css
pnpm run typecheck
pnpm run test       # build + vitest (dom + node)
```

Машинного pre-commit в репозитории нет: сборку, типы и тесты гоняем руками перед каждым
коммитом.

**Мутационные проверки** — каждая воспроизводится за минуту, и каждая прогонялась. Не
покраснело — гейта нет, есть его имитация.
