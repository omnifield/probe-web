# Пробел: разрешение конфликта одинаковых идентификаторов вклада почти не нормировано

**Вопрос (заказ P1, вопрос 5):** что среда обязана сделать, когда два расширения заявили один и тот же идентификатор команды / пункт меню / точку?

**Ответ: явно нормированного правила разрешения такого конфликта рынок в открытом доступе почти не даёт.** Декларативная сторона (два расширения объявили одинаковый `command`/`menu` id) в изученных источниках не описана как норма «кто выигрывает».

## Что перебрано

- **VS Code** — страницы Contribution Points и Extension Manifest перечисляют, ЧТО можно объявить, но не говорят, что происходит при столкновении одинаковых идентификаторов вклада двух расширений.
- **Eclipse** — модель «extension point / extension» по устройству СОБИРАЕТ все вклады к точке (несколько расширений дополняют одну точку, и все их вклады доступны), то есть «конфликта-победителя» там может не быть вовсе — но первично (help.eclipse.org отдаёт фреймсет) в этот заход не выписано.
- **OSGi** — сервисный реестр допускает несколько сервисов одного интерфейса с ранжированием (`service.ranking`); это не «конфликт», а упорядоченный набор — но к декларативному UI-вкладу прямого отношения не имеет.

## Важно: неподтверждённая формулировка НЕ выписана

Широко цитируется поведение VS Code «повторная регистрация команды с уже существующим идентификатором вызывает ошибку» (`commands.registerCommand`). При сверке в этот заход **подтвердить дословно не удалось**: инструмент предпросмотра выдал такую фразу, но на живой странице API-справочника (`api/references/vscode-api`) в DOM этого текста не оказалось. По правилу фонда (несущее — только дословно, названный пробел лучше правдоподобной замены) фраза сюда НЕ вписана как цитата. Это кандидат на добор: сверить `registerCommand` по актуальному API-справочнику или исходнику типов `vscode.d.ts`.

## Почему это пробел, а не недосмотр

«Конфликт одинаковых идентификаторов» распадается на два разных случая, и рынок их не сводит:
- **декларативный UI-вклад** (меню, команды) — правило разрешения обычно не публикуется; на практике либо порядок регистрации, либо ошибка, но нормой это не закреплено;
- **вклад в точку/реестр** (Eclipse extension point, OSGi service) — там модель СБОРА всех вкладов, а не выбора одного, то есть «конфликта» в смысле «победитель» может не быть.

**Следствие для рамки:** опереться на нормированное правило «что делать при дубле идентификатора вклада» нельзя — его в общем виде нет. Если продукту нужна детерминированная политика (ошибка / приоритет / порядок), её придётся задать самому.

## Не закрыто (добор)

- Дословная сверка `vscode.commands.registerCommand` по `vscode.d.ts` (первоисточник типов), а не по рендеру справочника.
- Первичная выписка модели сбора вкладов Eclipse extension registry (обойти фреймсет help.eclipse.org — например, через исходник документации).
