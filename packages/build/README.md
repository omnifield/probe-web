# @omnifield/probe-web-build

Оснастка сборки probe-web: **фабрика конфига Vite, базовая настройка TypeScript и пресет
vitest**. Три подпутя наружу — и ни строки рантайм-кода.

Зона отделена от `runtime` не ради симметрии: build-инструмент в зависимостях рантайма — это
названный дефект (`kb:PROBEWEB-4`), и здесь он вычищен с обратной стороны — рантайм-кода в
пакете нет, а значит приложение не тащит сборщик в бандл.

## Зачем прятать конфиги

Файлы `vite.config.ts`, `tsconfig.json` и `vitest.config.ts` едут потребителю классом
**`placed-once`**: обвес кладёт их один раз и больше никогда не обновляет. Всё, что окажется
внутри, застынет у него навсегда — версия Vite, набор плагинов, условия разрешения,
`jsxImportSource`. Поэтому внутри остаются три строки, а содержимое живёт здесь и меняется
нашим выпуском.

Ближайший пример, ради которого это и сделано: Solid 2.0 уносит JSX-типы из `solid-js` в
`@solidjs/web` и требует сменить `jsxImportSource`
(фонд `solidJS/sources/solid-2.0-migration.md`, сверено 2026-08-08). Смена — одна строка
**в этом пакете**, а не правка замороженного файла в каждом созданном продукте.

## Поверхность — три подпутя

```ts
// vite.config.ts потребителя
import { defineConfig } from "@omnifield/probe-web-build/vite";
export default defineConfig();

// vitest.config.ts потребителя
import { defineTestConfig } from "@omnifield/probe-web-build/vitest";
export default defineTestConfig();
```

```jsonc
// tsconfig.json потребителя
{
  "extends": "@omnifield/probe-web-build/tsconfig",
  "include": ["src", "vite.config.ts"]
}
```

Всё остальное — внутреннее и ломается свободно. Эти три подпутя — часть замороженной
поверхности выпуска (`kb:PROBEWEB-4`): менять их нельзя без мажора и разговора с architect.

### `/vite`

`defineConfig(): UserConfig` — готовый конфиг с `vite-plugin-solid` внутри. Потребитель не
знает ни про плагин, ни про версию Vite.

#### Дев-цикл: соседи по воркспейсу видны исходниками

Пакеты монорепозитория связаны `workspace:*` (симлинк), но их `exports` ведут в `dist`. Значит
без отдельной меры дев-сервер отдаёт приложению **собранное**: правишь исходник соседа — в
браузере вчерашний код, и вывод о своей правке делаешь по чужому старому (`PWEB-1`).

Поэтому в дев-режиме (`apply: "serve"`, сборки это не касается — собирается ровно то, что уедет
потребителю) конфиг добавляет четыре вещи:

- **алиас «подпуть соседа → файл его исходника»**. Сосед определяется машинно: символическая
  ссылка из `node_modules` ведёт НАРУЖУ из `node_modules`. Пакет из реестра — в том числе наш
  же кит, поставленный потребителю, — остаётся внутри, алиасов для него не возникает вовсе, и
  поставка ведёт себя как прежде. Списка имён нет намеренно: пресет едет и в чужие продукты,
  где набор соседей другой, а список молча отстаёт от дерева;
- **`optimizeDeps.exclude`** на этих же соседей: пребандл сложил бы их копию в кэш, и правка
  исходника перестала бы доезжать до браузера до сброса кэша — то есть вернулась бы ровно та
  беда, ради которой всё это и делается;
- **`server.fs.allow`** на папки найденных соседей: их исходники лежат вне корня приложения, и
  без разрешения дев-сервер отказывается их отдавать. Корень приложения перечислен там же и это
  не избыточность — заданный список отменяет умолчание Vite, и без него сервер отвечает `403`
  на собственный `/src/main.tsx` приложения;
- **`server.host: true`** — слушать все интерфейсы, а не имя `localhost`: оно разрешается в
  `::1`, и до сервера, поднятого в контейнере, не доходят ни браузер с хоста, ни пульт, который
  проверяет живость по `127.0.0.1`.

Подменяются **только модульные цели из `dist`**. Стили и данные оставлены на собранном
намеренно: собранный `css` пакета бывает не копией исходника, а результатом генерации (так
устроен `style`), и подмена отдала бы приложению другое содержимое — молча и без единой ошибки.

Способ выбран **алиасом, а не условием `development` в `exports` пакетов**: оба рыночные (дока
Vite `resolve.conditions`; vitejs/vite discussions #17417, #6684 — сверено 2026-08-19), но
условие в `exports` меняет публикуемую поверхность — цель `./src/...` обязывает класть исходники
в тарбол и отвечать за них перед потребителем. Это отдельное решение о поставке (`PWEB-8`), и
внутрь починки дев-цикла оно не едет. Алиас же целиком внутри оснастки.

**Чего алиас не закрывает.** Конфиг приложения сам импортирует `@omnifield/probe-web-build/vite`,
и его Vite грузит ДО того, как плагин из этого конфига может что-то подменить. Внутри
монорепозитория на свежем клоне это значит: зону `build` надо собрать один раз, иначе дев-сервер
приложения не поднимается вовсе (замерено 2026-08-19 на `apps/reference`). Потребителя из
реестра это не касается — ему `dist` приезжает в поставке.

### `/tsconfig`

Базовый `tsconfig.base.json` файлом пакета. Ключевое поле — `jsxImportSource`; здесь же
`jsx: "preserve"` (трансформ делает Vite, не `tsc`), `moduleResolution: "bundler"` и строгий
набор проверок.

### `/vitest`

`defineTestConfig(): UserConfig` — пресет тест-раннера. Три вещи, без которых тест Solid-
компонента не работает, и все три — **норма доки**, а не наше предпочтение (фонд
`solidJS/sources/solid-docs-testing.md`, сверено 2026-08-08):

- `vite-plugin-solid` в плагинах — он делает JSX-трансформ в раннере;
- **`resolve.conditions: ["development", "browser"]`** — иначе `solid-js/web` разрешится в
  серверную ветку и `render()` упадёт «Client-only API called on the server side»; этим же
  условием плагин дотягивает `solid`, по которому зависимости отдают непреобразованный JSX;
- `environment: "jsdom"` — без документа рендерить некуда;
- **`test.server.deps.inline: [/\.[jt]sx(\?|$)/]`** — трансформировать исходники Solid, где бы
  они ни лежали. Почему это обязательно — ниже.

`@testing-library/jest-dom` пресет не подключает намеренно: `vite-plugin-solid` подхватывает
его сам, если он установлен (та же дока).

#### Условие `solid` — и что из него следует для загрузки зависимостей

Условие `solid` означает «отдай мне **исходник**»: библиотека кладёт в свой `dist` файлы `.jsx`
с неразобранной разметкой, чтобы трансформацию под свою цель применил потребитель. Так
публикуются `@kobalte/core`, `@corvu/utils`, `solid-presence`, `solid-prevent-scroll` и наш
собственный кит `-ui` (снято с дерева 2026-08-18). Включает это условие пресет — в нём и смысл.

Дальше вступает раннер: зависимость он по умолчанию **внешнит** — отдаёт ноде нетронутой
(`server.deps.external` — «files inside `moduleDirectories`», дока vitest, сверено 2026-08-18).
У ноды загрузчика для `.jsx` нет, и проба на компонент кита падает `Unknown file extension
".jsx"` — на файле зависимости, а не на своём коде, поэтому текст ошибки ведёт совсем не туда
(заявка мира `tasker:PROBEWEB-37`).

Поэтому пресет говорит раннеру: то, что разрешилось в исходник Solid, — трансформируй.
**Признак — расширение файла, а не имя пакета:** расширение это свойство самого файла («нода
это исполнить не умеет»), а список имён приходится дописывать на каждой новой транзитивной
зависимости кита и он молча отстаёт. Правило может только превратить отказ в успех: файл с
таким расширением нода не исполнит ни при каких условиях, значит внешнить его всегда неверно.

#### Почему дефект выглядит выборочным — замер 2026-08-18

Отказ ловит не всякий, кто рендерит примитив кита, и это сбивает с толку: `tables` и
`reference` на голом пресете зелёные, а `products/skin` тем же пресетом падает.

Решает **манифест потребителя**, а не форма установки. Замерено на четырёх раскладках (кит из
тарбола реальной папкой и кит симлинком `workspace:*`; `@kobalte/core` рядом с китом и вложенным
в него; потребитель внутри репозитория и вне его):

- пакет, **объявленный** в `dependencies` потребителя, раннер трансформирует — прогон зелёный;
- тот же пакет, приехавший **транзитивно**, раннер отдаёт ноде — `Unknown file extension`.

`tables` и `reference` держат `@kobalte/core` в своих `dependencies` (он им нужен напрямую) и
поэтому дефекта не видят. `products/skin` его не объявляет — и там проба «кит без skin остаётся
голым» лежала с `.skip`, назвав в комментарии ровно эту ошибку. То есть в дереве репозитория
дефект был воспроизведён с самого начала; невоспроизводимым он выглядел из-за случайного
совпадения: те зоны, которые его не видят, объявили транзитивную зависимость кита у себя.

Отсюда форма пробы: `test/kit-consumer.test.ts` ставит кит из тарбола (`pnpm pack`) в
`node_modules` временного потребителя, который объявляет **только кит и Solid**, а
`@kobalte/core` получает вложенным в кит — ровно как мир. Объявить его в манифесте пробы значит
убить пробу, поэтому манифест сверяется отдельным утверждением.

## Зависимости

`vite-plugin-solid` — обычная зависимость: без него конфиг не собрать, и потребитель про него
знать не должен. `vite` и `solid-js` — peer'ы (две копии Solid в дереве ломают реактивность).
`vitest` и `jsdom` — **необязательные** peer'ы: нужны ровно тем, кто зовёт `/vitest`.

## Как это проверяется

- `test/build.test.ts` — **собирает настоящее приложение** (`test/fixture`) конфигом из
  `/vite`, исполняет бандл в JSDOM и утверждает узлы в разметке; там же `tsc` проходит по базе
  из `/tsconfig`. «Конфиг вернулся объектом» ничего не доказывает — доказывает собранная
  страница.
- `test/preset.test.ts` — запускает **отдельный прогон vitest** в тестовом приложении, где
  конфигом стоит наш пресет, и разбирает json-отчёт.
- `test/surface.test.ts` — поверхность перечнем: ровно три подпутя, каждая цель `exports`
  лежит в тарболе `pnpm pack`, исходники и тесты в тарбол не едут.
- `test/dev-source.test.ts` — **настоящий дев-сервер и настоящие HTTP-запросы к нему**, как их
  делает браузер: «в конфиге есть алиас» ничего не доказывает, доказывает отданный файл. Сосед
  `test/fixture-dep` держит подпуть `./built`, у которого собранная пара и исходник отвечают
  разными словами; собранную пару кладёт сама проба, а второй блок сносит её целиком — это и
  есть состояние свежего клона, где `build` ещё не запускали.
- `test/kit-consumer.test.ts` — **пресет глазами мира**: кит `-ui` ставится из тарбола в
  `node_modules` временного потребителя, конфигом там стоит голый `defineTestConfig()`, и в нём
  гоняется render-проба на примитиве кита. Проба сначала сверяет свою же раскладку (ветка `solid`
  несёт непреобразованный JSX, транзитивный peer не объявлен) — иначе она зеленела бы при
  сломанном пресете.

Тестовое приложение подключает пакет как установленный (`workspace:*`), а рядом лежит
`test/fixture-dep` — зависимость, отдающая **непреобразованный JSX** по условию `solid`, как
это делают настоящие solid-библиотеки. Её ветка `default` ведёт в модуль, который падает: без
условия `solid` тест обязан упасть с внятной причиной, а не пройти мимо и ничего не проверить.

## Трейсы

Perf-логгеры молчат по умолчанию; включает глобальный флаг:

```js
globalThis.__PROBE_WEB_BUILD_TRACE__ = true;
```

## Команды

```bash
pnpm run build      # tsc → dist
pnpm run typecheck  # проверка типов пакета
pnpm test           # build + весь набор тестов
```
