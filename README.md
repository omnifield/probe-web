<h2 id="структура">📁 Структура</h2>

```
├─ apps/       🖥️ приложения — витрины и гейты сборки, не библиотеки
├─ backend/    🗄️ службы вокруг фреймворка (пока — presets)
├─ canons/     📜 канон каждой зоны — архитектурные решения и договорённости, не код
├─ packages/   🧱 сам фреймворк: кит, механика скина/сборки, рантайм, оснастка
└─ products/   🚀 продукты поверх фреймворка (сейчас — Windshift)
```

Границы папок — не случайность: `.claude/harness.yaml` задаёт зоны (какая папка чей овнер) и
держит их машиной, а не договорённостью. `canons/<zone>` — где у зоны есть архитектор снаружи
(skin, tables, map, chat, studio) — несёт решения и обоснования; сам код лежит в `apps/`/`packages/`/
`products/` с тем же именем зоны.

<h2 id="базовые-понятия">🗃️ Базовые понятия сущности</h2>

Кит — не единственное место в репозитории, где будут «паспорт» или «анатомия». Любая сущность
фреймворка — компонент кита, отдельная функция, целый движок (`store`, `router`, будущие) —
описывает себя одним и тем же небольшим набором понятий. Смысл термина закрепляется здесь, один
раз на весь репозиторий; у каждой сущности он раскрывается в СВОЁМ контексте (см., например,
паспорт UI-компонента — [`packages/ui/README.md`](./packages/ui/README.md#passport)), но не
переизобретается заново под другим словом с тем же смыслом.

Первые пять понятий — то, что сущность заявляет о себе ДЕКЛАРАТИВНО, данными, а не кодом,
который что-то рисует или считает:

- **Анатомия** — именованный список частей сущности, каждая со своим устойчивым адресом. Нужна,
  чтобы что угодно снаружи (скин, редактор, любой инструмент) могло сослаться на конкретный кусок
  по имени, а не гадать по порядку или структуре.
- **Паспорт** — то, что сущность заявляет о себе как данные: какие у неё части (берутся из
  анатомии), что каждая часть умеет менять на себе (состояния), по какой оси она вообще может
  отличаться видом или поведением (вариант), какие у неё настройки. Машиночитаемый контракт, по
  которому внешние инструменты проверяют, что ничего не забыто.
- **ИО** — контракт данных: что сущность готова принять на входе и что реально отдаёт на выходе.
  Не про то, как это выглядит или что делает внутри — просто форма данных, зафиксированная один
  раз и переиспользуемая всем, что с сущностью соединяется.
- **Настройки** — именованные переключатели и выборы, у каждого из которых есть настоящий
  двойник в самой сущности — не воображаемый список того, что «неплохо бы» уметь.
- **Состояния** — состояния, в которых части сущности реально бывают, каждое с настоящей,
  проверяемой меткой — то, что реально можно поймать (для компонента — настоящий CSS-селектор, не
  выдуманный класс).

Последние два понятия — не декларация, а ДОКАЗАТЕЛЬСТВО, что декларация реально работает:

- **Сборки** — готовые примеры того, как части паспорта реально складываются в рабочую
  композицию через настоящий движок, а не только проходят проверку по отдельности.
- **Рецепт** — конкретное воплощение абстрактного контракта, живущее СНАРУЖИ самой сущности и
  проверяемое на полноту относительно её паспорта. У UI-компонента это визуальный скин; у движка
  та же идея — это его ПЛАГИНЫ: съёмный слой, который сущность не носит в себе, но паспорт
  которого обязан покрывать целиком, тем же способом, каким рецепт компонента обязан адресовать
  каждое заявленное состояние.

<h3 id="доки-сущности">📖 Как это оформляется в доке</h3>

Любая сущность держит свою тройку `README.md`/`FAQ.md`/`ROADMAP.yaml` по одному скелету
(порядок разделов, шапка, стиль — общие), но НАПОЛНЕНИЕ раздела зависит от `genus`, и здесь легко
ошибиться в обе стороны.

> [!WARNING]
> **У каждого `genus` — СВОЙ шаблон, копировать содержание чужого genus нельзя.** `genus: component`
> копирует манеру `packages/ui` (`genus: component`, ниже), `genus: engine` — манеру
> `packages/store`/`packages/assembly` (`genus: engine`), `genus: tooling` — манеру `packages/build`
> (`genus: tooling`, первый). Перед тем как переписывать доку сущности — сверить `genus` в её
> собственной шапке и взять пилот РОВНО этого genus, не соседнего.

- **Шапка** — `🏷️ группа · 🧬 genus · 📦 пакет`. Висит СРАЗУ ПОД заголовком `# H1` пакета, до
  навигации и до любого раздела — не внутри «Главное» и не повторяется там второй раз. `genus`
  называет ВИД сущности (`component` у компонента, `engine` у движка, `tooling` у оснастки без
  рантайм-кода в поставке); `группа` — категория внутри вида, своя таксономия под каждый genus
  (для движков и оснастки ещё не устоялась). У компонента в шапке есть ещё `📐 footprint`
  (визуальный размер на экране) — у движка и у оснастки этого поля НЕТ: безголовой сущности
  нечего измерять.
- **Разделы** — фиксированный порядок, один и тот же для любого genus: Главное → Анатомия →
  Использование → Настройки → Состояния → IO → Сборки → Рецепт → FAQ. Раздел может быть пустым или
  отсутствовать по смыслу (как `entity/io.ts` не заводится у компонента без формы) — это не
  нарушает порядок, остальные разделы не сдвигаются.
- **«Главное» — всегда первым.** Вступительный абзац (что это и зачем) — не висит сам по себе
  перед первым разделом, а составляет СВОЙ раздел, идущий первым всегда, даже когда README
  отдельно синкается страницами в базу знаний (там это тоже отдельная, первая страница, не
  довесок к оглавлению). Бейдж в README стоит под H1, выше навигации, отдельно от раздела
  «Главное». При синке в Windshift страница «Главное» сама по себе и есть аналог «под H1» —
  бейдж едет первой строкой её содержимого, а `description` воркспейса остаётся пустым.
- **Иконка/эмодзи — у каждого раздела, и в самом описании, не только в заголовке.** Голый текст
  без единого визуального якоря читается уныло и хуже сканируется взглядом — эмодзи в заголовке
  раздела (уже есть) и хотя бы один-два по тексту описания (не в каждой строке, к месту).
- **Обоснования — в `FAQ.md`, не в README.** README держит факты и примеры; FAQ — почему так, а не
  иначе, и что уже проверено на практике.
- **Раздел объясняется В КОНТЕКСТЕ этой сущности, не абстрактно.** Не «Анатомия» голым словом — а
  что анатомия значит именно для этого компонента/движка/фичи (у движка без DOM, например, за
  анатомию берутся именованные части/подпути поставки, а не куски разметки; у оснастки без
  рантайм-кода — то же самое, часть = точка входа/подпуть, а не внутренняя логика; «Состояния» у
  неё — режимы, в которых по-разному ведут себя фабрики/плагины, а не рантайм-стейт). Абстрактный
  смысл термина — здесь, в «Базовых понятиях» выше; на месте документации сущности он должен быть
  переведён в её собственные слова, не просто унаследован молча.
- **Никаких номеров/ссылок на тикеты и заявки — ни в README, ни в FAQ, ни в ROADMAP.yaml.**
  `(PWEB-83)`, `«задача WI-257»` и подобное — не аргумент и не объяснение: трекер меняется,
  тикеты закрываются и переименовываются, а читатель дока прав на него может и не иметь вовсе.
  Причина решения пишется своими словами прямо в тексте — так, чтобы понять её было можно, ни разу
  не открыв трекер.
- **В КОДЕ — не проза.** Простыня объяснения рядом с кодом (абзацы «почему сделано так») —
  запрещена. Обоснование живёт в `FAQ.md`, комментарий в коде — максимум короткая пометка и, если
  правда нужно, ссылка на страницу дока. Не «объяснить прямо тут», а «сказать, где объяснено».

Пилоты: [`packages/ui`](./packages/ui/README.md) (`genus: component`),
[`packages/store`](./packages/store/README.md) (`genus: engine`, первый) и
[`packages/build`](./packages/build/README.md) (`genus: tooling`, первый).

<h2 id="пакеты">🧱 Пакеты фреймворка</h2>

| пакет         | назначение                                                                               |
| ------------- | ---------------------------------------------------------------------------------------- |
| `ui`          | примитивы на Ark/Zag — 1-to-1 DOM, ноль стилей по умолчанию, паспорт компонента          |
| `runtime`     | `mount()`, контракт `#root` и механика подключения скина к потребителю                   |
| `skin`        | механика скина — модель, сборка рецепта по частям, адресация из анатомии, порождение CSS |
| `assembly`    | механика сборки — дерево узлов, реестр из паспортов, правки дерева, отрисовка по данным  |
| `style`       | набор значений — токен-контракт, шкалы, построение половин из семени                     |
| `style-tools` | инструменты стилизации — комбинатор классов, реактивная обвязка                          |
| `io`          | универсальный вход/выход данных фреймворка                                               |
| `query`       | данные из сети поверх `@tanstack/solid-query`                                            |
| `router`      | роутинг поверх `@tanstack/solid-router`                                                  |
| `store`       | стейт поверх `@xstate/store`                                                             |
| `build`       | оснастка сборки — фабрика конфига Vite, база TypeScript, пресет vitest                   |
| `lint`        | пресет `eslint-plugin-solid` — канон Solid, выраженный машиной                           |
| `generators`  | генераторы — что штампует шаблон в этом репозитории или держит его в актуальном виде     |

<h2 id="инструменты">🛠️ Инструменты</h2>

- **pnpm workspace** — пакеты ссылаются друг на друга `workspace:*`, не `file:` (снимок) и не
  реестром. Вложенные воркспейсы pnpm не поддерживает — все пакеты объявлены на верхнем уровне
  `pnpm-workspace.yaml`, даже если физически лежат глубже (например `apps/skin/.mcp`).
- **Nx** — `pnpm build|test|lint|typecheck|dev` гоняют соответствующую цель по всем пакетам
  (`nx run-many -t <target> -p '@web-core/*'`). `pnpm graph` — граф зависимостей.
