# @omnifield/probe-web-assembly

Механика сборки: то, чем из объявленных компонентов собирают дерево, правят его и рисуют по
данным. **Одна на два применения** — редактор скинов работает в границах компонента,
конструктор страниц в границах страницы; различие в охвате дерева, а не в устройстве.

Средство, а не решение. Механика не приносит своего вида, своих панелей и своих решений о том,
что должно получиться. Проверка на месте: всё, что отвечает на «чем это сделать», — здесь; всё,
что отвечает на «что именно сделать», — не здесь.

## ⚠️ ПРОЧТИ ПЕРЕД ТЕМ КАК ПИСАТЬ ДЕРЕВО ИЛИ КОМПОНЕНТ РУКАМИ

Это не необязательное чтение. За 2026-08-27 в одной сессии дважды случилось одно и то же: не
свериться с этим разделом раньше, чем писать код, — и в первый раз собрать составную страницу
руками через JSX (`<Workspace><WorkspaceSidebar>…`) вместо дерева-сборки, хотя движок для этого
уже почти дописан; во второй — начать проектировать событийную модель с нуля, хотя рынок (A2UI)
уже решил её лучше, чем черновик с нуля.

**Уточнено 2026-08-28, после того как та же формулировка увела в противоположную сторону ещё
несколько раз подряд (`PWEB-163`/`164`, разбор — страница «Сборка — раскладка, не данные;
компоненты ссылаются друг на друга», workspace 6).** `RenderTree` — законный способ там, где
дерево ДЕЙСТВИТЕЛЬНО данные: показ паспорта ОДНОГО компонента (витрина/редактор) или страница,
чья структура реально приходит JSON'ом (сохраняется, редактируется нетехническим человеком,
едет по сети). Явный тег узла (`genus`/`extra`/`part`) существует ИМЕННО ради этого случая — в
JSON `"button"` и `"Купить"` неразличимы по типу, и тег единственный способ сказать «это ссылка»
против «это значение».

**Для дерева, которое живёт ТОЛЬКО в TypeScript-коде продукта** (не сохраняется, не редактируется
интерфейсом, не путешествует по сети — обычная композиция реальных модулей с фиксированным,
известным на этапе кода составом) — эта механика избыточна, и `PWEB-161` ровно об этом: пять
целых экранов пульта (рельсы, шапка, показ, панель настроек, консоль) оказались НЕ тем случаем,
для которого дерево-объявление того стоит, — там это обычный JSX реальными компонентами кита,
без единого узла-объявления. Тот же урок повторился на виджете «список компонентов»: сборка
`catalog`/`list` с зашитым внутрь `Button` — попытка провести через дерево-объявление то, что
было простой JSX-композицией продукта, только через лишний слой.

**Правило одной фразой:** дерево реально ДАННЫЕ (JSON едет по сети/хранится/редактируется
интерфейсом ИЛИ это доказательство паспорта одного компонента для витрины/редактора) — сюда,
`RenderTree`. Состав известен на этапе кода и никуда не едет — обычный JSX, `RenderTree` не при
чём.

Что механика умеет **сейчас** — всё нижеперечисленное СДЕЛАНО и подтверждено живым `RenderTree`
(не заглушкой), полный сквозной путь проверен на настоящем `<App/>` продукта `products/skin`:

**Исправлено (`PWEB-166`/`172`, 2026-08-28), было здесь «известным изъяном»: `genus: "component"`
как род содержимого — снят совсем.** Контент-лист физически не мог нести настоящий компонент (ни
`props`, ни `children`, ни адреса) — ветка была дохлой и никогда не имела живого потребителя.
`PassportGenus` сегодня — `"text" | "icon"`, без `"component"`.

**Исправлено (`PWEB-166`, 2026-08-28), было здесь «известным пробелом»: ссылка на компонент
ОБЩЕГО реестра, не только приватная карта `extra` владельца.** Узел `{ node: "button", props?,
bind?, on?, children? }` (`PassportAssemblyElement`, `packages/skin/src/passport-assembly.ts`)
ссылается на голое верхнее имя ОБЩЕГО реестра — `registry.components["button"]`, ту же запись,
что использует кто угодно ещё, — резолвером, который уже был здесь (`registry.ts`'s
`readAddress`), без правок. «Своя часть или чужая ссылка» решается сравнением с анатомией
владельца, а не отдельным видом узла (`node.node` — то же поле для обоих случаев, `PWEB-172`).
`extra` (`PWEB-152`) остаётся отдельным, легитимным видом — приватная карта владельца для узлов
БЕЗ адреса анатомии вовсе (скрытый `<input>` чекбокса), не конкурент общей ссылке, а другой
вопрос. Разбор целиком — Windshift, workspace 6, страницы id 111/112.

**Исправлено следом (`PWEB-167`–`172`, тот же день): ссылка вызывает поведение компонента, а не
переопределяет его.** Первая версия ссылки резолвилась ФЛАТОМ — узел-ссылка сам задавал
`children`/`on` резолвленному компоненту, то есть диктовал ему поведение вместо того, чтобы
кормить его данными. `ComponentPassport.selfAssembly` (`PassportSelfAssembly`,
`packages/skin/src/passport-form.ts`) — новое узкое поле рантайм-паспорта: собственное дерево
поведения компонента (кнопка объявляет его в `packages/ui/src/button/entity/passport.ts`).
`RenderNode` в `render.tsx` при узле-ссылке (голый адрес, `parentId !== null`, у компонента
объявлен `selfAssembly`) не рисует свои `on`/`children`, а строит `selfAssembly.tree` ОТДЕЛЬНЫМ
поддеревом (`growSelfAssembly`, `self-assembly.ts` — узкая структурная копия формы, без
`repeat`/`ref`/вложенной ссылки) и рисует его вложенным `RenderTree` с данными = `props` +
резолвленный `bind` узла-ссылки. Терминируется сам: у развёрнутого поддерева корень имеет
`parentId === null`, второй раз `selfAssembly` не триггерится. Ссылка без `selfAssembly` у
компонента продолжает резолвиться старым флат-путём (`PWEB-166`) — оба пути живые, не один
заменил другой.

**НЕ сделано, форма уже выбрана из того же словаря A2UI — не изобретать заново, когда понадобится:**

| Будет | Форма (не менять без веской причины) | Ориентир |
|---|---|---|
| Двусторонний биндинг инпутов (пишет сам, без события на каждую букву) | `ResolvedBinding<T>{value}` / `WritableBinding<T>{value,set}` — литерал/функция только чтение, путь в данных даёт `set`. Ложится на Solid-сигналы почти один в один | [A2UI, `renderers/web_core/src/v0_9/nodes/resolved-binding.ts`](https://github.com/google/A2UI) |
| Вызов клиентской функции по имени вместо `event` | `Action = {functionCall: {call, args}}` — второй вариант того же union, сейчас не реализован | тот же `common-types.ts`, `ActionSchema` |
| Загрузка своих данных (файл, ручка API) вместо заготовленных JSON | НЕ форма A2UI — предмет отдельного решения, когда до этого дойдёт очередь (`PWEB-158`) | — |

Не восстанавливать старый `interactions` (снят при переносе, см. «Что снято» ниже) — он был
привязан к контроллерам чужой архитектуры. Новый слой построен под ЭТУ кодовую базу, поверх
`extras`/`provider`, формой A2UI — подробности и решение целиком в PWEB-151/156/157/160.

**«Дорого таскать дерево по API целиком»** (вопрос user, PWEB-160) — НЕ движковая задача сейчас.
A2UI шлёт структуру и данные раздельными ПОТОКОВЫМИ сообщениями (`updateComponents`/
`updateDataModel`), не всем деревом разом на каждое изменение; у нас та же граница уже есть
(структура/данные разделены, `PWEB-156`) — сборка сегодня TS-код, скомпилированный в бандл, не
сетевая запись. Вопрос станет настоящей задачей, когда/если сборки станут серверными записями —
тогда слать их надо тем же инкрементальным приёмом, не заменой всего дерева.

## Две половины поставки

| подпуть | что отдаёт | тянет ли Solid |
|---|---|---|
| `.` | всё, включая отрисовку `RenderTree` | да |
| `./model` | дерево, реестр, правила вложенности, правки, целостность | **нет** |

Второй подпуть — не украшение: хранилище скинов, проверка сохранённого дерева и сборка на
стороне сервера работают с правилами и не должны тянуть за собой отрисовку. Обещание проверяется
пробой поверхности, а не намерением.

## Что здесь есть

**Дерево — плоская карта с корнем.** Узел адресуется именем, а не путём до него: редактор
берёт узел по ключу, а не обходит дерево.

```ts
{ components: { root: "page", nodes: { page: { id, type, composedInto?, parentId, children, props?, bind?, on?, meta? } } } }
```

`bind`/`on` — узел ссылается на внешние данные и сообщает о своих событиях, оба поля необязательны
и оба разобраны в разделе «ПРОЧТИ ПЕРЕД ТЕМ КАК...» выше (`PWEB-156`/`157`).

`parentId` — обратный ход по дереву; `meta` — то, что нужно редактору и не нужно отрисовке.
Вида у узла нет: он приходит правилами по адресам, а не пропом (см. «Вид не приписывается узлу»).

**Узлов два рода, и второй — содержимое** (`PWEB-83`). Подпись кнопки, текст внутри раздела —
это узел дерева наравне с частью, а не свойство узла:

```ts
{ id: "подпись", genus: "text", value: "Доставка", parentId: "кнопка", children: [] }
```

Опознаётся наличием рода (`isContent`), лежит в ОБЩЕМ списке детей и вставляется тем же
`insertNode`. Из этого сразу два свойства, которых прежде не было: содержимое **сосуществует** с
частями и **упорядочивается** относительно них.

**Реестр складывается из пар поставщика** (`PWEB-85`). Пара — это паспорт вместе с тем, чем
рисуется каждая его часть; отдаёт её тот, кто компоненты поставляет:

```ts
import { kitOf } from "@omnifield/probe-web-ui";
import { admits } from "@omnifield/probe-web-ui/passport";

const registry = createRegistry({
  components: {
    button: kitOf("button"),        // пара: паспорт и части
    accordion: kitOf("accordion"),
  },
  admits,                           // по какому правилу читается объявленное
});
```

Механика не сочиняет ни того, ни другого: перечень допустимого приезжает **из паспортов**, а
решение «пускает ли часть внутрь себя вот это» принимает правило допуска, живущее рядом с формой
паспорта. Почему не здесь — ниже, в разделе про вложенность.

**Карту частей потребитель не переписывает.** Собрать её у себя можно за три строки — и именно
поэтому не должен никто, кроме поставщика: двадцать потребителей напишут двадцать карт, и ни одну
из них никто не сверит с анатомией. Добавит поставщик шестую часть — она останется неодетой у
всех сразу. Расхождение пары с анатомией называет `checkRegistry` (`part-uncharted`,
`part-not-callable`, `part-astray`) — значением, а не броском.

Разница между двумя ответами проходит по тому, есть ли о чём спрашивать дальше: **пробел внутри
пары** — значение (часть неодета, остальное работает), а **значение, которое парой не является**,
— отказ собрать реестр с названным адресом. Второе брошено бы посреди отрисовки, где падение
узла съедает его граница ошибок, и человек увидел бы пустое место вместо причины.

**Кит здесь ни при чём.** Механика знает **форму** пары, а не поставщика: кит стоит в
`devDependencies` и в поставку не едет, что проверяется пробой поверхности. Приедет второй
поставщик — сложится так же.

**Базовая сборка поставщика рисуется как есть** (`PWEB-90`). Паспорт везёт готовое дерево
рабочего экземпляра — у гармошки три раздела, первый раскрыт, `value` у каждого (`PWEB-89`), — и
`RenderTree` поднимает его без переклада: `baseAssemblyOf(passport, address)` отдаёт плоскую
карту с корнем, ту самую форму, которую читает механика. Проверка живёт не здесь, а у того, кто
отрисовывает: зависеть на механику кит не вправе даже пробой — механика уже зависит на кит, и
встречная зависимость замкнула бы граф. Собственных тестов у ЭТОГО пакета сегодня нет (`test/`
снят целиком, `PWEB-124`, «заменено `apps/panel`» — заявление устарело: `apps/panel` тестов тоже
не несёт, ниже отдельным пунктом); живая проверка идёт транзитивно, через тесты пакетов, что
реально зовут `RenderTree`/`baseAssemblyOf` на настоящих компонентах —
`packages/ui/src/button/button.test.tsx`, `packages/ui/src/accordion/accordion.test.tsx`,
`products/skin/src/entities/catalog/model/registry.test.tsx`.

**Адрес узла — через точку, и у каждой части он ОДИН.** `button` и `button.root` указывают на
одно место: узел компонента и есть его корневая часть, и `readAddress` приводит обе записи к
одной. Компонент по адресу берётся по **разобранной части** (`parts[passport.root]`), а не по
строке, — второго пути к корню не существует. `accordion.itemTrigger` — часть; `ui.button` —
компонент в чужом пространстве имён (адрес — ключ пары, имя из паспорта совпадать с ним не
обязано).

**Правки — чистые.** `insertNode`, `removeNode`, `moveNode`, `updateNode` возвращают новое
дерево либо **именованный отказ** (`content-not-admitted`, `into-own-subtree`, `root-locked`,
`content-holds-nothing`, `patch-not-of-node`…). Отказ — значение, а не исключение: недопустимая
правка это нормальный ход событий, и редактор обязан объяснить причину человеку.

**Целостность — `checkTree`.** Изъяны дерева именованы (`root-missing`, `child-missing`,
`orphaned`, `cycle`, `child-shared`, `content-in-props`…) и возвращаются все сразу, а не по
одному за проход.

**Отрисовка — `RenderTree`.** Один и тот же вызов в редакторе (предпросмотр) и у потребителя
(готовая страница): дерево это данные, и второго способа превратить их в вид не существует.
Детей она обходит **однородно**: ветки «либо дети, либо текст» больше нет.

## Содержимое — узел дерева, а не свойство узла

**Это починка дефекта, а не новая возможность** (`PWEB-83`, страница раздела «Паспорт
компонента»).

**Замер.** Паспорт кнопки раздела гармошки объявляет три допущения сразу — `part:itemIndicator`,
`content:text`, `content:icon`, — и правило допуска обе вставки подтверждает. А дерево выражало
**одно из двух**: содержимое ехало пропом `children`, и отрисовка показывала его только у узла
без детей. Появилась вложенная часть — подпись молча пропадала. У кнопки дыра не видна (частей у
неё нет), открылась она на первом составном компоненте.

Вторая причина, независимая: **порядок содержимого относительно частей был невыразим в
принципе** — у пропа места среди детей нет, а «подпись, потом стрелка» это решение автора вида.

**Что сделано.** У узла появился второй род: содержимое с полями `genus` и `value`. Оно лежит в
общем списке детей, вставляется тем же `insertNode` и проверяется тем же правилом допуска —
кандидатом `{ kind: "content", genus }`. Своей проверки под это не заводилось: она была с
`PWEB-24`, не хватало только места в дереве.

**Форма взята, а не придумана** (сверено 2026-08-23): у ProseMirror схема обязана объявить тип
`text` (inline-лист), у Slate текстовый узел это `{ text: … }` без детей, у Lexical — `TextNode`,
в DOM текст это отдельный тип узла в общем списке детей. Везде текст — узел-лист в том же списке,
что и элементы, а значение лежит полем узла. Расходимся в одном: значение названо **родом**, а не
типом `text`, — перечень родов принадлежит паспорту, и механика их не истолковывает.

**Что из этого следует:**

| | |
|---|---|
| содержимое и часть | лежат в одном списке — сосуществуют и упорядочиваются |
| внутрь содержимого | не кладётся ничего: `content-holds-nothing`, и паспорта у него нет — оно опознаётся родом |
| координата | у содержимого её НЕТ: подпись не одевается сама, её одевает часть-владелец |
| признак `data-node` | содержимому не ставится: это текст, а не элемент разметки |
| украшение (`editOverlay`) | содержимому не даётся: обвести его можно было бы только чужой обёрткой внутри компонента кита, а она попала бы в разметку, за которую цепляется скин. Выделять содержимое редактор обязан списком узлов |
| правка подписи | `updateNode(tree, id, { value })` — на месте, без пересоздания узла |

**Прежняя форма не оставлена «на совместимость».** Проп `children` содержимым больше не
считается: отрисовка перекрывает его детьми узла всегда, а `checkTree` называет такое дерево
изъяном `content-in-props`. Два ответа на один вопрос — это ровно то, из-за чего подпись и
терялась; молчаливый запасной путь вернул бы дефект туда, где детей нет.

## Узел несёт композицию

Компонент бывает не только собой: кнопка бывает триггером всплывающего окна, меню, подсказки,
раскрывашки. Это **обычный способ пользоваться** составным компонентом, а не краевой случай — и
без него конструктор страниц не смог бы выразить диалог вообще.

```ts
{ id: "настройки", type: "button", composedInto: "popover.trigger", … }
//                 ↑ вид и адрес           ↑ поведение и состояние
```

**Адрес узла не меняется** — он по-прежнему внутренний компонент, тот, чем вещь является
визуально (решение о композиции, страница «Паспорт компонента»). Рядом появляется указание, во
что узел вставлен; собирает композицию отрисовка.

**Собирает механизмом кита, а не своим.** Внешний компонент зовётся с внутренним в пропе `as` —
ровно так композицию делает сам кит. Отсюда и распределение, которого механика не устраивает
руками: поведение и состояние приходят от внешнего (раскрытость окна приезжает на узел
отдельным атрибутом), адресные атрибуты ставит внутренний.

**Вложенность проверяется дважды, и обе проверки — по тому же правилу допуска:**

| что проверяется | по какой паре |
|---|---|
| место в дереве | владелец ↔ **внешний** адрес: место занимает триггер, а не кнопка |
| сама композиция | **внешний** ↔ внутренний: вставить туда, где внешний не допускает, нельзя |

Внутрь же узел смотрит собственным адресом: содержимое определяет тот, кто рисует, — кнопка
пускает внутрь текст и значок независимо от того, во что она вставлена. Отдельного правила под
это не заведено, различие выражено одной функцией — `outerTypeOf`.

**Обычный узел не платит.** Поля нет — путь отрисовки прежний, ни `as`, ни лишних узлов; это
проверяется пробой, а не заявляется. Композиция меняется только пересозданием узла: `updateNode`
её не трогает — второго способа надеть внешний компонент не заводится.

У составного узла **два адреса**, и неразрешённый запасной вид называет именно тот, который не
нашёлся: «не нашёлся `popover.trigger`» отличается от «не нашлась `button`» ровно тем, что
человек пойдёт чинить.

## Вид не приписывается узлу — узел лишь адресуем

Вид приходит правилами по **двум областям адреса**, и обе становятся стилями одним и тем же
порождением (решение архитектора, страница «Скин»):

```
координата паспорта  →  правило скина    →  действует на ВСЕ узлы с этой координатой
идентификатор узла   →  правка образца   →  действует на ОДИН узел
```

**Карта стилей на узле снята** (`PWEB-27`). Три причины, каждой достаточно: она адресована
идентификатором, а не координатой — то есть по определению не скин; она плоская карта свойств —
ни состояний, ни вариаций, ни пересечений, рецептом быть не может; она приезжала **пропом**, а
кит безголовый и такого пропа не имеет. Встроенный стиль вдобавок перебивает любой скин: место,
поправленное в конструкторе, перестало бы одеваться навсегда.

**Взамен механика ставит на узел признак** — `data-node` с именем узла:

```html
<button data-scope="button" data-part="root" data-node="сохранить">Сохранить</button>
       └── координата паспорта ──────────┘  └── идентификатор узла ──┘
```

Признак ставит именно механика. Не потребитель — он о дереве не знает. Не редактор — тогда это
была бы его самодеятельность, и у двух редакторов она разошлась бы. Без признака вторая область
адреса существовала бы в записи и не существовала бы в разметке.

Признак ставится **после** пропов узла: перебить его собственным пропом нельзя, иначе правило,
адресующее узел, промахнулось бы молча.

Две вещи, которые механика при этом **не** решает и решать не должна:

- **вес правила.** Координата даёт две единицы (`[data-scope][data-part]`), признак — одну, то
  есть скин перебьёт правку образца, хотя нужно наоборот. Решается слоями или порядком в **том
  же порождении** — механика даёт зацепку, а не каскад;
- **разрез вывода.** Отдать отдельно скиновую часть и отдельно правки образца обязан генератор:
  иначе правки утекут в файл скина, и приложение получит вид, привязанный к идентификаторам
  чужого стенда.

Признак доезжает до разметки ровно потому, что **кит прозрачен** — произвольные пропы он
форвардит на свой узел. Это чужое обязательство, и проверяется оно живым китом транзитивно
(`packages/ui/src/button/button.test.tsx` монтирует настоящую кнопку и смотрит, что на узле стоят
обе стороны адреса — координата кита и признак механики), а не собственной пробой этого пакета —
своих тестов у него сегодня нет, см. пробел ниже.

## Что механика даёт скину

Скин адресует не узлы, а координаты, и мост между двумя адресациями — часть работы механики
(`PWEB-27`). Механика отдаёт **паспортную половину** координаты и не изображает остального:
состояние и вариация в дереве не живут вовсе, а полный адрес правила (`SkinCoordinate`) собирает
с живого узла разметки читатель паспорта под вид, живущий рядом с формой.

Имена разведены намеренно: у кита — `coordinateOf(узел, lookup)`, здесь — `coordinateOfType`
по адресу узла в дереве. Обе уедут в один редактор, и одноимённые функции с разным предметом
там пришлось бы различать по памяти.

**Координата узла и кто её делит.**

```ts
coordinateOfType(registry, "accordion.item") // { component: "accordion", part: "item", address: … }
nodesSharingCoordinate(tree, registry, "в1") // ["в2"] — оденется вместе с ним
nodesByCoordinate(tree, registry)            // вся раскладка: координата → узлы
```

У гармошки три вкладки — три узла и одна координата: человек красит одну, вид получают все три.
Механика этого не запрещает (запрещать нечего — так и устроен скин), но обязана **показать**,
иначе связь открывается человеку после покраски. Пустой перечень значит «узел единственный со
своей координатой», `undefined` — «узла нет или его адрес неизвестен»; разница показывается
по-разному, поэтому и различается.

**Образец компонента** — дерево его частей, порождённое из паспорта:

```ts
sketchOf(registry, "accordion")
// accordion → item → itemTrigger, itemContent
```

Чтобы одеть гармошку, её надо сперва собрать. Без общего средства каждый редактор собрал бы
скелет по-своему, и два редактора одели бы разные деревья одного компонента, будучи оба уверены,
что одевают компонент.

Состав образца — это `accepts` частей, в порядке объявления. Содержимое потребителя в образец
**не** кладётся: род говорит, что сюда можно положить текст или значок, но не говорит, что это
нужно сделать — положи механика туда подпись, она решила бы за человека, что у кнопки есть
текст. Часть, допускающая саму себя (вложенное меню, дерево), разворачивается один раз: глубину
выбирает человек.

Образец законен по правилам самой механики — это проверяется пробой: `checkTree` не находит
изъянов, а каждый его узел допустим внутри своего владельца.

**Возможные предки** — обратным чтением допуска, см. «Читается в обе стороны» ниже.

## Откуда это перенесено

Это **перенос, а не написание с нуля**. Источник — старый репозиторий `egor6-66/capsuleTech`,
пакет `packages/web/runtime/renderer` (форма схемы — в соседнем `runtime/contract/src/schema.ts`):

```
src/types.ts      98 строк   — модель узла, реестр, режимы, слоты запасного вида
src/resolve.ts    46 строк   — разрешение адреса через точку, с памятью на реестр
src/renderer.tsx 601 строка  — отрисовка
src/__tests__/  1357 строк   — пробы
```

Перенесено то, что решает нашу задачу. Остальное снято — с обоснованием, ниже.

### Четыре решения перенесены ВМЕСТЕ С ПРИЧИНАМИ

Они оплачены опытом, и переоткрывать их незачем:

1. **`createComponent` напрямую, а не `<Dynamic>`.** `<Dynamic>` оборачивает вызов компонента в
   `createMemo + untrack` — лишний слой вычисления на каждом узле. В источнике это вскрылось
   больно: обёртка рвала цепочку контекстов. Той причины у нас больше нет (ушла вместе с
   прежней архитектурой), но осталась первая: узлов в дереве редактора сотни.
2. **Явный запасной вид на неразрешённый адрес.** Молчание в редакторе неотличимо от «узел есть,
   просто пустой» — человек ищет ошибку вёрстки вместо опечатки в адресе.
3. **Изоляция упавшего узла от соседей.** Граница ошибок — на каждый узел. В редакторе половина
   дерева заведомо недособрана, и одна ошибка, гасящая всё, делает редактор непригодным ровно
   тогда, когда он нужнее всего.
4. **`editOverlay` — отдельная ось, а не новый режим.** Слот украшения на каждом узле, куда
   хозяин рисует обводку и ручки. Не задан — путь отрисовки не меняется вовсе.

Плюс мелочь, которая находится только опытом: обёртка узла, не принимающего содержимое,
использует `display:block`, а **не** `display:contents`. Элемент с `display:contents` собственного
бокса не создаёт, `position:relative` на нём игнорируется, и украшение растянулось бы по
родителю. Проба на это перенесена вместе с решением.

## Что снято при переносе и почему

Через полгода этот раздел — единственное, что отличает «убрали осознанно» от «забыли».

| снято | почему |
|---|---|
| **`interactions` целиком** (`IInteraction`, индекс по узлам, цепочка обёрток, `activeInteractions`) | привязка поведения к поддереву ссылками на «контроллеры» и «фичи» прежней архитектуры. У нас такой архитектуры нет, а пустое поле в поставке выглядит обещанием |
| **режим `full`** | в источнике он объявлен и **не реализован**. Переносить объявление нереализованного значит переносить враньё |
| **шкала режимов `RenderMode` целиком** | после снятия `interactions` в ней оставалось одно значение (`static`). Ось с единственным значением — не ось |
| **маркер `__capsuleKind`** и сверка вида обёртки | часть снятого `interactions`: сверял `kind` обёртки, которых больше нет |
| **подпуть `./capsule`** — манифест регистрации пакета в прежнем ядре | объявлял отрисовку как «компонент слоя Widget» чужой архитектуры и был единственным местом, тянувшим `@capsuletech/web-core`. Архитектуры нет — регистрировать не в чем |
| **зависимости на прежнее ядро** (`@capsuletech/web-contract`, `@capsuletech/web-core`) | проверено по коду, а не по описанию: сама отрисовка импортировала только Solid, свой разрешатель и свои типы. Первая зависимость держала форму схемы (переехала сюда своим файлом), вторая — снятый подпуть `./capsule`. Обратных реэкспортов «для совместимости» не заведено |
| **жёстко вписанный перечень void-адресов** (`VOID_NODE_TYPES`: `ui.Input`, `ui.Separator`, `ui.Image`…) | это были **собственные правила механики**: перечень знал имена чужих компонентов и устаревал на первом же новом. Тот же вопрос теперь задаётся паспорту |
| **карта стилей на узле** (`styles` у узла, `NewNode`, `NodePatch`) | снята уже после переноса (`PWEB-27`): не скин (адрес по идентификатору), не рецепт (плоская карта свойств) и не проп кита (он безголовый). Подробности — разделом выше |
| **рекурсивная карта компонентов и разрешатель адреса** (`ComponentMap`, `resolveAddress` с памятью на реестр) | снято `PWEB-85`: карту складывал ПОТРЕБИТЕЛЬ, и её никто не сверял с анатомией; корень при этом оказывался адресуемым дважды — голым именем и веткой по тому же ключу. Реестр складывается из пар поставщика, часть берётся по имени, спускаться по вложенным объектам стало некуда. Память разрешений ушла вместе со спуском: взятие по ключу кешировать нечем |
| **содержимое в пропах узла** (`props.children` как текст листа и ветка «либо дети, либо текст» в отрисовке) | снято `PWEB-83`: паспорт объявлял часть и содержимое в одной части одновременно, а дерево выражало одно из двух — подпись молча терялась. Содержимое стало УЗЛОМ (разделом выше). Прежняя форма не оставлена запасным путём: `checkTree` называет её изъяном `content-in-props` |
| **предупреждения о дефектах дерева в консоль** | проверки остались, но стали **значением** (`checkTree`): консоль читает человек в момент запуска, а редактору нужно показать изъян в своём окне, хранилищу — отказаться сохранить, пробе — проверить именно тот изъян |

Переименования при переносе (форма та же, имена наши): `ISchema` → `AssemblyTree`,
`IEditorNode` → `AssemblyNode`, `Renderer` → `RenderTree`. Карта компонентов источника
(`Registry` → `ComponentMap`) и её разрешатель (`resolvePath` → `resolveAddress`) прожили у нас
до `PWEB-85` и сняты — строкой выше сказано, почему.

## Вложенность: правила читаются из паспорта, своих механика не заводит

Уровень один. Часть компонента и есть вложенный компонент, увиденный с другой стороны: у Ark
вкладка гармошки — и часть гармошки, и самостоятельный компонент. Значит и дерево одно, и
правило одно.

Паспорт несёт правило вложенности сам (`PWEB-24`, форма живёт в ките; форма допуска слита в один
вид `PWEB-166`–`172`, 2026-08-28 — было три: `part`/`extra`/`component`, стало одно):

```ts
accepts?: readonly (
  | { kind: "component"; genus?: PassportComponentGenus; name?: string }
  | { kind: "content"; genus: PassportGenus }
)[]
genus: "component" | "icon"   // PassportComponentGenus — чем компонент является, когда его
                               // кладут внутрь чужого узла ЦЕЛИКОМ; не то же самое, что
                               // PassportGenus ("text"|"icon") — род ЛИСТА содержимого
```

Где резолвится (своя часть анатомии / приватный `extras` владельца / общий реестр) — забота
адресации (`baseAssemblyOf`/`checkAssembly` в `packages/skin`, `nesting.ts` здесь), не самого
допуска: `{kind:"component"}` говорит только «сюда можно положить компонент», иногда с
уточнением по `genus`/`name`, а какая из трёх карт его найдёт — вопрос отдельный. Несколько
разрешённых значений — несколько записей в `accepts`, не массив на одном поле.

Три состояния поля, и все три разные: **не объявлено** — часть не запрещает ничего; **пустой
перечень** — не пускает ничего; **перечень** — допустимо ровно перечисленное.

**Решение принимает не механика.** Правило допуска (`admits`) живёт рядом с формой паспорта, и
там же записано, почему: правило одно на всех читателей, а написанное вторым читателем
разъезжается с написанным первым молча — обе стороны остаются зелёными. Механика подчиняется
буквально: своего правила не пишет, а **принимает его вместе с паспортами** (третий вход
`createRegistry`). Знание об иерархии родов — что значок подходит под место «любой компонент», а
обратное неверно — остаётся в одном месте, и это место не здесь.

Работа механики — поставить правилу верный вопрос: перевести адрес узла в кандидата (часть
своего компонента либо содержимое рода), найти часть-владельца и назвать отказ так, чтобы
редактор мог объяснить его человеку.

### Читается в обе стороны

Вперёд — `canContain` / `canAdmit` / `allowedInside`: что допустимо внутри узла. Назад —
`possibleOwnersOf` / `ownersAdmitting`: какие части пускают внутрь себя вот это.

Обратный ход нужен не механике сборки, а **скину**: адрес правила скина имеет поле «предок» —
часть-владелец и её состояние, — и перечислить его нечем, кроме этого хода. Без него редактор
предлагал бы предков наугад, то есть вернулся бы к свободному селектору, от которого ушли.

```ts
possibleOwnersOf(registry, "accordion.itemTrigger")
// [{ address: "accordion.item", component: "accordion", part: "item" }]

possibleOwnersOf(registry, "icon")   // компонент опознают родом — ищем по всему реестру
// [{ address: "button", … }, { address: "layout", … }, …]
```

Решение по каждой паре принимает **то же самое** правило допуска, что и ход вперёд: второго
правила для обратного чтения не заведено, иначе «допустимо внутри» и «возможный предок»
разъехались бы, и редактор предлагал бы вложение, которое сам же отвергнет. Проба проверяет
именно это — на каждом найденном владельце ход вперёд обязан сказать «допустимо».

Часть ищет владельцев только среди частей своего компонента (часть живёт внутри своего
компонента и в чужой попадает лишь вместе с ним); компонент — по всему реестру, потому что
приходит содержимым и опознаётся родом. Состояния найденной части механика не отдаёт: они
адресуют вид, и их читает читатель паспорта под вид, живущий рядом с формой.

### Что было узким местом и чем закрыто

На момент постановки задачи паспорт умел сказать «пускает содержимое» и не умел сказать «какое
именно»: записать «внутрь кнопки только текст или значок» было нечем, и механике предписывалось
проверять то, что паспорт умеет, не подменяя недостающее догадкой.

Зона `ui` закрыла это в той же ветке (`PWEB-24`): появились `accepts` и `genus`. Механика
работает уже с новой формой, и «кнопка внутрь кнопки» отвергается по-настоящему, а не остаётся
предупреждением в документации.

## Что механика НЕ читает из паспорта

Состояния части, назначения, ось вариаций. Всё это адресует **вид**, а вид — предмет скина и
редактора. В `passport-read.ts` объявлена самая узкая запись читаемого; совпадение с настоящей
формой стережёт машина — проба берёт поставляемый паспорт кнопки и настоящее правило допуска из
кита (кит стоит в `devDependencies`, в поставку не едет).

## Совместимость с A2UI

A2UI (Google) — стандарт формата, не библиотека: рендерера на Solid у него нет, поэтому как
поставкой воспользоваться нечем, а как ориентиром — обязательно, и не только для формы дерева
(было так с переноса), но и для формы данных/событий (`PWEB-151`/`156`/`157`, решение 2026-08-27
— ресёрч рынка перед тем, как проектировать своё, нашёл готовое и более продуманное). Обе формы —
плоская карта с корнем, расхождение не структурное:

| A2UI | здесь | |
|---|---|---|
| `root` | `components.root` | одно и то же |
| `elements` | `components.nodes` | одно и то же |
| `type`, `props`, `children` | `type`, `props`, `children` | один в один |
| — | `parentId` | выводится обходом; у нас хранится ради обратного хода |
| — | `meta` | необязательная добавка |
| — | узел содержимого (`genus` + `value`) | наш второй род узла: у элемента новых обязательных полей не появилось, поэтому элемент читается по-прежнему один в один |
| `DynamicString`/`DynamicValue` (`{path}`, JSON Pointer) | `DynamicValue` (`{path}`) — `PassportAssemblyContent.value` | форма один в один, урезана до литерала и пути (без `call`) |
| — (у A2UI это тоже `DynamicValue`, просто на прочих пропах) | `bind?: Record<имя, путь>` — ОТДЕЛЬНОЕ поле, не смешано со значением `props` | расхождение НАМЕРЕННОЕ: у A2UI каждый проп каждого компонента типизирован заранее (закрытый каталог), у нас `props` — открытый мешок, и различать «это литерал» от «это путь» по форме значения было бы неоднозначно на открытом наборе пропов |
| `ChildList` (`{componentId, path}`-шаблон) | `PassportAssemblyRepeat` (`{repeat, template}`) | форма один в один — «размножь этот один узел по длине массива» |
| `Action` (`{event: {name, context}}`) | `DispatchAction` (то же самое) | форма один в один; `functionCall`-вариант союза НЕ завезён |
| `A2uiClientActionSchema` (`{name, surfaceId, sourceComponentId, timestamp, context}`) | `DispatchedEvent` (`{name, nodeId, address, timestamp, context}`) | `surfaceId` не заведён — `RenderTree` и есть поверхность, вызывающий уже знает, какой вызов слушает; `sourceComponentId`→`nodeId`+`address` — у нас узел и адрес разные вещи, там одна |
| компоненты — плоская карта `id → {type, properties}`, «ребёнок» — просто СВОЙСТВО со ссылкой на чужой id, граф, не дерево (`state/component-model.ts`, `surface-components-model.ts`) | `PassportAssemblyRef` (`{ref: "имя"}`) | расхождение НАМЕРЕННОЕ: у нас `RenderTree` обходит настоящее дерево (`parentId` — одно поле), а не граф — ссылка не общий узел с двумя родителями, она разворачивается в СВОИ узлы на каждой площадке (`PWEB-160`) |

Узел содержимого опознаётся **наличием** рода, а не признаком у каждого узла, — ровно ради этой
строки: заведи мы у элемента обязательное поле «я не содержимое», прямое чтение чужой формы
кончилось бы на первом же узле.

## Трасса

Замеры включает потребитель, а не сборка:

```js
globalThis.__PROBE_WEB_ASSEMBLY_TRACE__ = true;
```

Пишутся сборка каждого узла, неразрешённые адреса и изъяны целостности (каждый — один раз).
Выключенная трасса не трогает часы: замер на каждый узел дерева сам стал бы тем, что он измеряет.
Автоопределение по режиму сборщика (`import.meta.env.DEV`) не используется — механика приезжает
потребителю зависимостью, и подстановку в файлы из `node_modules` сборщик не делает.

## Открытые вопросы (не решаются в этой зоне)

- **Дом формы паспорта.** Форма живёт в ките, потому что там выписан первый паспорт; механика —
  её второй читатель, и зависеть в поставке на кит она не вправе. Нейтральный дом — cross-zone
  решение architect. Пока форма читается структурно, а совпадение проверяется пробой.
