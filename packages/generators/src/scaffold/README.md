# scaffold

Черновик концепции, проговаривается с user по шагам (2026-09-01) — ЕЩЁ НЕ РЕАЛИЗОВАНО. Каждый
раздел ниже — подтверждённый шаг обсуждения, не мои домыслы вперёд. Дописывается по ходу.

## Что это

Способность создать НОВЫЙ файл по шаблону — не пересборка существующего (это уже умеют
`AggregatePlugin`/`PerEntryPlugin` из `../engine`), а генерация с нуля, как `nx generate`
создаёт новый компонент.

## Блоки и теги — только адресация

Шаблон размечен на блоки. Каждый блок несёт тег.

Тег — это ТОЛЬКО адресация: «вот этот кусок текста — блок X». Работает одинаково в ЛЮБОМ файле
(markdown, TypeScript, что угодно) — тегу всё равно, что внутри блока, его дело — дать этот кусок
вычленить.

## Парсер — по типу файла, не по тегу

Тег не знает, КАК читать/писать содержимое блока — это знает ПАРСЕР, привязанный к ТИПУ ФАЙЛА:
`.ts` → TS-парсер (кандидат — `ts-morph`, см. «Ресёрч» ниже), `.md` → свой парсер под markdown,
и т.д. Тег и парсер — разные оси: тег отвечает «какой это блок», тип файла — «каким инструментом
его читать/писать».

«Свободный» блок (человек пишет прозу без структуры) — не отдельная механика, а частный случай:
парсер такого блока просто ничего не вытаскивает, отдаёт текст как есть (тождество).

## Тег — просто строка, типу файла всё равно

Поисковику тегов не важно, TS это, Python или обычный текст — он ищет по двум заданным строкам,
и всё. Отдельного «формата маркера под тип файла» не нужно.

## Маркер ставит `write` при генерации, и это опционально

Тег в файле появляется НЕ отдельным шагом — его ставит сам `write`, когда генерирует файл по
шаблону. Разметка блока — опциональна: не всякому месту в файле нужна повторная читаемость. Нет
тега — нет и `read` для этого места, это нормально, не особый случай.

## Инструмент тегов и парсер — разделены строго

Инструмент тегов ТОЛЬКО извлекает нужный блок (или блоки) текстом и отдаёт парсеру — не лезет в
то, как этот текст устроен. Парсер ТОЛЬКО парсит переданный ему текст — не ищет по тегам сам,
не знает про маркеры вообще.

(На будущее, не сейчас: возможны связи НА УРОВНЕ ТЕГОВ — инструмент тегов сможет собрать несколько
блоков сразу и отдать их парсеру одним куском. Это расширение извлечения, парсера не касается.)

## `write` и `read` — два независимых инструмента, не одна операция

`write` создаёт файл по шаблону. `read` вытаскивает данные из файла по тегу/схеме. Это РАЗНЫЕ
инструменты, не одна пара «записал-перечитал» одного и того же файла.

`read` не работает в вакууме — его кто-то вызвал, и этот вызывающий код получает данные и решает,
что дальше. Файл не обновляет сам себя. Пример цепочки: `write` создал файл по шаблону → человек
заполнил размеченные блоки своими данными → `read` вытащил эти данные → вызывающий код передал их
в `write` ещё раз, но уже для ДРУГОГО файла (например, README). Обычная передача данных по цепочке,
ничего внутри `read`/`write` не знает про эту цепочку целиком.

## Ресёрч: `ts-morph` как кандидат на TS-парсер

- `node.getStructure()` — из существующего узла AST в обычный JS-объект (чтение).
- `node.set(structure)` / `addX(structure)` — из такого же объекта обратно в узел (запись/правка
  существующего файла).
- `printStructure(structure)` — из объекта сразу в текст, без существующего файла (сценарий
  «создать новый файл с нуля»).
- Побочный эффект: раз это настоящий TS-синтаксис, сам TypeScript уже не даст вписать массив там,
  где ждут строку — валидатор писать не нужно.
- Ограничение: работает только для TS/JS. Для markdown (README, проза) нужен свой парсер —
  `ts-morph` его не заменяет, он один из парсеров под конкретный тип файла.
