# ❓ FAQ — грабли, на которые уже наступили

Не документация возможностей (та — в `README.md`) и не план (тот — в `ROADMAP.yaml`). Конкретные
ловушки движка/Solid/skin-механики, каждая — по факту, после того как реально наступили на неё.

## Сборки — `node`, не `part`

`playground/assemblies/*.ts`'s `tree` использует ключ `node` для имени части
(`{ node: "root", children: [{ node: "axis", ... }] }`). Референс в `products/diagrams` (откуда
портировался `axis`) использовал `part` — устаревшее имя поля, актуальный тип уже сменился на
`node` к моменту переноса в кит. Смотреть на актуальный тип (`table/playground/assemblies/basic.ts`
как живой пример), не копировать имя поля из референса вслепую.

## `props.children` через `{...dropAddress(rest)}` — реально работает, не требует ручного рендера

`DiagramRoot` не деструктурирует `children` отдельно — `splitProps(props, ["width", "height"])`'s
`rest` несёт `children` дальше, и `<svg {...dropAddress(rest)} .../>` рендерит их по-настоящему:
Solid's спред-раннер обрабатывает ключ `children` в объекте спреда так же, как явный JSX-children,
даже на нативном элементе. Тот же приём уже держит `grid`'s `Grid` (`<Polymorphic as="div" {...rest}
{...address} />`, без единого явного упоминания `children`). Не нужно заводить `local.children`+
явный рендер, как у `table`'s `TableRoot` — там это render-prop (функция), другая категория, не
плейн JSX-вложенность.

## `RenderTree`/сборки требуют реальной `parts`-карты в реестре теста

`createRegistry({ components: { diagram: { passport: ..., parts: {} } } })` с пустой `parts` не
падает явно — просто ничего не рисует (0 узлов, включая `root`). Нужна настоящая карта из
`kit.parts` (`import { kit as diagramKit } from "../components/index.js"`), не заглушка — та же
ошибка, что легко скопировать по инерции из чужого теста, не заметив разницы.

## `color` на декоративной SVG-линии — всё равно проверяется как «краска», не заливка

`grid`'s линии рисуются через `stroke="currentColor"` (та же схема, что `axis`), и приглушённый
цвет для них — интуитивно ступень «заливки» (`--neutral-4`, светлая, для фонов). `skinGaps`
отказывает: `step-purpose-mismatch` — свойство `color` семантически всегда «краска» (текст/иконка,
контрастный класс токенов), какой бы DOM-элемент ни читал `currentColor` дальше по цепочке. Кит не
смотрит, что именно красится — только на CSS-свойство. Фикс — ink-токен (`--neutral-11`, тот же,
что у `axis`) + `opacity` для приглушения, не смена ступени шкалы. Та же грабля уже описана в
`table/FAQ.md` — это второй, независимый случай на неё, не совпадение.

## Проп `x`/`y` на компоненте, рисующем `<path>`/`<line>` — конфликтует с одноимённым SVG-атрибутом

`DiagramLine`'s `x`/`y` — аксессоры данных (`(datum: T) => number`), не координаты. `<path>` сам по
себе таких атрибутов не несёт, но общий тип `JSX.SvgSVGAttributes<SVGPathElement>` в Solid делит
атрибуты между разными SVG-элементами не по одному интерфейсу на тег — `x`/`y` там уже объявлены
(они реальны у `<rect>`/`<circle>`/`<text>` и т.п.). Без явного `Omit<..., "x" | "y">` компонентный
проп и унаследованный атрибут сливаются в пересечение типов, которое ничему не удовлетворяет — `tsc`
падает на месте использования, не на объявлении типа. Проверять `Omit`-список на пересечение с
именами будущих пропов заранее, не только `"children"`/`"d"`. Повторилось на `bar` (`x`/`y` тоже
аксессоры, `<g>` тоже несёт унаследованные `x`/`y`) — и снова тихо: `tsc` на самом файле компонента
прошёл чисто, ошибка всплыла только там, где проп реально ПЕРЕДАЛИ функцией (тест). Проверять
`Omit`-список сразу при объявлении пропа с именем `x`/`y`/`width`/`height`/… — не полагаться на то,
что «раз файл компонента прошёл tsc, конфликта нет».

## `solid/reactivity` на замыканиях, переданных СТОРОННЕЙ функции (не только на bare arrow в JSX)

`shapeLine<T>().x((datum) => local.xScale!(local.x(datum)))` — чтение `local.xScale`/`local.x`
ВНУТРИ замыкания, переданного `d3-shape`'s билдеру, ловит тот же предупреждение, что раньше поймал
`tree-view`'s `<Context.Provider value={() => local.activeValue}>` (см. `table/FAQ.md`'s аналог для
другого случая) — линтер не видит, что замыкание вызывается синхронно внутри уже отслеживаемого
JSX-выражения (`d={d()}`), и трактует чтение пропа глубоко вложенным. Фикс — прочитать реактивные
поля в ПЛОСКИЕ локальные константы ДО того, как их захватят вложенные замыкания
(`const xScale = local.xScale;` и т.д.), не заворачивать в `createMemo` (здесь не нужен отдельный
computed — вызов и так происходит внутри одного тика JSX-чтения).

## `axis`/`grid` умеют ТОЛЬКО `ScaleLinear` — категориальную (`scaleBand`) ось строить пока нечем

`DiagramAxis`/`DiagramGrid` вызывают `scale.ticks(...)` — метода, которого у `ScaleBand` попросту
нет (у band-шкалы есть `domain()`/`bandwidth()`/`step()`, но не `ticks()`). `bar` (единственная
серия, которой категориальная ось вообще нужна) использует `scaleBand` для своей `xScale`, но
подписанную ось под неё строить не из чего — сборка `bar` поэтому рисует только `y`-сетку/ось,
`x`-подписи категорий отсутствуют вовсе. Это честный, названный пробел (см. `ROADMAP.yaml`'s `bar`
description), не тихо забытый — строить категориальную ось стоит только когда реально понадобится
подписанная ось категорий, не заранее «на всякий случай».
