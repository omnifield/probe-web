# Пробел: явной нормированной границы «конфигурация против расширения» нет

**Вопрос (заказ P4, вопрос 2):** какой признак называется РЕШАЮЩИМ в разделении «расширение» и «конфигурация», и формулирует ли его источник ЯВНО?

**Ответ рынка: явного, сформулированного критерия нет.** Среды разделяют конфигурацию и расширение на практике — раскладкой, местом хранения, отдельными пунктами в переносе, — но ни один из перебранных источников не даёт определения «это конфигурация, потому что…».

## Что перебрано и что найдено вместо критерия

- **VS Code Settings** (`sources/vscode-settings.md`): настройки уложены в слои, расширение лишь ПОСТАВЛЯЕТ значения по умолчанию. Различие проведено по роли (данные-настройки vs код-расширение), но текст критерий не называет.
- **VS Code Settings Sync** (`sources/vscode-settings-sync.md`): `Extensions` и `Settings`/`Profiles` — РАЗДЕЛЬНЫЕ пункты синхронизируемого набора. Различие есть де-факто, определения нет.
- **JSON Schema** (`sources/json-schema-2020-12.md`): валидирует любой JSON безразлично к тому, конфигурация это или нет — по определению не проводит границу.
- **OSGi** (`sources/osgi-core-8.md`): единица — бандл (код); отчуждаемая конфигурация как отдельный нормированный вид в Core R8 §4 не выделена.

## Признак, используемый ДЕ-ФАКТО, хоть и не названный

Из перебранного вычитывается рабочий, но нигде не сформулированный признак: **конфигурация — данные без исполняемого кода, укладываемые в слои и переопределяемые; расширение — код, который эти данные потребляет и который поставляет их значения по умолчанию.** Косвенно это подтверждается тем, что конфигурация и расширение переносятся раздельными пунктами и хранятся в разных местах. Но это НАШЕ обобщение практики, а не цитата: ни один источник так не пишет.

## Почему это пробел рынка, а не недосмотр

Граница проходит внутри каждой среды по её собственной раскладке и нигде не поднята до нормы. Нет органа и нет проектного документа, который определил бы «конфигурацию» и «расширение» как различаемые сущности с решающим признаком. Есть только следствия различия (разные слои, разные пункты переноса, разное хранение).

**Следствие для рамки:** опереться на нормированный критерий «где кончается настройка и начинается расширение» нельзя — его нет. Если критерий нужен продукту, его придётся сформулировать самому; рынок его не выдаёт.

## Не перебрано (можно уточнить добором)

- JetBrains: разделение «настроек» и «плагинов», модель profiles.
- Модель пресетов инструментов сборки (ESLint `extends`, tsconfig `extends`) — где конфигурация сама наследуется и «расширяется» другой конфигурацией; возможно, там граница ещё размытее.
