# Пробел: что делать с сохранённым запросом при ИЗМЕНЕНИИ схемы данных — нормы нет

**Заход B, вопрос 4 распадается надвое. Первая половина — «хранение отбора как самостоятельной сущности» — ЗАКРЫТА: WFS 2.0 нормирует Stored Query (`sources/ogc-wfs-2.0-stored-query.md`) — именованный, параметризованный, серверный, с операциями List/Describe/Create/Drop. Вторая половина — «что рынок делает с сохранённым запросом, когда схема данных изменилась (миграция, версия формата, отказ)» — НЕ закрыта: нормированного ответа перебор не нашёл. Это и есть самая ценная часть вопроса, и она остаётся пробелом с названной границей.**

## Что проверено и с каким итогом

- **OGC WFS 2.0 Stored Query** (выписан) — нормирует сущность и её операции, но МОЛЧИТ о том, что происходит с сохранённым запросом, когда типы объектов/поля, на которые он ссылается, изменились. Нет ни версии схемы у запроса, ни правила отказа/миграции при рассинхроне. Проверено по открытой OGC-редакции 09-025r2.
- **Вендорские сохранённые объекты в панелях наблюдения** (Grafana saved dashboards/queries, Kibana saved objects, Elastic/OpenSearch) — известны как практика, но это РЕАЛИЗАЦИИ, не своды: у каждого своя схема миграции сохранённых объектов, и общей нормы между ними нет. Не выписаны как стандарт намеренно — практика вендора это не канон рынка (в шапке это было бы `издатель`=вендор, и статус «стандарт» пришлось бы отрицать).
- **GraphQL persisted queries / Relay** — есть механизм «сохранить запрос под идентификатором», но он про хранение ТЕКСТА запроса ради экономии трафика, а не про поведение при эволюции схемы; вопрос миграции при смене схемы там тоже не нормирован.

## Где норма могла бы быть, но не подтверждена

- Форматы версионирования схемы (напр., реестры схем — Confluent Schema Registry, JSON Schema `$schema`/`$id` версии) отвечают на «как версионировать СХЕМУ», но не на «что делать с ранее сохранённым ЗАПРОСОМ, когда схема сменилась». Стык этих двух вопросов рынком, похоже, не нормирован — это гипотеза следующего захода, не проверенный факт.

## Почему это результат, а не молчание

Граница названа: сущность сохранённого запроса нормирована (WFS, выписан), а её ПЕРЕНОСИМОСТЬ ЧЕРЕЗ ИЗМЕНЕНИЕ СХЕМЫ — нет; проверены OGC (норма только на сущность), вендорские панели (практика без общей нормы), persisted queries (про текст, не про эволюцию). Следующий заход не начинает с нуля: искать нужно не «сохранённый запрос вообще», а именно контракт «сохранённый отбор ↔ версия схемы ↔ поведение при рассинхроне», и первым непроверенным местом остаются реестры схем на стыке с сохранённым запросом.
